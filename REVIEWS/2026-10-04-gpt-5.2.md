### 1) Book-cap rebaseline can erase real losses (kill-switch bypass)
- **File:** `src/tradebot/risk.py`
- **Function:** `RiskManager.book_equity`
- **Claim (1):** The “account reset” heuristic can re-anchor the baseline after a real trading loss (not a dashboard reset), shrinking the apparent drawdown and preventing the slow-arm kill switch from firing.
- **Severity:** **HIGH**
- **Failure scenario:**  
  - **Config:** `risk.book_cap=50`, `risk.max_drawdown_pct=10`  
  - **State:** `book_baseline=100` (from earlier), `high_water_mark` previously set near `50` book-equity.  
  - **Inputs:** broker reports `raw equity=49` after losses in the underlying $100k paper account (e.g., other activity, bad fills, fees, or just actual loss).  
  - **Path:** baseline exists and condition `(raw < baseline*0.5 and raw <= cap*2)` becomes `(49 < 50 and 49 <= 100)` ⇒ **True**, so baseline is reset to `49`.  
  - **Wrong behavior:** `book_equity` becomes `min(cap + (raw-baseline), raw)=min(50+(49-49)=50,49)=49`. Any prior book losses embedded in `raw-baseline` are effectively forgiven because baseline moved to the new low. Subsequent recovery/loss is measured from the new baseline, so a drawdown that should have halted may never reach 10% from the (forgiven) HWM path.

### 2) Slow-arm max_positions check can be bypassed via “top-ups” (more positions than allowed)
- **File:** `src/tradebot/risk.py`
- **Function:** `RiskManager.filter_orders`
- **Claim (2):** `max_positions` enforcement only counts **buy orders with `to_notional > 0`**, not the *resulting* set of nonzero target positions. This allows ending the run holding more than `max_positions` if the bot already has positions and issues buys that don’t create new positions (or if positions exist without corresponding buy orders).
- **Severity:** **MED**
- **Failure scenario:**  
  - **Config:** `risk.max_positions=2`  
  - **Inputs:** `positions` already contains 2 symbols: `{"SPY": 10, "QQQ": 10}` but due to drift/corporate action/manual paper interference it also contains a tiny third position `{"IWM": 0.50}`.  
  - **Orders produced:** strategy wants to *top up* SPY and QQQ only (two buy orders), and generates **no order touching IWM** because `abs(delta)` is below `min_order_notional`.  
  - **Wrong behavior:** `filter_orders` sees only 2 buys and approves them; **no logic detects that after execution you still hold 3 positions**, violating `max_positions`. (Because the check is on order count, not on final nonzero position count.)

### 3) Slow-arm per-day idempotency key uses UTC date, can double-run on the same trading day (day rollover bug)
- **File:** `src/tradebot/run.py`
- **Function:** `run_once`
- **Claim (3):** Idempotency is keyed to `today = datetime.now(timezone.utc).date()` while “market day” logic is broker/exchange-local. Around ET evening hours, the UTC date flips while the market day is unchanged, so a second invocation can place a second set of orders “same trading day”.
- **Severity:** **HIGH**
- **Failure scenario:**  
  - **Time:** 20:30 ET on a trading day (01:30 UTC next day).  
  - **Inputs:** `ledger.last_run_date()` returns the prior UTC date (yesterday in UTC terms) while the market day is still the same ET trading day’s post-close window.  
  - **Wrong behavior:** `today` becomes tomorrow’s UTC date, `last_run_date()!=today`, and if `broker.market_open()` incorrectly returns true due to clock/calendar issues or a fake broker in replay/tests, the bot can re-run and submit a second rebalance for the same ET session. Even if Alpaca’s `market_open()` is usually false post-close, this is still a concrete day-key mismatch that breaks the claimed “idempotent per day” invariant.

### 4) Intraday arms: stop-loss can silently disappear for held symbols when bars missing (stale/absent data → protective logic skipped)
- **File:** `src/tradebot/fastarm.py`
- **Function:** `run_fast_once` (stop section), `live_px`
- **Claim (4):** For held symbols that temporarily have no bar and no quote snapshot available (API hiccup, symbol halt, feed glitch), `live_px` returns `None` and the OR-low stop is not evaluated (only a log line is written). This is a concrete “risk control fails open” state: the arm continues holding without being able to trigger the stop.
- **Severity:** **MED**
- **Failure scenario:**  
  - **Inputs:** You hold `SYM` with `or_low[SYM]=100`. Market drops hard to 90. At a tick, `broker.intraday_5min()` returns no bar for `SYM` and `quote_snapshot()` errors/returns no mid.  
  - **Wrong behavior:** stop branch logs `fast_stop_unevaluable` and **does not exit**, even though price has violated the stop. On the next tick you might still have no price, so the stop can be skipped repeatedly while losses grow.

### 5) Intraday arms in broker mode: modeled cost accrues on *intended* notional, not actual fills (money-math inconsistency)
- **File:** `src/tradebot/fastarm.py`
- **Function:** `_fill`, `_mark_equity`
- **Claim (5):** In broker mode, `cost_accrued` is increased using `qty*px` (intended notional) even though Alpaca may fill a different notional/avg price/partial fill. Net equity (`broker.equity() - cost_accrued`) can diverge materially from the modeled cost definition (“bps per side of executed notional”).
- **Severity:** **MED**
- **Failure scenario:**  
  - **Inputs:** Attempt buy with `qty=0.5`, `px=200` ⇒ intended notional $100; but broker partially fills only $30 (cash limits, fraction rules, etc.) or fills at different avg price.  
  - **Wrong behavior:** modeled cost accrues on $100, not $30, overstating costs and potentially triggering daily loss stop / drawdown kill prematurely, or understating if actual execution was larger than intended due to rounding/venue behavior.

### Overall risk assessment
Kill-switch integrity is **high risk** due to baseline re-anchoring and day-key/idempotency edge cases that can suppress halts or allow unintended repeated trading.
