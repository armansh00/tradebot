### src/tradebot/risk.py — `RiskManager.book_equity`
1) **Claim (HIGH): book-cap rebaseline can erase real losses and bypass the drawdown kill switch.**  
**Failure scenario:**  
- Config: `risk.book_cap=50`, `max_drawdown_pct=10`.  
- State: `book_baseline=100000` from prior capped run on the old $100k paper account (as described in config comments).  
- Inputs: broker reports `raw=80` (e.g., account was reset/withdrawn/changed, or you accidentally pointed “slow” at a $50 account that got topped up/down; any case where `raw` drops below half the old baseline and `raw <= cap*2` holds).  
- Behavior: `book_equity()` triggers rebaseline (`baseline=raw=80`) and returns `min(50+(80-80), 80)=50`.  
- Wrong result: equity presented to `check_drawdown()` becomes **50**, which *prevents* a halt that would have fired if equity were correctly treated as 80 (or if the historical HWM were preserved against a reset). This is explicitly “re-anchors baseline” logic, but it makes the drawdown rule dependent on a heuristic about resets; if the drop is a real loss path or misrouting to another account, the halt is bypassed.

2) **Claim (MED): capped equity can jump upward due to baseline reset, corrupting high-water mark and delaying future halts.**  
**Failure scenario:**  
- State: `high_water_mark=50` from normal operation under cap.  
- Then `book_equity()` reanchors baseline upward/downward due to the reset heuristic (same condition as above).  
- Equity as seen by `check_drawdown()` may “teleport” to 50 regardless of raw, causing HWM updates that do not reflect the true account trajectory; later, genuine losses may not reach the measured drawdown threshold because the HWM/starting point got rewritten.

### src/tradebot/risk.py — `RiskManager.check_drawdown`
3) **Claim (HIGH): high-water mark is global across runs/arms (single `state_path`), so drawdown kill can fail or misfire when multiple accounts are used.**  
**Failure scenario:**  
- Slow arm uses `cfg.state_path` and `RiskManager` in `run.py`. Fast/movers maintain separate state files (`fast_state_path`, `movers_state_path`) and their own drawdown logic.  
- If you ever run slow arm against a different account (as config comments suggest happened historically, and can happen again via env misconfig), the single `high_water_mark` persists and is applied to a new raw equity series.  
- Example: previous account HWM=100000; new account equity=50. `dd_pct≈99.95%` ⇒ immediate halt + flatten orders, even though nothing “drew down” in the new account. Reverse case: previous HWM low, new account high ⇒ drawdown won’t trigger soon enough. This is a kill-switch correctness failure driven by state reuse across accounts.

### src/tradebot/risk.py — `RiskManager.filter_orders`
4) **Claim (HIGH): `max_positions` enforcement is incorrect; it limits *buy orders per rebalance*, not resulting open positions.**  
**Failure scenario:**  
- Config: `max_positions=2`.  
- Current positions: already holding 2 symbols (`positions={"SPY":15,"QQQ":15}` market values).  
- Strategy rotates: targets want 2 different symbols (`{"IWM":15,"EFA":15}`), so `diff_orders()` produces 2 sells and 2 buys.  
- `filter_orders()` builds `buys` from approved buys and checks `len(buys) > max_positions`. Here `len(buys)=2`, so it approves both buys even though you *also still have the existing positions until sells fill*. In live execution (paper broker), orders are submitted sequentially without waiting for fills; buys can execute before sells, causing **4 concurrent positions**, violating the cap. (Even in notional terms, you can briefly exceed both position count and buying power.)

5) **Claim (MED): order-notional cap can be bypassed via broker-side partial fills / price movement because the cap is checked on intended notional, not filled notional.**  
**Failure scenario:**  
- Intended order `notional=30.00` passes.  
- Market gaps/executes at worse price (or broker interprets notional differently), resulting filled notional > 30.00.  
- There is no post-trade verification step; the cap is assumed satisfied. This is a concrete “risk cap fail” mode in broker execution paths.

### src/tradebot/run.py — `run_once`
6) **Claim (HIGH): kill switch can be bypassed for *the day it should fire* because drawdown check happens before submitting orders, but equity is sampled once and not recomputed after fills.**  
**Failure scenario:**  
- Equity at start of run is just above drawdown limit, so `check_drawdown(equity)` returns False.  
- The bot submits trades that immediately lose >10% intraday (or even instantly due to spread/price move).  
- Because `run_once` runs once per day and does not re-check drawdown after orders, the kill switch won’t fire until the next day’s run, allowing the bot to hold through the breach (and potentially worsen), violating “trades after the kill switch should have fired.” (This is especially relevant since you describe real broker fills now.)

7) **Claim (MED): idempotency can fail across UTC date boundary vs US trading day.**  
**Failure scenario:**  
- `today = datetime.now(timezone.utc).date().isoformat()`; `ledger.last_run_date()` is also UTC via `_now()` in ledger.  
- If the bot is scheduled in US evening hours (e.g., 21:00 ET = 01:00 UTC next day) it will consider it a new “day” and run again, despite being the same US trading session context (market may be closed, but `broker.market_open()` check is separate and only gates when closed; if `force=True` is used operationally, it can double-run).  
- Concrete wrong behavior: repeated rebalances in the same US trading day due to UTC roll, potentially exceeding trade expectations and interacting badly with risk caps.

### src/tradebot/fastarm.py — `run_fast_once` / `_fill`
8) **Claim (HIGH): max_positions/top_k can be violated in live mode because `_positions()` reads broker positions, but orders are submitted without waiting for fills; positions can remain “not yet updated” while additional buys are sent.**  
**Failure scenario:**  
- `top_k=2`, currently hold 0.  
- Two buy orders are sent in the same tick (loop over `candidates`). If broker accepts but positions API lags (common), `_positions()` still shows 0 while submitting the second buy (and potentially more on retries or subsequent ticks), so `slots = top_k - len(held)` is stale.  
- Wrong behavior: ends up with >2 positions in the account even though the arm believes it respected `top_k`.

9) **Claim (HIGH): daily loss stop and drawdown kill can silently fail to flatten in live mode because `_fill` sells via `broker.close(sym)` but never checks that a position was actually closed (filled), and `_positions()` may still show it held; yet the code proceeds as if risk is reduced.**  
**Failure scenario:**  
- A halt condition triggers; `_stand_down` iterates positions and calls `_fill(... "sell" ...)`.  
- In live mode `_fill` uses `broker.close(sym)` and treats any status not containing `"reject"` or `"cancel"` as success. Many broker APIs return statuses like `"accepted"`, `"pending"`, etc. That path accrues costs and logs “fast_order” and returns True, so `_stand_down` marks it “closed”.  
- If the close order is accepted but not executed (illiquidity, halted symbol, etc.), the position remains open. Next tick `_positions()` still shows it, so it will retry—good—but your logs and “flattened” list are incorrect and any downstream evaluation that assumes flattened-at-halt is wrong. More importantly: there is **no escalation** if close never fills; the arm remains exposed indefinitely while reporting it is halted.

10) **Claim (MED): halt-file flatten can be bypassed by running outside session hours; function returns `market_closed` before checking halt on those ticks.**  
**Failure scenario:**  
- Operator creates `.halt` at 08:00 ET while positions are open from a prior day due to some failure.  
- `run_fast_once`: it computes `halt` and *will* stand down before the market-hours return — good.  
- But if `.halt` is created after a tick, and the scheduler only invokes the arm outside market hours, the code returns `{"status":"market_closed"}` after halt handling (halt handling is before market-hours check, so this specific bypass does not occur).  
- However, the *overnight_flatten* logic only runs on `new_day` and only if the function runs during market hours (`if now < open_dt or now >= close_dt: return {"status":"market_closed"}` happens before `new_day` handling). If a scheduler runs only premarket, overnight positions will not be flattened until after open, violating “flat overnight” invariant and allowing exposure during the open gap.

11) **Claim (HIGH): money-math inconsistency in live mode equity used for risk controls: `_mark_equity` subtracts `cost_accrued` from `broker.equity()`, but `broker.equity()` already reflects unrealized P&L and may include commissions/fees semantics; modeled costs are then double-counted vs actual venue behavior assumptions.**  
**Failure scenario:**  
- Paper broker starts modeling some fees/slippage (or you later switch venue that does).  
- `_mark_equity` will still subtract modeled costs, overstating losses; this can spuriously trip drawdown/daily loss stops and halt. Conversely, evaluation compares “net” equity that is not consistent across venues. This is a concrete math-risk defect because kill-switch thresholds are based on this net number.

### src/tradebot/broker.py — `intraday_5min`
12) **Claim (HIGH): opening range and signal logic can use future (not-yet-available) bars due to requesting the full-day window up to 16:00 regardless of `now`.**  
**Failure scenario:**  
- At 10:05 ET, `intraday_5min()` requests bars from 9:30 to 16:00. Depending on provider behavior, the response can include the 10:05 bar as incomplete, or (worse) backfilled bars beyond `now` if the API returns the entire day’s bars for the session in progress (some data services do for paper/sim endpoints).  
- Then `lasts = df["c"].iloc[-1]` may point to a bar after the current time, and entries/exits compare against a price that wasn’t available at decision time (look-ahead).  
- Even if Alpaca normally doesn’t do this, the code is written in a way that makes it possible; there is no explicit filter `df["t"] <= now`.
