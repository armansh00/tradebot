### src/tradebot/risk.py — RiskManager.filter_orders

1) **Max positions cap can be bypassed via target “buys” represented as sells (or short covers)**
- **Severity:** HIGH
- **Defect:** The max-positions enforcement only counts orders where `side=="buy"` **and** `to_notional > 0`. Any order that results in a *new long position* but is encoded as a `sell` (e.g., crossing from short to long), or any broker/strategy path that uses `qty` (not `to_notional`) or omits/sets `to_notional` incorrectly, will not be counted toward `max_positions`.
- **Concrete failure scenario:**
  - **Inputs:** `cfg.risk.max_positions=2`. Current positions include a short in `A` (e.g., `positions={"A": -10.0}`) and flat elsewhere. Strategy generates orders that flip `A` from short to long (a “buy-to-cover and go long” scenario) but encodes it as a `sell` with negative-from/positive-to, or otherwise fails the `side=="buy" and to_notional>0` predicate.
  - **Wrong behavior:** `len(buys)` undercounts, so additional buys for two other symbols pass; end state can exceed `max_positions` with 3+ long holdings.

2) **Max positions cap ignores existing positions entirely**
- **Severity:** HIGH
- **Defect:** The code limits the *number of buy orders in this batch*, not the resulting number of open positions. If you already hold `max_positions` positions and you submit a “rotation” that sells one symbol and buys two new ones (common during rebalances), the buys list size can be 2 (<= max_positions) and pass—yet you may momentarily or ultimately hold 3 positions depending on execution order/partial fills.
- **Concrete failure scenario:**
  - **Inputs:** `max_positions=2`. Current positions: `{"SPY": 25.0, "QQQ": 25.0}`. Targets rotate out of `SPY` into `{IWM, EFA}` while keeping `QQQ`. `diff_orders` produces: sell SPY 25, buy IWM 25, buy EFA 25.
  - **Wrong behavior:** `filter_orders` sees 2 buys, allows both. If the SPY sell fails/rejects (venue rejects, network hiccup, insufficient qty due to rounding), both buys still go out, leading to **3 concurrent positions**, violating the cap.

3) **Order notional cap can be bypassed if broker.submit uses qty instead of notional**
- **Severity:** MED
- **Defect:** `filter_orders` only checks `o["notional"]`. In `broker.submit`, the actual request switches to `qty` if `order.get("qty")` is present, ignoring `order["notional"]`. Any code path that populates `qty` (even accidentally) can submit an order whose real notional exceeds `max_order_notional` while passing the risk check.
- **Concrete failure scenario:**
  - **Inputs:** An order dict contains `{"symbol":"SPY","side":"buy","qty": 1.0,"notional": 30.0,...}` while SPY trades at $600.
  - **Wrong behavior:** Risk check passes because `notional==30`. Broker uses `qty=1.0`, submitting ~$600 notional, violating the cap.

### src/tradebot/run.py — run_once

4) **Kill switch can be bypassed due to day-level idempotency preventing drawdown checks**
- **Severity:** HIGH
- **Defect:** The function exits early if `ledger.last_run_date() == today`, **before** any new equity snapshot or drawdown check. If equity collapses after the first run (intraday move, manual trade, broker correction), rerunning the bot the same day won’t re-check drawdown, won’t halt, and won’t flatten.
- **Concrete failure scenario:**
  - **Inputs:** Bot runs at 10:00 UTC, logs `run` with equity=50.00. Later the same day, equity drops to 44.00 (>-10% drawdown) due to market move. Operator reruns `run_once` expecting kill switch flatten.
  - **Wrong behavior:** Returns `{"status":"already_ran_today"}`; **no drawdown check**, no halt file written, no flatten orders sent.

5) **Kill switch flatten orders are not risk-checked; can exceed max_order_notional**
- **Severity:** MED
- **Defect:** On drawdown breach, flatten orders are constructed and submitted directly, bypassing `risk.filter_orders`. That can submit a liquidation notional far above `max_order_notional`.
- **Concrete failure scenario:**
  - **Inputs:** `max_order_notional=30`. Position market value is $45 in SPY. Drawdown triggers.
  - **Wrong behavior:** Bot submits a single close order with `notional=45`, violating the order notional cap. (If the intent is “kill switch overrides caps”, that’s not enforced/documented here; it’s a cap failure state per your criteria.)

6) **State corruption crash path: malformed JSON in state file bricks trading (no fail-closed halt)**
- **Severity:** MED
- **Defect:** `RiskManager._state()` does `json.loads(read_text())` with no exception handling. If the state file is manually edited, truncated by external tooling, or contains partial garbage, the bot will raise and terminate, and **will not place a halt** or flatten.
- **Concrete failure scenario:**
  - **Inputs:** `state.json` contains `{"high_water_mark": 50` (missing brace).
  - **Wrong behavior:** `run_once` crashes at `risk.book_equity()` / `check_drawdown()`; trading process stops without writing `.halt`, potentially leaving positions unmanaged.

### src/tradebot/fastarm.py — run_fast_once / _fill / risk controls

7) **Max positions / risk caps from config are not enforced for intraday arms**
- **Severity:** HIGH
- **Defect:** `config.yaml` defines global `risk.max_order_notional` and `risk.max_positions`, but `fastarm.py` does not consult `RiskManager` at all. It uses `f.top_k` and budget-per-slot sizing, but there is no enforcement that a single order notional stays under `risk.max_order_notional` (30) or that positions never exceed `risk.max_positions` (2) unless `top_k` happens to match.
- **Concrete failure scenario:**
  - **Inputs:** `risk.max_order_notional=30`, `fast.top_k=2`, equity=$50, cash=$50, two slots => budget_per_slot=25; OK. But if equity rises (or config changes) so budget_per_slot becomes 40 while global cap remains 30, arm will place $40 notional buys.
  - **Wrong behavior:** Intraday arm submits orders above the pre-registered max order cap with no rejection.

8) **Kill switch can be bypassed in broker mode because `_fill` records modeled cost even when the broker order is merely submitted (not filled)**
- **Severity:** MED
- **Defect:** In broker mode, `_fill` accrues `cost_accrued` immediately after `broker.submit(...)` unless status contains reject/cancel. It does not require confirmation of an actual fill. If orders remain unfilled, equity is marked down by costs, potentially **triggering drawdown/daily-stop halts unrelated to real losses**, and conversely can distort high-water mark evolution.
- **Concrete failure scenario:**
  - **Inputs:** Thin/halts cause market orders to be accepted but not filled promptly; broker returns status like `"accepted"` with `filled_qty=0`.
  - **Wrong behavior:** `cost_accrued` increases; `_mark_equity` subtracts it; drawdown/daily loss stop may trigger and halt/flatten even though no position exists. This is a money-math error affecting kill-switch correctness.

9) **Stop-loss and EOD flatten can silently fail to liquidate in broker mode due to `broker.close()` always using side="sell"**
- **Severity:** HIGH
- **Defect:** `_fill` in broker mode uses `broker.close(sym)` for any `side != "buy"`. `AlpacaBroker.close()` always returns `{"side":"sell"}` and calls `close_position(symbol)` which closes the whole position, but if the position is **short**, close_position requires a buy-to-cover; relying on a sell semantic is incorrect and may be rejected or behave unexpectedly depending on API.
- **Concrete failure scenario:**
  - **Inputs:** Account is short (possible via external/manual action or if broker allows shorting and a bug elsewhere creates it). `_stand_down` or stop-loss calls `_fill(..., "sell", ...)`.
  - **Wrong behavior:** `broker.close_position` may reject, leaving the short open; the kill switch “stands down” loops but cannot exit, violating “never stop exiting” invariant.

### src/tradebot/signals.py — momentum_12_1

10) **Look-ahead via insufficient skip handling**
- **Severity:** LOW (depends on how `daily_closes` is timestamped/when run executes)
- **Defect:** `momentum_12_1` checks only `len(closes) < lookback + 1`, but then indexes `end = closes.iloc[-(skip + 1)]`. If `skip` is large and the series is barely long enough for lookback but not for skip, you’ll index into the wrong region (or raise) depending on pandas behavior and length. Proper requirement should be `len(closes) >= lookback + skip + 1`.
- **Concrete failure scenario:**
  - **Inputs:** `lookback=252`, `skip=21`, but `daily_closes` returns only 253 points (enough for lookback+1, not enough for skip+lookback+1).
  - **Wrong behavior:** `end` and `start` are not separated by the intended horizons; momentum computed on unintended endpoints (or exception), producing a signal that implicitly uses too-recent data relative to the declared 12-1 definition.
