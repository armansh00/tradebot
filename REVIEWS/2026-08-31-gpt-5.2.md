### src/tradebot/risk.py — `RiskManager.filter_orders`
1) **Claim:** `max_positions` cap can be bypassed by “buy” orders that reduce an existing long (or cover a short), letting the bot exceed the allowed number of concurrent positions.  
**Severity:** HIGH  
**Why concrete:** The cap logic counts only `buys = [o for o in approved if o["side"] == "buy" and o["to_notional"] > 0]` and rejects excess *buy orders*, not excess *resulting positions*. It also ignores “sell” orders that open/increase shorts (which are positions too).  
**Failure scenario:**  
- Config: `risk.max_positions = 2`  
- Current positions: `{"SPY": 15, "QQQ": 15}` (2 positions)  
- Targets (buggy strategy output or manual override) include adding a new long while reducing an existing long via a *buy* (e.g., covering a short) doesn’t apply here; more direct: open a short via sell.  
- Orders produced:  
  - `{"symbol":"IWM","side":"sell","from_notional":0,"to_notional":-15,"notional":15}` (opens a new short position)  
  - `{"symbol":"TLT","side":"sell","from_notional":0,"to_notional":-15,"notional":15}` (opens another short)  
These are **not** counted in `buys`, so **both are approved**, resulting in 4 concurrent positions (2 longs + 2 shorts) despite `max_positions=2`.

### src/tradebot/run.py — `run_once`
2) **Claim:** Kill-switch flatten orders can violate `max_order_notional`, and the code does not route them through any order-level risk checks.  
**Severity:** HIGH  
**Why concrete:** On drawdown breach, it builds `flatten` orders with `notional = abs(mv)` where `mv` is current market value per symbol. It then submits them directly: `results = [broker.submit(o) for o in flatten]`. No `risk.filter_orders` call is applied to flatten orders.  
**Failure scenario:**  
- Config: `risk.max_order_notional = 30.0`  
- Positions: `{"SPY": 120.0}` (market value $120)  
- Equity falls enough to trigger drawdown.  
- Bot generates flatten order with `notional=120.0` and submits it despite the explicit per-order cap of $30.  
Result: the “hard brake” path places an order 4× above the configured maximum order notional.

3) **Claim:** Kill-switch can fail to flatten shorts due to broker API mismatch: uses `broker.submit` with `notional` for buys (to cover shorts), which may be invalid/unsupported for buys in some broker implementations; failure is not checked and bot records positions as flattened even if orders rejected.  
**Severity:** MED  
**Why concrete:** Flatten uses `side: "buy" if mv < 0 else "sell"` and always passes `notional: abs(mv)` into `broker.submit`. If the broker rejects notional buys (common constraint: notional may be allowed only for buys, or only certain account types; or a particular wrapper expects `qty` for closing shorts), the code doesn’t handle it. It logs whatever `broker.submit` returns, then logs `positions={}` and returns `"killed"`.  
**Failure scenario:**  
- Positions: `{"AAPL": -25.0}` (short market value -$25).  
- Drawdown triggers.  
- Flatten sends `{"side":"buy","notional":25}`; broker rejects (e.g., requires `qty` to cover shorts).  
- Bot still writes `ledger.write("run", ..., positions={}, halted=True)` and exits `"killed"` although the short remains open.

### src/tradebot/fastarm.py — `run_fast_once`
4) **Claim:** In live/broker mode, the arm can exceed `top_k` (max concurrent positions) because it may place multiple buy orders in one tick before broker positions reflect fills.  
**Severity:** HIGH  
**Why concrete:** Entry logic determines `held = _positions(...)` once, computes `slots = f.top_k - len(held)`, then loops through candidates and calls `_fill(..., "buy", ...)`. In broker mode, `_positions` reads the account, but after submitting an order the new position may not yet appear in `get_all_positions()` due to latency/eventual consistency. The code does not update a local “pending” count; it continues submitting until `slots` hits 0 based on the *stale* `held` size from before any buys.  
**Failure scenario:**  
- `top_k=2`, currently `held` empty at tick time.  
- Two buy orders are submitted; broker positions still show empty until later.  
- If code is invoked again quickly (or within same process with multiple arms/ticks) or `slots` bookkeeping is wrong due to partial fills, it can submit more buys than intended because it’s not reconciling with open orders/pending state. Even within one call, if `len(held)` is 0 and `slots=2`, it will submit up to 2 buys; but if the account already has 2 positions that are not returned by `positions_detail()` yet (API lag after prior actions), it can open more, exceeding `top_k`.

5) **Claim:** Daily-loss-stop and drawdown-kill attempt to sell using a quantity sourced from `positions_detail()` (`qty` shares), but `_fill` in broker mode ignores that qty and uses `broker.close(sym)` (full liquidation). This can liquidate more than intended and break money-math/trade-count logic that assumes a specific qty.  
**Severity:** MED  
**Why concrete:** `_fill(... side="sell" ...)` in live mode always does `result = broker.close(sym)` regardless of the `qty` argument. Call sites pass `pos["qty"]`, but it is unused; if later logic assumes partial reductions (or if `pos["qty"]` is stale/incorrect), the actual action is “close entire position”, not “sell qty”.  
**Failure scenario:**  
- Account holds 2 lots due to external/manual intervention or partial fills; `positions_detail()` shows qty=1 due to stale read.  
- Stop triggers and code believes it’s selling qty=1; broker closes the *entire* position.  
- The arm’s ledger records qty=1, but real liquidation is qty=2. Downstream P&L attribution/cost accrual becomes inconsistent with what actually happened.

6) **Claim:** In broker mode, modeled costs accrue on every successful sell/buy, but there is no reset/realization boundary; costs can grow without bound across days and permanently depress equity, potentially triggering the drawdown kill even if the underlying account equity is making new highs.  
**Severity:** MED  
**Why concrete:** `st["cost_accrued"]` monotonically increases and is subtracted from broker equity in `_mark_equity`. There’s no mechanism to “pay”/reset it (it’s not moved into cash; it just accumulates). That means the arm’s “net equity” can only diverge downward vs broker equity as time goes on, creating artificial drawdowns unrelated to trading losses.  
**Failure scenario:**  
- Broker equity rises from 50 → 55 over weeks.  
- Modeled costs accrue to, say, 6.  
- Net equity computed as 55 - 6 = 49, which is below the historical HWM (which may have been recorded earlier), producing a drawdown and halting trading even though real book is profitable.

### src/tradebot/broker.py — `AlpacaBroker.intraday_5min`
7) **Claim:** Timestamp localization likely wrong: `datetime.combine(date, time, et)` uses a `tzinfo` argument positionally in a way that is easy to get wrong across Python versions; if it produces a naive datetime, Alpaca request start time may be interpreted as UTC, shifting the opening range window and introducing look-ahead/stale-window bugs.  
**Severity:** MED  
**Why concrete:** The code uses `datetime.combine(datetime.now(et).date(), dtime(9, 30), et)`; correctness depends on Python’s `datetime.combine` signature supporting `tzinfo` as the third positional argument (it does in modern Python, but this is fragile and frequently misused). If it ends up naive or wrong tz, the returned bars and their timestamps can include premarket or exclude early regular-session bars, breaking the “first 30 minutes” definition and potentially including bars after `or_end`.  
**Failure scenario:**  
- On an environment where `datetime.combine` doesn’t apply tzinfo as expected (or a refactor introduces naive datetimes), `start` becomes naive and interpreted by the API as UTC.  
- Request starts at 09:30 UTC (05:30 ET), pulling premarket bars; OR computed from wrong window; entries/exits are based on data outside intended session.
