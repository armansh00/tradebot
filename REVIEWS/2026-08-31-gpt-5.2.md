### src/tradebot/risk.py — `RiskManager.book_equity`
1) **Claim (HIGH): book-cap “reset” can erase real losses and bypass drawdown kill.**  
**Why:** baseline is re-anchored when `(raw < baseline * 0.5 and raw <= cap * 2)`. That condition can be satisfied by genuine trading losses, not only a “dashboard reset”. Re-anchoring increases computed `book_equity` and can prevent `check_drawdown()` from ever seeing the true drawdown.  
**Failure scenario:**  
- Config: `book_cap=50`, `max_drawdown_pct=10`.  
- Prior state: `book_baseline=100000` (slow arm on the legacy $100k paper account; this is plausible per config comments).  
- Genuine loss: account equity falls to `raw=95` (still possible with leveraged/buggy trading, or if the account had been drawn down massively over time).  
- Condition: `95 < 100000*0.5` true AND `95 <= 50*2` true → baseline re-anchors to 95.  
- Returned `book_equity = min(50 + (95-95)=50, raw=95)=50`.  
- Result: the strategy/risk layer now “believes” equity is $50 (no drawdown) instead of reflecting catastrophic loss from the original baseline, so `check_drawdown(50)` won’t halt for the true drawdown path.

### src/tradebot/risk.py — `RiskManager.check_drawdown`
2) **Claim (HIGH): high-water mark can be permanently raised before confirming flatten succeeded; halt can lock in with open risk.**  
**Why:** function writes `high_water_mark = max(prev_hwm, equity)` *before* any trading/flattening and immediately halts if breached. In `run.py`, after `risk.check_drawdown(equity)` returns True, bot attempts to flatten, but does not verify fills/position closure succeeded. If flatten orders are rejected (buying power, short locate, API error), you can end up halted with positions still open; subsequent runs refuse to trade because `.halt` exists, so you never get another chance to flatten via the bot.  
**Failure scenario:**  
- You hold a short (negative `market_value`) in Alpaca paper (possible from prior manual action or earlier bug).  
- Equity drawdown breaches limit → `check_drawdown` writes halt file.  
- `run.py` generates flatten order for short as a **buy** notional `abs(mv)`. Broker rejects buy due to insufficient buying power.  
- Bot logs `order` results but does not check status, then logs `positions={}` (incorrectly; see finding #5) and returns `{"status":"killed"}`.  
- Next invocation: `risk.halted()` true → exits immediately, leaving the short open indefinitely.

### src/tradebot/risk.py — `RiskManager.filter_orders`
3) **Claim (HIGH): `max_positions` enforcement is incorrect; it counts buy *orders*, not resulting positions, so you can exceed the cap.**  
**Why:** it computes `buys = [o for o in approved if o["side"]=="buy" and o["to_notional"] > 0]` and caps by `len(buys)`. That does not account for:
- existing positions already held (which may persist), and
- multiple buy orders that *increase* existing holdings vs open new symbols.  
Also it ignores the case where sells are rejected upstream and buys still go through, increasing concurrent positions beyond the limit.  
**Failure scenario:**  
- `max_positions=2`.  
- Current positions: `{"SPY": 10, "QQQ": 10}` (already at cap).  
- Targets shift to `{ "SPY":0, "QQQ":0, "IWM":10, "EFA":10 }`.  
- `diff_orders` creates four orders: sell SPY, sell QQQ, buy IWM, buy EFA.  
- If the two sells get rejected by broker (or only partially fill) but buys are accepted, you temporarily hold 4 positions even though risk “approved” because `len(buys)==2` is within cap. No logic checks *resulting* position count.

### src/tradebot/run.py — `run_once`
4) **Claim (MED): risk caps can be bypassed on flatten; kill-switch flatten submits orders with notionals above `max_order_notional`.**  
**Why:** when drawdown triggers, `flatten` orders use `notional=abs(mv)` directly, and they bypass `RiskManager.filter_orders`. If a position market value is > $30 (your cap), flatten submits an order bigger than the cap. Even if you *want* flatten to ignore caps, that violates the stated “Hard brakes checked before every order” invariant and can create inconsistent behavior (e.g., broker rejects large notional close).  
**Failure scenario:**  
- `max_order_notional=30`. You somehow have `SPY` market_value = $80 (e.g., price jumped after entry, or earlier code version allowed >$30, or manual position).  
- Drawdown triggers. Bot submits a single sell notional $80. If broker rejects due to constraints (or partial fill), you remain exposed but halted (ties into finding #2).

5) **Claim (HIGH): position state logged as empty on kill even if flatten fails.**  
**Why:** after drawdown, code unconditionally writes `ledger.write("run", equity=equity, positions={}, halted=True)` rather than querying broker positions post-flatten or reflecting actual results. This creates a false record used by later evaluation/reporting and can mask that the bot is halted with open positions.  
**Failure scenario:** same as #2: flatten buy-to-cover rejected, yet ledger shows `positions={}` and `status=killed`, misleading monitoring and any postmortem logic.

### src/tradebot/fastarm.py — `run_fast_once`
6) **Claim (HIGH): in broker mode, exits use `broker.close(sym)` but still pass/compute `qty`; position sizing fields can be stale/incorrect and stop logic can crash.**  
**Why:** `_positions()` in live mode returns `broker.positions_detail()` which includes `qty` and `entry_px`, but in `_fill` live sell path it ignores `qty` and calls `broker.close(sym)`. That’s fine for execution, but upstream code assumes every `pos` has `qty` and `entry_px` in multiple places; if Alpaca returns different schema or a position is in a nonstandard state, your arm can raise KeyError before flattening (no try/except), leaving trading running without applying stops.  
**Concrete failure scenario:**  
- Alpaca API returns a position object missing `avg_entry_price` temporarily (or returns `None` during corporate action / symbol change). `positions_detail()` casts `float(p.avg_entry_price)` → raises `TypeError`.  
- `run_fast_once` crashes before kill-switch / EOD flatten, leaving positions unmanaged intraday.

7) **Claim (MED): daily-loss-stop and drawdown-kill assume sells will always work; if close is rejected, trading continues (daily stop) or halts with exposure (drawdown).**  
**Why:** `_fill` returns False on rejection, but callers ignore it in multiple critical loops:
- drawdown kill loop ignores return; then sets `st["halted"]=True` regardless.
- daily loss stop ignores return; then sets `st["stopped_today"]=True` regardless.  
**Failure scenario:**  
- You hold a position that cannot be closed (broker error / rejection).  
- Daily loss stop triggers: close rejected; bot marks stopped_today True and will not attempt further risk-reducing actions later in the day, while still holding the losing position.

8) **Claim (HIGH): end-of-day flatten timing ignores half-days; bot can hold positions past close.**  
**Why:** fast arm hardcodes `OPEN_T=9:30`, `CLOSE_T=16:00` and computes `flat_dt` from that. Broker has `session_today()` that handles half-days, but fast arm does not use it.  
**Failure scenario:**  
- Day after Thanksgiving: market closes 13:00 ET.  
- `flat_dt` computed as 15:30 ET, which is after the actual close; `now >= flat_dt` never becomes true while market is open.  
- Bot can carry positions into the close unintentionally; then at `now >= close_dt` (16:00) it returns `market_closed` without flattening.

### src/tradebot/broker.py — `AlpacaBroker.daily_closes` / `signals.snapshot`
9) **Claim (MED): look-ahead/stale data risk: daily close series may include the current day’s partial bar, contaminating momentum/SMA decisions.**  
**Why:** `daily_closes()` fetches `TimeFrame.Day` bars from `start=now - ...` with no explicit `end` and no filtering to exclude “today” if the trading day is in progress. `signals.snapshot` always uses `closes.iloc[-1]` as “price” and includes it in SMA and “above_sma” check; momentum uses `end=closes.iloc[-(skip+1)]` which could be shifted if today’s incomplete bar is present.  
**Failure scenario:**  
- Bot runs intraday (or schedule drift) while today’s daily bar exists as an updating/incomplete value.  
- Strategy may treat today’s partial bar as a completed close, effectively using information not available at prior close and altering eligibility/ranking.
