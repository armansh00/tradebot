### src/tradebot/run.py — `run_once`

1) **Claim:** Kill-switch can be bypassed when `force=True` even if market is closed; flatten orders are submitted into a closed market and can be rejected, leaving exposure while the bot records a “killed/flattened” outcome.  
**Severity:** HIGH  
**Scenario:** Inputs: `force=True`, `broker.market_open() == False`, `positions={"SPY": 25.0}` (long), `equity` below drawdown threshold so `risk.check_drawdown(equity)` returns True.  
Path: The `market_open()` guard is skipped because of `force`, drawdown triggers, `flatten` orders are built and `broker.submit()` is called despite market closed. If broker rejects/queues or errors, positions remain open. The code then logs `ledger.write("run", ..., positions={}, halted=True)` and returns `{"status":"killed"}`, falsely indicating flattened positions and halted state.

2) **Claim:** Drawdown kill-switch computes drawdown on *book-capped equity* (`risk.book_equity(broker.equity())`) rather than true account equity, so a real-account drawdown can exceed limits without triggering the halt.  
**Severity:** HIGH  
**Scenario:** Config: `risk.book_cap=50`, `max_drawdown_pct=10`. True account equity path: starts at $10,000, rises to $11,000 (true HWM), then falls to $9,900 (true DD = 10%).  
But `equity = risk.book_equity(raw)` returns near ~$50 ± small P&L and will not reflect the $1,100→$9,900 drawdown magnitude. Result: `risk.check_drawdown(equity)` never sees the true DD and does not halt; trading continues after a real 10% account drawdown.

3) **Claim:** `max_positions` enforcement is incorrect because it counts only *buy orders in the current batch*, not resulting open positions after sells/buys; the bot can end the rebalance holding more positions than allowed.  
**Severity:** HIGH  
**Scenario:** `max_positions=2`. Current positions already at cap: `positions={"SPY": 25, "QQQ": 25}`. Targets introduce rotation but also add new names due to signal changes + dust threshold behavior, generating orders: `sell SPY to 0`, `buy IWM to 25`, `buy EFA to 25`, while `sell QQQ` is skipped because its delta falls under `min_order_notional` (or strategy targets keep it).  
`filter_orders()` only limits number of buy orders, not final holdings. Approved buys could be 2 (IWM,EFA) while QQQ remains, leaving 3 positions after execution.

### src/tradebot/risk.py — `RiskManager.book_equity`

4) **Claim:** “Account reset” re-anchoring condition can erase real losses and prevent the drawdown halt by lowering the baseline after a loss, especially when trading a small account near the cap.  
**Severity:** HIGH  
**Scenario:** `book_cap=50`. First run baseline recorded at `raw=100` (baseline=100). Then a genuine trading loss drops account equity to `raw=40`. Condition `(raw < baseline*0.5 and raw <= cap*2)` becomes `(40 < 50 and 40 <= 100)` => True, so baseline is reset to 40.  
Now `book_equity = min(cap + (raw-baseline), raw) = min(50 + 0, 40)=40`. High-water mark logic now operates on a re-anchored baseline, effectively forgiving the 60% drawdown from 100→40; halt may never trigger if this reset happens before `check_drawdown()` accumulates/retains the old HWM (and it will, because `run_once` only feeds it the capped equity series).

### src/tradebot/risk.py — `RiskManager.filter_orders`

5) **Claim:** Order notional cap can be bypassed by `NaN` notionals: comparison `NaN > max_order_notional` is False, so the order is approved and passed to broker.  
**Severity:** MED  
**Scenario:** `orders=[{"symbol":"SPY","side":"buy","notional": float("nan"), ...}]`.  
`if o["notional"] > cap:` evaluates False, so approved. `broker.submit()` receives `notional=round(nan,2)` which yields `nan` and may be coerced, rejected, or (in some brokers) treated unexpectedly. This violates “fail closed” intent and can lead to uncontrolled behavior.

6) **Claim:** `max_positions` enforcement uses `to_notional > 0` on buys, but does not consider existing positions kept (no buy order) and does not consider sells that reduce positions; it’s not checking the *post-trade portfolio cardinality*.  
**Severity:** HIGH  
**Scenario:** Existing positions: 2 names. Strategy targets keep both and add a third by increasing it from a tiny existing stub (e.g., $1.99 dust below `min_order_notional` previously left in portfolio). If that third name already exists in `positions` at small positive notional and target increases it, it creates a buy order; buys count may be ≤2, but final distinct positions can exceed 2 because dust positions are never force-closed due to `min_order_notional` and cardinality is never enforced on holdings.

### src/tradebot/fastarm.py — `run_fast_once`

7) **Claim:** Kill-switch bypass via missing halt file integration: config’s global `risk.halt_file` is ignored by the fast/movers arms; they keep trading even when the slow arm is halted.  
**Severity:** HIGH  
**Scenario:** `.halt` file exists (slow arm halted). Calling `run_fast_once()` returns `{"status":"ok"...}` and continues trading because it only checks `st.get("halted")` in its own JSON state, not `cfg.halt_path.exists()`.

8) **Claim:** Look-ahead/stale data: ORB uses `lasts` from the latest 5-min bar in `broker.intraday_5min(universe)` without filtering bars to `<= now`; if broker returns bars beyond `now` (common in backtests, caching layers, or clock skew), entries/exits use future prices.  
**Severity:** HIGH  
**Scenario:** `now=10:05 ET`, but `intraday_5min()` returns bars through 10:30 due to provider latency/caching or because it always returns “latest completed bar” beyond `now` in simulation. `lasts` becomes 10:30 close, and breakout decision uses that future close relative to OR high. Bot enters trades it could not have known at 10:05.

9) **Claim:** Opening-range window is defined by timestamp `< or_end` but bars are 5-minute; with `or_minutes=30`, you intend 9:30–10:00. If the 10:00 bar timestamp equals 10:00 and represents 10:00–10:05, it is excluded (good). But if provider timestamps bars at bar *end* (10:00 means 9:55–10:00), it is excluded incorrectly, shrinking the opening range to 25 minutes.  
**Severity:** MED  
**Scenario:** Provider’s bar timestamp convention is end-time. Bar labeled 10:00 contains 9:55–10:00, but `t < 10:00` excludes it, making OR only 9:30–9:55. This changes hi/lo and triggers false breakouts/stops.

10) **Claim:** Simulated P&L math is inconsistent: position `entry_px` includes cost (slippage), but equity marking uses mid/last `px` without subtracting exit cost until close; this systematically overstates unrealized equity and can delay drawdown/daily-loss stops.  
**Severity:** MED  
**Scenario:** You buy at `fill_px=100.05` (with 5 bps), last trades at `100.00`. `_mark_equity` uses `qty*100.00` (already below entry) but does not account for the *additional* cost to exit (another 5 bps). True liquidation value is `100.00*(1-5bps)=99.95`. Stops based on marked equity will trigger later than they should, allowing losses to exceed stated caps.

### src/tradebot/ledger.py — `Ledger.write`

**Severity:** MED  
**Scenario:** Process crashes mid-line write, leaving a truncated JSON record. Next run, `Ledger.read()` hits that line and raises `JSONDecodeError`, which can abort `run_once` before it checks/records risk decisions, breaking “errors fail closed” and idempotency guarantees.
