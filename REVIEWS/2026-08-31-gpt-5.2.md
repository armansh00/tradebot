### src/tradebot/risk.py — `RiskManager.book_equity`
1) **Claim:** Book-cap baseline can re-anchor after real trading losses, shrinking the effective drawdown and delaying/avoiding the kill switch.  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `risk.book_cap=50`, `risk.max_drawdown_pct=10`.  
- Day 1: baseline set at `raw=100` (larger paper account). Book equity = `min(50+(100-100),100)=50`. HWM becomes 50.  
- Market loss occurs in the real account: `raw` drops to 45 due to actual trading losses (e.g., holding untracked positions/manual trades in the paper account, or another bot trading same account).  
- Condition triggers: `raw < baseline*0.5` (45 < 50) and `raw <= cap*2` (45 <= 100) ⇒ baseline is reset to 45.  
- New book equity becomes `min(50+(45-45),45)=45`, and subsequent HWM/drawdown are now measured off 45 instead of reflecting the true loss from the earlier baseline. This can prevent/retard halting relative to the intended “equity 10% below high-water mark” invariant for the capped book across account-level losses.

### src/tradebot/risk.py — `RiskManager.filter_orders`
2) **Claim:** `max_positions` enforcement is incorrect; it caps the number of *buy orders* in a batch, not the resulting number of open positions.  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `max_positions=2`.  
- Current positions already at limit: `positions={"SPY": 25, "QQQ": 25}`.  
- Strategy decides to rotate: targets become `{"IWM":25, "EFA":25}` producing orders: sell SPY, sell QQQ, buy IWM, buy EFA (2 buys).  
- `filter_orders` sees `len(buys)==2` and approves both buys even though sells might fail/reject at broker or partially fill.  
- If sells fail but buys succeed, end state can be 4 positions (SPY, QQQ, IWM, EFA) > `max_positions`, violating the cap.
   - This is a concrete bypass because enforcement is not based on *post-trade holdings* and not tied to confirmed fills.

3) **Claim:** `max_positions` check ignores the sign of `to_notional` and existing holdings semantics; it can approve “buy” actions that increase exposure even when already over limit (e.g., existing >max due to manual positions).  
**Severity:** MED  
**Failure scenario:**  
- Current positions: 3 symbols due to manual intervention: `{"SPY": 10, "QQQ": 10, "TLT": 10}` with `max_positions=2`.  
- Strategy chooses to keep SPY and QQQ, target those two only; diff generates a sell for TLT plus possibly a buy add to SPY.  
- `filter_orders` only limits number of buys, not whether the portfolio is already over-positioned; it will happily approve the SPY buy while still holding 3 positions until TLT sell fills (or if it fails, permanently).

4) **Claim:** Order notional cap can be bypassed via split orders in a single run; there is no total-trade or per-symbol per-run notional cap.  
**Severity:** MED  
**Failure scenario:**  
- Config: `max_order_notional=30`.  
- A bug or upstream strategy change produces two buy orders for the same symbol each at $30 (e.g., duplicated symbol entries or multiple diffs).  
- `filter_orders` approves both because it only checks each order independently. Result: $60 notional executed in one run despite the intended “no single order above $30” often being used as a practical throttle for the whole run/symbol.

### src/tradebot/run.py — `run_once`
5) **Claim:** Kill switch can be bypassed intra-run because drawdown is checked only once, before submitting new orders, using **pre-trade equity**; large fills can push equity below the drawdown threshold without triggering halt/flatten until the next day.  
**Severity:** HIGH  
**Failure scenario:**  
- Morning equity (book) = 50, HWM = 50, drawdown limit 10% ⇒ threshold 45.  
- `check_drawdown(50)` passes.  
- Bot submits buys; market moves immediately against positions the same day and equity becomes 44 by end of day.  
- `run_once` never re-checks drawdown after execution; it logs the *old* equity (the pre-trade value) into the ledger `run` record.  
- Result: drawdown breach occurs but no halt/flatten until next run, violating “flatten + halt” on breach.

6) **Claim:** `run_once` idempotency uses UTC date (`datetime.now(timezone.utc).date()`), which can cause double-trading or skipped trading around ET midnight boundaries.  
**Severity:** MED  
**Failure scenario:**  
- Bot is “designed to run once per trading day” (US market).  
- At 20:30 ET (00:30 UTC next day), market is closed but if `force=True` or broker’s `market_open()` is mistakenly true (or used in another context), `today` becomes the next UTC date while it is still the prior ET trading day.  
- Ledger `last_run_date()` compares against UTC-day string from `ts` (also UTC). This makes “once per trading day” actually “once per UTC day”, enabling either:
  - A second run during the same ET trading day after 00:00 UTC (duplicate trades), or
  - Preventing a legitimate run early the next ET morning if a prior late-evening maintenance run wrote a `run` record under that UTC date.

### src/tradebot/fastarm.py — `run_fast_once`
7) **Claim:** Fast/movers arms ignore the global halt file (`risk.halt_file`); kill-switch presence stops only the slow arm.  
**Severity:** HIGH  
**Failure scenario:**  
- `.halt` is present (manual safety stop or slow-arm drawdown halt).  
- `run_once` will skip trading, but `run_fast_once` checks only `st.get("halted")` in its own state and does not consult `cfg.halt_path.exists()`.  
- Outcome: intraday simulated trading continues despite an explicit halt switch being set.

8) **Claim:** Daily loss stop does not actually stop trading for the day; it flattens and sets `stopped_today=True` but does not persist state immediately and can re-enter if the process crashes before `_save_state`.  
**Severity:** MED  
**Failure scenario:**  
- Equity drops enough to trigger daily loss stop, positions flattened, `stopped_today=True` set.  
- Process crashes before reaching the end-of-function `_save_state(state_path, st)`.  
- Next invocation reloads state without `stopped_today` set and can enter trades again the same day, violating “flatten, done for the day.”

9) **Claim:** Opening range uses all bars with `t < or_end` from `broker.intraday_5min(universe)` without filtering out future bars relative to `now`; if the broker returns the full day’s bars (or delayed caching returns bars beyond `now`), this is a look-ahead bug.  
**Severity:** HIGH (if broker returns future bars; code assumes it doesn’t)  
**Failure scenario:**  
- At 10:05 ET, `now` is shortly after `or_end` (10:00).  
- `intraday_5min` returns bars through 16:00 (common in backtests or some cached data sources).  
- `opening_range(df, or_end)` correctly uses pre-10:00 bars, but **entry/exit logic uses `lasts = df["c"].iloc[-1]`**, which would be the **16:00 close**, not the current price at 10:05.  
- Bot will enter/exit based on end-of-day prices, a direct look-ahead.

10) **Claim:** End-of-day flatten scheduling is hardcoded to 16:00 ET and ignores exchange half-days; can carry positions past the actual close and never flatten that day.  
**Severity:** MED  
**Failure scenario:**  
- On a 13:00 ET early close day, broker bars stop at 13:00 but `close_dt` is still set to 16:00 and `flat_dt` to 15:30.  
- The code will keep attempting intraday logic between 13:00 and 15:30 with stale `lasts` and will not trigger EOD flatten at the intended time relative to the actual session end. If it entered positions before 13:00 and the scheduler runs after 13:00 but before 15:30, it may *not* flatten because `now < flat_dt` and OR logic can still run on stale data.

### src/tradebot/fastarm.py — `_fill`
11) **Claim:** P&L math is wrong for sells when closing: it uses the `qty` passed into `_fill` rather than the stored position qty, enabling incorrect P&L (and cash) if caller passes mismatched qty.  
**Severity:** LOW (current callers pass matching qty, but this is a concrete defect in the function contract)  
**Failure scenario:**  
- A future partial-close feature calls `_fill(..., "sell", qty=pos_qty/2, ...)` but still `pop(sym)` removes the entire position.  
- Cash increases by `qty * fill_px` (half position), but the position is removed entirely, losing remaining shares from state.  
- Logged pnl computed on half qty, equity becomes inconsistent/corrupt.
