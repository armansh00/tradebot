### Finding 1
- **File:** `src/tradebot/risk.py`
- **Function:** `RiskManager.book_equity`
- **Claim (1):** **Book-cap rebaseline can erase real losses and bypass the drawdown kill switch.**
- **Severity:** **HIGH**
- **Failure scenario:**  
  **Inputs:** `risk.book_cap = 50`; prior `state["book_baseline"]=100000` (slow arm legacy on $100k paper); account suffers a real loss or withdrawal bringing `raw` to `40000` (still far above cap), then later drops to `raw=80` (e.g., cash transfer out / broker reset / test operator mistake), satisfying `(raw < baseline*0.5 and raw <= cap*2)` because `80 < 50000` and `80 <= 100`.  
  **Wrong behavior:** baseline is reset to `80`, and returned book equity becomes `min(50 + (80-80), 80)=50`. This “reanchors” after a huge realized loss path (or a partial reset) and allows subsequent drawdown tracking to restart from an artificially clean slate, potentially avoiding the configured `max_drawdown_pct` halt that should have fired based on the true high-water mark/economic loss.

### Finding 2
- **File:** `src/tradebot/risk.py`
- **Function:** `RiskManager.check_drawdown`
- **Claim (2):** **High-water mark is updated and persisted *before* checking drawdown; a transient equity spike can permanently raise the HWM and force false halts later (or make halts unrecoverable).**
- **Severity:** **MED**
- **Failure scenario:**  
  **Inputs:** broker briefly reports `equity=200` due to API glitch, then normalizes to `equity=50`.  
  **Wrong behavior:** `high_water_mark` is saved as `200` immediately; next run with correct equity computes drawdown `(200-50)/200=75%` and halts + flattens even though no real drawdown occurred. Because the HWM is already saved, the system can remain effectively bricked unless state is manually edited/cleared.

### Finding 3
- **File:** `src/tradebot/risk.py`
- **Function:** `RiskManager.filter_orders`
- **Claim (3):** **`max_positions` enforcement is incorrect: it counts buy *orders*, not resulting positions, and can allow exceeding the cap.**
- **Severity:** **HIGH**
- **Failure scenario:**  
  **Inputs:** `max_positions=2`. Current positions already hold 2 symbols (A and B). Rebalance generates one additional buy order for a third symbol C (e.g., because A is being sold and C bought, but sell gets rejected later, or because targets include C while keeping A,B >0). `orders` contains exactly one buy (`len(buys)=1`).  
  **Wrong behavior:** filter passes the buy since `len(buys) <= max_positions`. After execution, positions can become 3 symbols (A,B,C) violating `max_positions`. This is a direct risk-cap failure.

### Finding 4
- **File:** `src/tradebot/risk.py`
- **Function:** `RiskManager.filter_orders`
- **Claim (4):** **`max_order_notional` can be bypassed/invalidated for NaN notionals (or missing keys) because comparison behaves unexpectedly or throws, and caller doesn’t fail closed.**
- **Severity:** **MED**
- **Failure scenario:**  
  **Inputs:** an order dict contains `{"notional": float("nan"), ...}` (possible if upstream math divides by 0 or parses missing data), or lacks `"notional"`.  
  **Wrong behavior:**  
  - If `notional` is NaN: `nan > cap` is `False`, so the order is **approved** despite being nonsensical/unbounded.  
  - If `"notional"` missing: KeyError propagates; `run_once` doesn’t catch it; depending on runner, it may crash **after** some orders already submitted (partial execution), violating “errors fail closed” and leaving state inconsistent.

### Finding 5
- **File:** `src/tradebot/run.py`
- **Function:** `run_once`
- **Claim (5):** **Idempotency is based on UTC date, which can execute twice in a single US trading day (and/or skip a day) around timezone boundaries.**
- **Severity:** **HIGH**
- **Failure scenario:**  
  **Inputs:** bot runs at `00:30 UTC` and later at `20:00 UTC` on the same ET trading date (e.g., 20:00 UTC is 16:00 ET during DST). `today = datetime.now(timezone.utc).date()` differs across runs even though it’s the same market session in ET depending on schedule/ops.  
  **Wrong behavior:** `ledger.last_run_date()` also keys off UTC `ts` dates, so the second run is not recognized as “already ran today” in market terms. The strategy can place a second full rebalance inside the same trading day (duplicate turnover, risk cap interactions, extra costs).

### Finding 6
- **File:** `src/tradebot/fastarm.py`
- **Function:** `_fill` (live/broker mode), `_stand_down`, and all forced liquidations
- **Claim (6):** **Kill-switch liquidation can silently fail for shorts and leave risk open, because broker-side close is always `close_position` via `broker.close(sym)` which hardcodes `"side": "sell"` and doesn’t handle buy-to-cover explicitly.**
- **Severity:** **HIGH**
- **Failure scenario:**  
  **Inputs:** account is short `SYM` (possible if broker account allows shorting, or a previous bug created it). `_stand_down` and drawdown/eod/daily stops always call `_fill(..., "sell", sym, ...)` and in live mode `_fill` routes sells to `broker.close(sym)`, which returns `{"side":"sell"}` regardless of actual position direction.  
  **Wrong behavior:** if Alpaca rejects close due to side mismatch or other conditions, `_fill` may log rejection and return False; `_stand_down` will retry next tick, but the implementation never attempts an explicit buy-to-cover path. Net effect: kill switch does not reliably flatten “shorts included” as claimed.

- **Function:** `run_fast_once` (new day handling)
- **Claim (7):** **New-day detection uses local `today` but state `st["day"]` is set before ensuring liquidation succeeded; failed overnight flatten can be masked and stops/logic reset anyway.**
- **Severity:** **MED**
- **Failure scenario:**  
  **Inputs:** it’s the first tick of a new day, positions exist, broker refuses close (e.g., trading blocked, symbol halt). The loop calls `_fill(... "overnight_flatten" ...)` but ignores its return value. Then `st.update({"day": today, "trades_today": 0, "stopped_today": False})` executes regardless.  
  **Wrong behavior:** arm proceeds as if overnight invariant restored, resets daily counters, and can enter new positions while still holding old ones (risk cap failure: more than `top_k` effective positions and unintended overnight carry).
