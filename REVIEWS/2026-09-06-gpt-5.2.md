### src/tradebot/risk.py — `RiskManager.filter_orders`

1) **Claim:** `max_positions` cap can be bypassed with existing positions (checks only *buy orders*, not *post-trade holdings*).  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `risk.max_positions = 2`  
- Current broker positions: `{"SPY": 25.0, "QQQ": 25.0}` (already 2 names)  
- Strategy target introduces rotation but not via “buys only”: e.g. targets `{"SPY": 25.0, "QQQ": 15.0, "IWM": 10.0}`  
- `diff_orders` yields orders: `sell QQQ $10`, `buy IWM $10` (only **1** buy)  
- `filter_orders` sees `len(buys)=1` so approves it, resulting in **3 simultaneous symbols** (SPY, QQQ still >0, plus IWM) until the sell fills (and if partial fill / rejection on sell, it can persist).  
**Why it’s concrete:** the code never computes “distinct symbols with target_notional>0 after applying all approved orders”; it only counts buy orders.

2) **Claim:** `max_positions` can be violated permanently on partial fills/rejections because enforcement happens pre-submit and assumes sells succeed.  
**Severity:** HIGH  
**Failure scenario:**  
- Same as above, but broker rejects/partially fills the `sell QQQ` (e.g., trading halted, short sale restricted, etc.).  
- The buy is still submitted/filled, leaving 3 names held, violating `max_positions` with no later correction in this run.  
**Why it’s concrete:** `filter_orders` does not link a buy’s approval to sell success; `run_once` submits all approved orders regardless of sell outcomes.

### src/tradebot/run.py — `run_once`

3) **Claim:** Kill-switch flatten orders can exceed `risk.max_order_notional` and are submitted without any risk filtering.  
**Severity:** HIGH  
**Failure scenario:**  
- `risk.max_order_notional = 30.0`  
- Existing position market value: `{"SPY": 80.0}` (or any > 30)  
- `risk.check_drawdown(equity)` trips (equity down >= 10%).  
- Code builds `flatten` with `notional = abs(mv)` => 80.0 and submits directly: `broker.submit({"notional": 80.0, ...})`  
- This violates the stated hard cap “no single order above $30” exactly at the most safety-critical moment; broker may reject the close, leaving exposure after kill.  
**Why it’s concrete:** flatten path bypasses `risk.filter_orders()` entirely.

4) **Claim:** Kill-switch can be bypassed by an external `.halt` created mid-run; `run_once` checks `risk.halted()` only at the top and never re-checks before submitting orders.  
**Severity:** MED  
**Failure scenario:**  
- `run_once` starts, `.halt` absent.  
- After decision is logged but before `broker.submit`, an operator creates `.halt`.  
- Bot proceeds to submit approved orders anyway.  
**Why it’s concrete:** only one `risk.halted()` check exists, before data fetch/decision/risk filter/submit.

5) **Claim:** “Idempotent per day” guard can silently fail across ET day boundaries because `today` is UTC date, while strategy inputs/market_open are exchange-based. This can allow **two runs in one ET trading day** or **skip a day** depending on schedule.  
**Severity:** MED  
**Failure scenario:**  
- Runner scheduled at 00:30 UTC (20:30 ET prior day) and again at 14:00 UTC (10:00 ET).  
- First run: `today=YYYY-MM-(DD+1)` (UTC already next day) but market is closed -> logs `market_closed`.  
- Second run same UTC date -> `ledger.last_run_date()==today` could now block the real trading-day run if the first run wrote a `run` record (or if force misuse), or conversely allow double-execution across UTC midnight for the same ET session if the bot runs late.  
**Why it’s concrete:** run’s day key is `datetime.now(timezone.utc).date()` while the trading session is ET/exchange calendar.

### src/tradebot/fastarm.py — `run_fast_once` / `_fill` / `_positions`

6) **Claim:** In broker mode, exit/flatten logic uses `pos["qty"]` but always submits `broker.close(sym)` (ignores qty). For shorts, close requires a **buy**, but broker `close_position` handles it; however the ledger records `side="sell"` unconditionally in `Broker.close()`, corrupting state/audit trails and can break downstream risk/evaluation that assumes “sell means reduce long”.  
**Severity:** MED  
**Failure scenario:**  
- Account holds a short position (possible if allowed).  
- Fast arm triggers stop/flatten; calls `_fill(..., side="sell", ...)` which calls `broker.close(sym)` and ledger writes `fast_order side="sell"`, and broker.close returns `{"side":"sell"}` even though economic action is **buy-to-cover**.  
- Any later logic keyed on side (cost attribution, win-rate, exposure) will be wrong; could also hide that kill-switch did not actually remove risk if close rejected but recorded as sell attempt.  
**Why it’s concrete:** `Broker.close()` hardcodes `"side": "sell"`; fastarm always passes `"sell"` for liquidation.

7) **Claim:** Order notional/risk caps from `config.yaml` are not enforced for fast/movers at all (no `max_order_notional`, no `book_cap` equivalent, no `max_positions` hard check beyond `top_k`, and liquidation orders can be any size).  
**Severity:** HIGH  
**Failure scenario:**  
- `fast.top_k=2`, equity grows (or broker reports higher due to deposits), budget_per_slot = equity/2; nothing prevents a single entry from being far above the global `risk.max_order_notional=30`.  
- With equity = $500 (e.g., accidental paper reset upward), it will place ~$250 notional orders, violating the pre-registered global risk cap.  
**Why it’s concrete:** fastarm never instantiates/uses `RiskManager` and has no local `max_order_notional` in its config section.

8) **Claim:** In broker mode, `st["cost_accrued"]` is applied even if the broker order only partially fills or doesn’t fill at all (but returns a non-reject/non-cancel status). This can create phantom losses that trigger the arm’s drawdown kill incorrectly, or conversely mask true drawdown if close orders reject but cost is still accrued elsewhere.  
**Severity:** MED  
**Failure scenario:**  
- Submit buy notional $25; broker returns status `"accepted"` with `filled_qty=0`.  
- Code accrues modeled cost immediately: `st["cost_accrued"] += cost` even though no execution occurred.  
- `_mark_equity` subtracts `cost_accrued` from broker.equity, reducing equity and potentially tripping `max_drawdown_pct` / `daily_loss_stop_pct` without any real trading loss.  
**Why it’s concrete:** cost accrual is unconditional after any non-reject/non-cancel status; it does not check filled quantity.

### src/tradebot/signals.py — `momentum_12_1`

9) **Claim:** Look-ahead bug: momentum ignores `skip` sufficiency (`len(closes) < lookback + skip + 1`), so it can compute “12-1” using data that doesn’t actually exclude the most recent month when history is short.  
**Severity:** MED  
**Failure scenario:**  
- `lookback=252`, `skip=21`, but `len(closes)=253` (just enough for lookback+1, not enough to skip 21).  
- `end = closes.iloc[-(skip+1)]` is still valid (it will index within the available 253), but `start = closes.iloc[-(lookback+1)]` is also valid.  
- The computed return is effectively over a **shorter-than-intended** span and uses a recent point as `end` even though “skip month” promise can’t be met with the available data. Strategy may trade when it should have marked `enough_data=False`.  
**Why it’s concrete:** function only checks `len(closes) < lookback + 1`; it never checks `skip`.
