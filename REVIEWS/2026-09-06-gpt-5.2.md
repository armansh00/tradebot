### src/tradebot/risk.py — `RiskManager.filter_orders`
1) **Claim (HIGH): `max_positions` cap can be bypassed via “replace” buys that include sells.**  
**Severity:** HIGH  
**Failure scenario:**  
- **Inputs:** `cfg.risk.max_positions = 2`. Current positions: `{"SPY": 30, "QQQ": 30}` (2 positions). Strategy wants to rotate into `{"IWM": 30, "EFA": 30}` (still 2 positions).  
- `strategy.diff_orders` produces **four** orders: sell SPY, sell QQQ, buy IWM(to_notional=30), buy EFA(to_notional=30).  
- `filter_orders` computes `buys = [o for o in approved if o["side"]=="buy" and o["to_notional"]>0]` and rejects buys only if `len(buys) > max_positions`. Here `len(buys)==2`, so **both buys approved**, even though at decision time the account already has 2 positions and sells may fail/reject/partial-fill.  
- **Wrong behavior:** if either sell is rejected (or fills later), the bot can temporarily hold **4 positions**, violating `max_positions`, because the cap is enforced only on count of buy orders, not on resulting post-trade positions under execution risk.

2) **Claim (MED): Order notional cap can be violated when orders include `qty` notional drift at submit-time.**  
**Severity:** MED  
**Failure scenario:**  
- **Inputs:** An order dict passes `filter_orders` with `notional=29.99` (<= 30 cap) but broker-side execution uses `qty` (or price changes between decision and submit) causing actual notional > 30.  
- In slow arm path, `broker.submit` chooses `qty` vs `notional` based on `order.get("qty")`; `filter_orders` only checks `o["notional"]` and never checks a `qty`-based order.  
- **Wrong behavior:** if any caller ever supplies `qty` (even accidentally), the order bypasses `max_order_notional` enforcement entirely.

### src/tradebot/run.py — `run_once`
3) **Claim (HIGH): Kill switch can be bypassed by using `force=True`.**  
**Severity:** HIGH  
**Failure scenario:**  
- **Inputs:** `.halt` file exists (manual emergency stop) or drawdown halt has been triggered previously; operator calls `run_once(cfg, broker, force=True)`.  
- `run_once` checks `risk.halted()` **before** the `force` logic, so `.halt` is respected; however drawdown halt is **only represented by `.halt`**. If the process crashed after `risk.halt()` wrote state but before `.halt` was written (or if `.halt` is deleted manually), `force=True` allows trading even though prior state indicates a kill event happened (there is no state-based “halted” check in `run_once`; it only checks the file).  
- **Wrong behavior:** a previously-triggered drawdown kill can be cleared by deleting `.halt`, and then `force=True` permits same-day re-run despite the kill having fired (no “halt persists” invariant except the file).

4) **Claim (MED): Drawdown flatten can exceed `max_order_notional` and bypass order-level caps.**  
**Severity:** MED  
**Failure scenario:**  
- **Inputs:** `cfg.risk.max_order_notional=30`. Existing position market value `{"SPY": 80}` due to gap-up or because earlier orders were larger (e.g., configured differently in the past, or manual intervention). Equity drops triggering `risk.check_drawdown`.  
- In kill path, `flatten` orders are built with `notional = abs(mv)` and submitted directly via `broker.submit(o)` **without** `risk.filter_orders`.  
- **Wrong behavior:** emergency liquidation submits an $80 order despite a $30 cap. That violates the hard risk invariant “no single order above $30”.

### src/tradebot/fastarm.py — `run_fast_once` / `_fill` / `_positions`
5) **Claim (HIGH): In broker mode, exits can submit the wrong side and/or size because `_fill` always uses `broker.close(sym)` for sells and ignores `qty`.**  
**Severity:** HIGH  
**Failure scenario:**  
- **Inputs:** Broker account holds a **short** position (possible via prior bug/manual action; slow arm explicitly mentions shorts). `positions_detail()` returns `qty=-1`.  
- `_stand_down` and all flatten logic call `_fill(..., side="sell", qty=pos["qty"])`. In broker mode, `_fill` ignores `qty` and does `broker.close(sym)` unconditionally for sell.  
- Alpaca’s `close_position` closes the position, but the returned dict in `broker.close` hardcodes `"side": "sell"`. Ledger and logic assume sells, not “buy-to-cover”.  
- **Wrong behavior:** accounting/logging becomes inconsistent (records “sell” even when covering a short). More importantly: upstream calls pass negative qty for a short into `_fill` cost calculation `cost = abs(qty*px*bps)` (fine) but the “side” semantics are wrong. This can mask a path where shorts remain (or are reopened) because the system never asserts “no shorts” for intraday arms, yet logs imply it flattened.

6) **Claim (HIGH): Max positions / order notional caps are not enforced at all for fast/movers arms in broker mode.**  
**Severity:** HIGH  
**Failure scenario:**  
- **Inputs:** `fast.top_k=2` is intended as a position cap; `risk.max_order_notional=30` exists globally.  
- `run_fast_once` computes `budget_per_slot = equity / top_k` and then `notional = min(budget_per_slot, cash)`. If cash is $50 and `top_k=2`, notional is $25 (fine), but **there is no enforcement** against config `risk.max_order_notional` or any global kill conditions beyond the arm’s own `max_drawdown_pct` and `daily_loss_stop_pct`.  
- If `top_k` is changed, or equity grows, or a bug sets `top_k=1`, the arm can submit >$30 notionals with no check.  
- **Wrong behavior:** stated global risk caps (`risk:` section) do not apply to intraday arms; a configuration that expects a universal order notional limit is silently violated.

7) **Claim (MED): Daily loss stop does not “stand down”; it only blocks entries, but still allows repeated exit churn and costs after stop triggers.**  
**Severity:** MED  
**Failure scenario:**  
- **Inputs:** Day P&L breaches -3%, `st["stopped_today"]=True`.  
- Code prevents entries via `elif not st["stopped_today"] and now >= or_end:` but still evaluates end-of-day flatten branch (fine) and still evaluates OR-low stops earlier in same tick before stopped_today is set (order matters within tick). If equity calculation lags and the stop flips mid-loop, you can still place new exits and incur modeled costs multiple times if broker rejects/partials and position persists.  
- **Wrong behavior:** after daily stop, the system can continue to generate trade-cost accrual and repeated close attempts without a stricter “halt until tomorrow” invariant (it’s softer than advertised “flatten, done for the day”).

### src/tradebot/signals.py — `momentum_12_1`
8) **Claim (MED): Look-ahead / window definition bug: `momentum_12_1` ignores `skip` in the length check, causing incorrect “enough_data” and miscomputed momentum at boundary.**  
**Severity:** MED  
**Failure scenario:**  
- **Inputs:** `lookback=252`, `skip=21`. Provide `closes` length = 253 (just enough for lookback+1, but **not** enough to also skip 21 days).  
- `momentum_12_1` checks only `len(closes) < lookback + 1`, so it proceeds. Then `end = closes.iloc[-(skip + 1)]` requires at least `skip+1` elements (true) but conceptually you need `lookback+skip+1` trading days to compute 12-1 momentum properly from the intended window. With only 253 points, `start = closes.iloc[-(lookback + 1)]` is the first element, while `end` is near the end; you effectively compute ~252-day momentum **without skipping a full month**, because the start is too recent relative to the intended definition when the series is short.  
- **Wrong behavior:** strategy may treat a symbol as `enough_data=True` and trade it even though the declared 12-1 definition can’t be satisfied with the available history; boundary symbols can get systematically wrong momentum.

**Severity:** LOW  
**Failure scenario:**
