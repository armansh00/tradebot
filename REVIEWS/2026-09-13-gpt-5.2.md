### Findings

**src/tradebot/risk.py — `RiskManager.filter_orders`**
1) **(HIGH) max_positions cap can be bypassed by rebalance-to-existing positions.**  
   **Why:** it counts only `buys = [o for o in approved if o["side"] == "buy" and o["to_notional"] > 0]` and enforces `len(buys) > max_positions`. This does *not* cap the resulting number of nonzero target positions; it caps only the number of buy orders.  
   **Failure scenario:**  
   - Inputs: `cfg.risk.max_positions=2`. Current `positions={"SPY": 10.0, "QQQ": 10.0}` (2 positions already). Targets want to add a 3rd by reallocating: `targets={"SPY": 0.0, "QQQ": 10.0, "IWM": 10.0}`.  
   - `diff_orders` emits sell SPY, buy IWM. `buys` has length 1 so it passes.  
   - Now consider *partial* sell due to min_order_notional dust: `targets={"SPY": 9.0, "QQQ": 10.0, "IWM": 10.0}` produces buy IWM without fully exiting SPY; after execution you hold 3 positions (SPY, QQQ, IWM) while `max_positions=2`. No risk rejection fires.

**src/tradebot/risk.py — `RiskManager.filter_orders`**
2) **(MED) max_positions enforcement ignores sells-first coupling; can approve buys that exceed cap if paired sells get rejected upstream.**  
   **Why:** `filter_orders` evaluates each order in isolation, then caps buy-count. It doesn’t ensure that approved sells actually succeed before the buys (and it can’t, but then the “max_positions” check is not a hard brake).  
   **Failure scenario:**  
   - Inputs: current positions already at cap (2). Strategy emits 1 sell and 1 buy to rotate.  
   - Broker rejects the sell (e.g., position not found due to stale positions dict, or close-only restriction, or short-sale constraints), but buy is still submitted because risk approved it.  
   - Result: positions become 3 (cap violated) or leverage increases. This is a concrete path because `run_once` submits all approved orders without conditioning buys on sell fills.

**src/tradebot/run.py — `run_once`**
3) **(HIGH) Kill switch can be bypassed by running with `force=True`.**  
   **Why:** `force` bypasses both the “already ran today” guard and the `broker.market_open()` guard. More importantly, the function checks `risk.halted()` *before* the `force` logic, but it does **not** prevent trading when halted if a user clears the halt file (or state) and reruns with `force=True` outside market hours; the broker may still accept orders depending on asset/venue rules (or if `market_open()` is inaccurate for the traded product). This undermines the stated “Hard brakes. Checked before every order, every run.”  
   **Failure scenario:**  
   - Inputs: It’s a weekend/holiday; `force=True`; broker’s `market_open()` would be False but bypassed.  
   - `strategy.diff_orders` generates orders; `broker.submit` is called.  
   - Wrong behavior: trades can be sent when market is closed, violating intended guardrails (and if broker queues DAY orders, you’ve effectively entered risk after the time gate should have blocked).

**src/tradebot/fastarm.py — `_fill` (live/broker mode)**
5) **(MED) Idempotency is only implemented for buys, not for sells/flatten/kill-switch exits.**  
   **Why:** buys use `client_order_id=iid`; sells use `broker.close(sym)` with no idempotency key. If the process restarts mid-exit or retries a tick, it can send repeated close requests; depending on broker semantics this can error or create unintended orders (some venues translate close into market order for full qty at that moment; repeated calls after partial fills can cascade).  
   **Failure scenario:**  
   - Inputs: drawdown kill triggers with 2 positions; network drop after first `close_position` reaches broker but before response/ledger write; process restarts, kill branch runs again.  
   - Wrong behavior: second close call is sent again; could be rejected (and then `_stand_down`/kill logic may think still held and keep spamming), or in edge cases if position flipped/partial it can overshoot into a short (venue-dependent). Either way, exit path is not safely idempotent.

**src/tradebot/fastarm.py — `run_fast_once`**
6) **(HIGH) Drawdown kill can permanently fail to trigger due to equity math using `broker.equity() - cost_accrued` while `cost_accrued` never resets.**  
   **Why:** In live mode, modeled costs are accrued forever (`st["cost_accrued"] += cost`) but never reset by day or by withdrawal, and `high_water_mark` is computed on this net equity. If the account is reset/top-upped (common in paper), HWM can jump, and subsequent “net equity” (gross equity - historical costs) can show artificial drawdowns or prevent real ones from triggering correctly (because the net baseline includes costs from prior regimes). This is a kill-switch integrity problem: it is neither pure mark-to-market nor pure account equity.  
   **Failure scenario:**  
   - Inputs: Start $50; over many days accrue $20 modeled costs; gross equity remains $50 (paper fills perfect), net equity used for kill = $30. `high_water_mark` maybe hit at $45 net earlier.  
   - A real trading loss happens that reduces gross equity to $40; net = $20. Drawdown vs HWM now looks enormous and triggers kill earlier than intended, or conversely if you top-up gross equity back to $50, net remains depressed and HWM logic becomes incoherent. The halt can fire or not fire for reasons unrelated to actual account drawdown.

**src/tradebot/signals.py — `momentum_12_1`**
7) **(LOW) Look-ahead / window definition mismatch: skip period not enforced for “enough data” check.**  
   **Why:** `momentum_12_1` checks `len(closes) < lookback + 1` but then accesses `closes.iloc[-(skip + 1)]`; if `skip` is large relative to available history, it can still index into the series (Python allows negative indexing) but produce a value inconsistent with the intended 12-1 definition (you need `lookback + skip + 1` observations). `run_once` tries to fetch extra days, but this is still a concrete math defect in isolation.  
   **Failure scenario:**  
   - Inputs: `lookback=252`, `skip=21`, `len(closes)=253`.  
   - Check passes (`253 < 253` false). `end = closes.iloc[-22]` is valid, but `start = closes.iloc[-253]` is also valid; you effectively compute ~1-month momentum, not 12-1. Strategy may trade on an unintended shorter lookback without any “insufficient history” flag.

**src/tradebot/ledger.py — `Ledger.read`**
8) **(MED) State/ledger corruption risk: a single truncated JSONL line crashes all reads (no try/except), breaking idempotency and kill-switch observability.**  
   **Why:** `read()` does `json.loads(line)` for every non-empty line with no error handling. A crash mid-write elsewhere (or manual edit, disk issue) leaves a partial line; subsequent runs that call `ledger.last_run_date()` will raise and may skip risk controls or reporting entirely depending on caller handling (here, `run_once` would crash before `risk.check_drawdown`).  
   **Failure scenario:**  
   - Inputs: process killed while writing ledger line (despite fsync, partial writes can exist if killed between write() calls or due to filesystem issues).  
   - Next invocation: `ledger.last_run_date()` triggers `read()`, which throws `JSONDecodeError`.  
   - Wrong behavior: bot crashes before checking `.halt` or drawdown and before flattening logic; depending on scheduler, it may stop managing positions.

Overall risk assessment: **HIGH—multiple concrete paths allow risk caps/position limits and kill-switch invariants to be violated, especially in the intraday arms.**
