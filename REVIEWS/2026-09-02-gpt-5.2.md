### 1) Halt file is not honored by intraday arms (kill-switch bypass)
- **File:** `src/tradebot/fastarm.py`
- **Function:** `run_fast_once`
- **Claim #1 (HIGH):** The intraday arms ignore `risk.halt_file` (`.halt`) entirely; they only consult `st["halted"]`.
- **Failure scenario:**  
  - **Inputs/state:** `.halt` file exists (e.g., slow arm tripped drawdown and called `RiskManager.halt()`, or human creates `.halt` as emergency stop). `fastarm` state has `st["halted"] == False`.  
  - **Wrong behavior:** `run_fast_once()` proceeds to trade normally (submits buys/sells) despite the global halt switch being active. This is a direct bypass of the configured kill switch.

### 2) “Max positions” cap can be bypassed when rebalancing (risk cap failure)
- **File:** `src/tradebot/risk.py`
- **Function:** `filter_orders`
- **Claim #2 (HIGH):** `max_positions` enforcement only counts **buy orders with `to_notional > 0`**, so you can end the run holding more than `max_positions` if extra positions already exist and the rebalance submits only sells (or buys that don’t increase count).
- **Failure scenario:**  
  - **Inputs/state:** `cfg.risk.max_positions = 2`. Broker currently has 3 open positions: `{"SPY": 10, "QQQ": 10, "IWM": 10}` (e.g., manual intervention, prior bug, broker-side corporate action, or another process). Strategy targets only 2 symbols, so `diff_orders()` produces **only sells** (reduce/remove the 3rd), or even no buys if already allocated.  
  - **Wrong behavior:** `filter_orders()` sees `buys = []`, so it never rejects anything for `max_positions`, and there is **no explicit check that current positions already exceed the cap** or that the post-trade set will be ≤ 2. If the sell for the 3rd position is rejected/bounced by broker, the bot can continue day after day with 3 positions without ever tripping the cap logic (because the cap logic is only applied to *new buys*).

### 3) Drawdown kill in `run.py` can submit orders above `max_order_notional` (risk cap failure after kill switch)
- **File:** `src/tradebot/run.py`
- **Function:** `run_once`
- **Claim #3 (HIGH):** When drawdown triggers, the code builds `flatten` orders with `notional = abs(mv)` (market value) and submits them **without passing through** `risk.filter_orders()`. This can violate `cfg.risk.max_order_notional`.
- **Failure scenario:**  
  - **Inputs/state:** `cfg.risk.max_order_notional = 30`. Positions include `{"SPY": 50}` market value (possible if price moves up after entry, or if broker reports market_value > cap, or if book_cap logic differs from broker’s actual holdings). Drawdown breach occurs.  
  - **Wrong behavior:** `flatten` contains `{notional: 50}` which exceeds the $30 cap; the bot submits it anyway. If broker accepts it, the bot breaks the risk cap. If broker rejects it (common), the bot believes it “killed” but **may remain exposed** because it doesn’t re-check position status after failures nor does it chunk liquidation into cap-sized orders.

### 4) Kill-switch flatten uses `submit()` “sell notional” even for shorts; can increase exposure (money-math / side logic error)
- **File:** `src/tradebot/run.py`
- **Function:** `run_once` (drawdown flatten block)
- **Claim #4 (HIGH):** For shorts, flatten logic sets `side="buy"` (correct) but still uses `notional=abs(mv)` where `mv` is `market_value`. For short positions, many brokers report `market_value` as **negative** (you assume that), but notional-to-cover should be based on **price * shares** (absolute exposure). Using `market_value` as notional can be wrong sign/magnitude depending on broker conventions.
- **Failure scenario:**  
  - **Inputs/state:** Broker’s `positions()` returns values where `market_value` for shorts is **positive** (some APIs return absolute market value with separate side/qty). Example: short 1 share at $100, API returns `"XYZ": 100.0` (positive).  
  - **Wrong behavior:** Code interprets `mv > 0` and sets `side="sell"` (thinking it’s long) and submits a sell order, which **increases** the short instead of covering it, during a kill switch event.

### 6) Intraday “market hours” logic ignores half-days; can trade after early close (stale-time/session bug)
- **File:** `src/tradebot/fastarm.py`
- **Function:** `run_fast_once`
- **Claim #6 (MED):** Uses hardcoded `OPEN_T=9:30` and `CLOSE_T=16:00` and checks `now >= close_dt` / `flat_dt` based on that, but broker has `session_today()` explicitly to handle half-days. Fast arm doesn’t use it.
- **Failure scenario:**  
  - **Inputs/state:** Half-day where market closes 13:00 ET. Scheduler calls `run_fast_once()` at 14:00 ET.  
  - **Wrong behavior:** `now < close_dt` (16:00) so it believes market open and may submit orders into a closed session (or fail to flatten by true close). That breaks the invariant “flat before close” and can carry positions overnight unintentionally.

### 7) Opening-range window can include bars that were not available at decision time (look-ahead/stale data)
- **File:** `src/tradebot/fastarm.py`
- **Function:** `opening_range`, `run_fast_once` (use of `broker.intraday_5min(universe)` without `end=now`)
- **Claim #7 (MED):** `intraday_5min()` fetches bars from 9:30 to 16:00 for the whole day; if the data provider returns *future bars* (relative to `now`) during the session (common in backfill/pagination quirks or when `now` is simulated/replay), then OR levels and signals can include information from after `now`.
- **Failure scenario:**  
  - **Inputs/state:** At 10:05 ET, `broker.intraday_5min()` returns bars up to 10:30 due to provider latency/backfill behavior (or because replay passes a `day` but not a cut-off). `or_end=10:00` and opening range computed from `bars["t"] < or_end` is fine, **but** entry/exit logic uses `lasts = df["c"].iloc[-1]` which would then be a close from 10:30 (future to 10:05).  
  - **Wrong behavior:** Trades based on a price (`lasts[sym]`) that wasn’t available at decision time, creating look-ahead bias and potentially triggering false entries/exits.
