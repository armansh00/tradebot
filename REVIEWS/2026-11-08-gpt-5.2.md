### src/tradebot/risk.py — `RiskManager.filter_orders`

1) **[HIGH] max_positions cap can be bypassed by submitting “buy” orders that *reduce* positions (negative `to_notional`)**
- **Claim:** The position-count check only counts buys where `o["side"]=="buy"` **and** `o["to_notional"] > 0`. Any “buy” that results in `to_notional <= 0` is excluded from the cap, even though it is still an order and can change exposure (especially for shorts).
- **Why concrete:** The code:
  ```py
  buys = [o for o in approved if o["side"] == "buy" and o["to_notional"] > 0]
  if len(buys) > self.cfg.risk.max_positions: ...
  ```
- **Failure scenario:** (inputs → wrong behavior)
  - Config: `max_positions=2`
  - Current positions: `{"SPY": +25, "QQQ": +25}` (2 longs)
  - Strategy/bug elsewhere emits additional orders like:
    - `{"symbol":"AAPL","side":"buy","notional":10,"from_notional":-5,"to_notional":0}` (a “buy” that closes a short / reduces a short)
    - plus two normal buys to open new longs:
      - `{"symbol":"IWM","side":"buy","notional":25,"from_notional":0,"to_notional":25}`
      - `{"symbol":"EFA","side":"buy","notional":25,"from_notional":0,"to_notional":25}`
  - Result: The AAPL “buy” is **not counted** toward `buys`, so only 2 buys are counted and approved, even though total number of symbols touched/positions can exceed the intended cap logic (and depending on broker netting, can transiently exceed constraints you meant to enforce). This is a risk-cap logic hole: the cap is not applied consistently to all buy-side intents.

### src/tradebot/risk.py — `RiskManager.book_equity`

2) **[HIGH] Drawdown kill switch can be defeated by baseline re-anchoring after a cash withdrawal/account drain**
- **Claim:** The “account reset” heuristic re-anchors the baseline when `raw < baseline*0.5 and raw <= cap*2`. This can erase real drawdowns if equity is reduced by *withdrawal/manual adjustment* (or any non-trading reduction), because book equity is computed from the new baseline rather than reflecting loss from prior HWM.
- **Why concrete:** On re-anchor:
  ```py
  baseline = raw
  ...
  return min(cap + (raw - baseline), raw)  # becomes min(cap, raw) ~= raw when raw < cap
  ```
  and drawdown check uses this book equity number, not raw.
- **Failure scenario:**
  - `cap=50`
  - Baseline initially recorded at `raw=100000` (slow arm on the $100k account; config comments say that’s the situation).
  - Bot trades poorly: raw equity drops to `90000` (a real 10% drawdown from 100k HWM) — kill switch should halt at 10%.
  - Before `run_once` executes (or between runs), someone manually “resets”/withdraws funds such that raw becomes `80` (still `<= cap*2 == 100` and also `< baseline*0.5`).
  - On next run, `book_equity(raw=80)` re-anchors baseline to 80 and returns ~80. Now `check_drawdown(equity=80)` compares equity to a high-water mark that may also get updated downward behaviorally over time (see next finding), and—critically—the book equity no longer encodes the prior massive loss from 100k. The drawdown path is effectively “laundered” by the reset heuristic.
  - Net: the system can continue trading even though the strategy experienced/realized a catastrophic drawdown relative to the earlier evaluation period, because the book cap logic explicitly allows rebaselining on “reset-like” equity levels.

### src/tradebot/risk.py — `RiskManager.check_drawdown`

3) **[HIGH] High-water mark is updated and persisted *before* verifying halt; a crash between `_save_state` and `halt()` can permanently raise HWM without halting**
- **Claim:** The function writes the updated `high_water_mark` to disk, then computes `dd_pct`, then halts. If the process dies after `_save_state` but before `halt()` writes `.halt`, you can end up with an HWM that is too high and no halt file—changing future dd calculations and potentially preventing halts (or causing spurious halts later).
- **Why concrete:** Order is:
  1) compute `hwm = max(old_hwm, equity)`
  2) `state["high_water_mark"]=hwm`
  3) `_save_state(state)`
  4) compute dd and maybe call `halt()`
- **Failure scenario:**
  - Old state: `high_water_mark=50`
  - Equity spikes intra-day due to mark: `equity=60` → state saved with HWM=60.
  - Immediately after saving, process crashes (OOM, container kill, etc.) *before* `.halt` is written on a later drawdown breach.
  - Next run: equity is back to 50; dd is now computed vs HWM=60, and behavior diverges from what actually happened operationally. More importantly, if the breach *should* have halted on the prior run (equity low), but crash occurred before writing `.halt`, the bot continues trading with inconsistent state. This is a concrete state-consistency bug around kill switch reliability.

### src/tradebot/run.py — `run_once`

4) **[HIGH] `force=True` bypasses *both* the “already ran today” idempotency guard and the “market_closed” guard, enabling trading when it should be disallowed**
- **Claim:** With `force=True`, the function will proceed even if:
  - it already ran today (duplicate trading day), and/or
  - the market is closed.
  This is a direct bypass of safety constraints in a single flag.
- **Why concrete:** Guards are explicitly `if not force and ...`.
- **Failure scenario:**
  - Operator runs with `force=True` during a weekend or holiday.
  - `broker.market_open()` would be false, but that check is skipped.
  - Bot fetches prices and submits orders anyway (`broker.submit`), potentially queuing orders for next session or being accepted depending on broker behavior.
  - This violates “Designed to run once per trading day; safe to re-run (idempotent per day)” and creates a pathway to unintended duplicate exposure.

### src/tradebot/fastarm.py — `run_fast_once` / `_fill`

5) **[HIGH] Intraday arms ignore `risk.max_order_notional` entirely; they can submit orders well above cap**
- **Claim:** The slow arm routes through `RiskManager.filter_orders`, but the fast/movers arms submit directly via `_fill` with `notional = qty*px` derived from `budget_per_slot` and cash, with no reference to `cfg.risk.max_order_notional`.
- **Why concrete:** In `run_fast_once` entries:
  ```py
  notional = min(budget_per_slot, cash)
  qty = notional / lasts[sym]
  _fill(... "buy", ..., px=lasts[sym], qty=qty ...)
  ```
  `_fill` in live mode does:
  ```py
  broker.submit({"notional": round(qty*px,2)})
  ```
  No cap check.
- **Failure scenario:**
  - Suppose equity grows (or account is mis-set) to `$500` in fast arm (paper accounts can be edited/reset; also profits could accumulate).
  - `top_k=2` ⇒ `budget_per_slot=250`
  - Cash is available, so `notional=250`
  - This submits a $250 notional order even though global risk config says `max_order_notional: 30.0`.
  - Result: order notional cap fails for fast/movers arms.

6) **[HIGH] `top_k` position limit can be violated in broker mode because `_positions()` may include symbols with `market_value` but missing/invalid `qty`, and entry logic uses `len(held)`**
- **Claim:** In broker mode, `_positions()` returns `broker.positions_detail()`. If broker returns positions including non-equity lines or a position with `qty` as string/0/None quirks, `len(held)` may be wrong relative to actual risk-bearing exposure, and entries proceed because `slots = top_k - len(held)` uses that length only.
- **Failure scenario:**
  - Broker returns a position list that includes a symbol with `market_value != 0` but `qty` missing/0 due to corporate action / fractional rounding behavior.
  - `_positions` includes it (dict entry exists), increasing or decreasing `len(held)` incorrectly.
  - Bot thinks it has a free slot and enters a new symbol, resulting in >`top_k` real concurrent positions. This is a concrete “count positions by dict keys from broker payload” fragility.

### src/tradebot/fastarm.py — `run_fast_once` (kill switch / drawdown)

7) **[MED] Drawdown kill uses net equity (broker equity minus accrued modeled cost), but liquidation uses broker.close without realizing modeled cost; can re-enable trading if state reset, masking true gross drawdown**
- **Claim:** The fast arm’s kill switch triggers off `_mark_equity` (net of `cost_accrued`). But on liquidation it does not reconcile/realize those costs anywhere except continuing to accrue them. If state is ever reset (deleted state file), `cost_accrued` resets to 0 and the drawdown history disappears while the broker account equity (gross) may look fine. This is a path to “book-cap rebaseline logic that erases real losses” analog, but for the modeled-cost layer.
- **Failure scenario:**
  - Many trades accrue `cost_accrued = $8` on a $50 book.
  - Net equity used for evaluation is depressed; dd kill may trigger and set `st["halted"]=True`.
  - Operator deletes state file to “unstick” the arm (common operational move).
  - Next run: `cost_accrued` resets to 0, `high_water_mark` resets to start_cash, and kill switch no longer reflects the modeled execution losses already “paid” in evaluation terms. The arm resumes trading with an artificially improved net equity and drawdown history.

### src/tradebot/signals.py — `momentum_12_1` / `snapshot`

8) **[MED] 12-1 momentum uses `closes.iloc[-(skip+1)]` but `snapshot` uses last close as “price”; this mixes decision-time price with momentum window that includes the same last close day**
- **Claim:** The strategy decision compares `price` (last element) to SMA, but momentum “end” is `-(skip+1)`. If `skip=21`, momentum excludes the most recent month, but the eligibility filter uses `price` from the most recent close (which is inside the skipped region). That means you are using post-skip information to gate eligibility, a form of subtle look-ahead relative to the momentum definition.
- **Failure scenario:**
  - A symbol has strong momentum through `t-21` but crashes in the last 5 days.
  - Momentum remains positive (since it ends at `t-21`), but `price` is now far below SMA and you exclude it based on that post-window crash—changing what “12-1 momentum with a skip month” would have selected at the decision boundary if you were consistently using the same end date for all features.
  - This is an internal temporal inconsistency: part of the signal uses newer data than the momentum feature’s stated window.
