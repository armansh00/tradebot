### src/tradebot/risk.py — RiskManager.filter_orders

1) **Max positions cap can be bypassed via pre-existing holdings**  
**Severity: HIGH**  
**Claim:** `filter_orders()` enforces `max_positions` by limiting the *count of buy orders*, not the post-trade number of open positions.  
**Failure scenario:**  
- Config: `risk.max_positions = 2`  
- Current broker positions already hold 2 symbols (e.g., `{"SPY": 25, "QQQ": 25}`)  
- New targets rotate into two different symbols, producing two buy orders (e.g., buy `IWM`, buy `TLT`) and sells for SPY/QQQ might be rejected by venue or missing for any reason (or `diff_orders` produces buys without corresponding sells if “current” is mis-stated).  
- `filter_orders()` sees `len(buys)=2` and approves both.  
- If sells don’t execute (or were not present), you end up with **4 positions**, violating `max_positions`.  
This is a concrete logic gap: it never computes `existing_positions + approved_buys - closed_positions`.

2) **Order notional cap can be bypassed with NaN**  
**Severity: HIGH**  
**Claim:** `if o["notional"] > max_order_notional:` fails closed only for normal numbers; `NaN` compares false, so it passes.  
**Failure scenario:**  
- `strategy.diff_orders()` or another caller produces `{"notional": float("nan"), ...}` (possible if upstream math gets NaN from broker data, or JSON de/serialization, or a bad target/current).  
- In Python, `float('nan') > 30.0` is `False`, so the order is **approved**, and passed to `broker.submit()`.  
- Broker-side could interpret notional oddly or reject; either way the bot’s risk layer **did not enforce the cap**.

### src/tradebot/run.py — run_once

3) **Idempotency failure: can trade twice in the same local trading day**  
**Severity: MED**  
**Claim:** “once per trading day” is enforced using `today = datetime.now(timezone.utc).date()`, while the trading day is ET.  
**Failure scenario:**  
- Run at `2026-10-12 23:30 ET` (still same trading date in ET). UTC is already `2026-10-13`. `today="2026-10-13"`.  
- Later the same ET trading day (still 10/12 ET session context if used differently elsewhere), a second run happens after midnight UTC; `ledger.last_run_date()` might be `"2026-10-13"` vs `"2026-10-12"` depending on prior run time.  
- This can allow a second execution on what an operator considers “the same trading day,” because the guard is keyed to **UTC date**, not exchange session date.

4) **Kill-switch can be bypassed by `force=True`**  
**Severity: MED**  
**Claim:** `force` bypasses both “already ran today” and “market_closed” checks, and there is no additional guard preventing order submission outside the intended schedule.  
**Failure scenario:**  
- Human/operator or a bug passes `force=True` while market is closed.  
- `broker.daily_closes()` can still return data; `strategy.diff_orders()` can generate orders; `broker.submit()` is called even though market is closed (depends on broker behavior; Alpaca will accept and queue DAY orders in many cases).  
- Result: bot can place orders when it explicitly claims “Designed to run once per trading day” and “market_closed” should skip.

### src/tradebot/fastarm.py — _fill / run_fast_once / _stand_down

5) **Live-mode exits are incorrectly treated as “sell orders”; close() always sells (breaks shorts + can bypass flatten)**  
**Severity: HIGH**  
**Claim:** In live mode, `_fill(..., side="sell", ...)` calls `broker.close(sym)` unconditionally. `AlpacaBroker.close()` always returns `{"side":"sell"}` and calls `close_position`, which will buy-to-cover for shorts, but your ledger/state logic assumes “sell”. More importantly: `_stand_down` and other flatten loops always pass `"sell"` regardless of long/short direction.  
**Failure scenario:**  
- Account is short (possible if broker account allows it, or if a prior bug created it). `positions_detail()` returns `qty=-1`.  
- `_stand_down()` calls `_fill(..., "sell", qty=-1)`; `_fill` calls `broker.close(sym)` (which is correct action), but it logs side `"sell"` and uses `qty` sign inconsistently.  
- State cleanup (`st["or_low"].pop`) happens in the `"sell"` branch, but if a short exists the semantics are “buy to cover”; your audit trail and any later logic keyed on side will be wrong.  
Concrete defect: flatten logic does not branch on sign of position qty in live mode, unlike slow-arm drawdown flatten which does.

6) **Daily-loss stop can be bypassed due to inconsistent “day_start_equity” reset logic**  
**Severity: MED**  
**Claim:** `day_start_equity` is set using a brittle trio of conditions:
```py
if st.get("day_start_equity") is None or st.get("day") != today or "day_equity_set" not in st:
    st["day_start_equity"] = _mark_equity(...)
    st["day_equity_set"] = today
if st["day_equity_set"] != today:
    st["day_start_equity"] = _mark_equity(...)
    st["day_equity_set"] = today
```
but you also set `st.update({"day": today,...})` earlier on `new_day`. This makes `st.get("day") != today` false immediately after rollover, so the first condition won’t fire unless `day_equity_set` is missing.  
**Failure scenario:**  
- State file contains `day_start_equity` and `day_equity_set` from a prior day due to a crash between `st.update({"day": today...})` and the equity-set block being executed/saved.  
- Next run: `new_day` is true, you set `st["day"]=today`, but `day_equity_set` still equals yesterday; first `if` does **not** run because `st.get("day") != today` is false and `day_equity_set` exists. Second `if` *does* run and sets it—so far OK.  
- The bypass happens when the crash happens *after* `day_equity_set` is written but before positions/costs are consistent (or in broker mode, when `_mark_equity` depends on broker snapshot timing). You can end up anchoring `day_start_equity` to an intra-day equity after losses, weakening the daily stop so it never triggers.

7) **Risk caps not enforced for intraday arms (no max_order_notional / max_positions)**  
**Severity: HIGH**  
**Claim:** `fastarm.py` never applies `risk.max_order_notional` or `risk.max_positions` from the shared config risk section; it uses `top_k` and per-slot `budget_per_slot = equity/top_k`, but nothing prevents notional per order exceeding the global cap (e.g., $30), and nothing cross-checks account positions beyond `top_k`.  
**Failure scenario:**  
- Config sets `risk.max_order_notional=30`. Fast arm equity rises to $200 over time (paper). `budget_per_slot = 200/2 = $100`.  
- On a breakout, it will submit a **$100 notional buy** (subject only to cash), violating the system-wide `max_order_notional` invariant you claim is “checked before every order”. It isn’t checked here.

### src/tradebot/signals.py — momentum_12_1

8) **Look-ahead / incorrect skip handling: skip period not validated against available data**  
**Severity: LOW**  
**Claim:** `momentum_12_1` checks only `len(closes) < lookback + 1`, ignoring `skip`. With small histories, indexing with `-(skip+1)` can still work but not represent the intended “skip last month” window.  
**Failure scenario:**  
- `lookback=252`, `skip=21`, but data returned is length 253 (passes check).  
- `end = closes.iloc[-22]` exists; `start = closes.iloc[-253]` exists. But this uses almost the entire series with barely any buffer; if the broker returns partial/unadjusted days or missing sessions, you’re not actually skipping a month of *trading days* reliably. (Not catastrophic, but it violates the stated rule under data gaps.)
