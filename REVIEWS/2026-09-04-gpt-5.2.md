**src/tradebot/risk.py — `RiskManager.book_equity`**
1) **Claim (HIGH): book-cap “reset” rebaselines after real trading losses, erasing drawdown and bypassing the kill switch.**  
   **Failure scenario:**  
   - Config: `risk.book_cap=50`, `risk.max_drawdown_pct=10`.  
   - State: `book_baseline=100000` (slow arm on legacy $100k paper acct).  
   - A real loss happens elsewhere in the account (or an earlier period), so `broker.equity()` drops to `raw=60`.  
   - Code path: `raw < baseline*0.5` (60 < 50000) and `raw <= cap*2` (60 <= 100) ⇒ baseline is reset to 60.  
   - Next line returns `book_equity = min(cap + (raw-baseline), raw) = min(50 + 0, 60) = 50`.  
   - **Wrong behavior:** equity fed into `check_drawdown()` becomes 50 instead of reflecting a ~99.94% loss from 100k→60; drawdown halt never triggers. This is explicitly a “drawdown path that never triggers halt” and the condition does not distinguish “dashboard reset” from “catastrophic loss that happens to land near the cap band.”

**src/tradebot/risk.py — `RiskManager.filter_orders`**
2) **Claim (HIGH): `max_positions` enforcement is based on count of buy orders, not resulting positions; can exceed cap without any rejection.**  
   **Failure scenario:**  
   - `risk.max_positions=2`.  
   - Current positions already hold 2 symbols (at target or not), and strategy generates a rebalance that *adds* a third symbol by selling one and buying two, but net buy orders count is 2 (or 1).  
   - Example orders after `diff_orders`:  
     - Sell A (side="sell") to 0  
     - Buy B (side="buy") to_notional>0  
     - Buy C (side="buy") to_notional>0  
     - If the sell is for a symbol not actually held (or fails/rejects at broker), you can end with 3 open positions.  
   - Code only does: `buys = [approved buys]`; if `len(buys) > max_positions` then reject extras. With `len(buys)=2`, it approves both regardless of existing holdings and regardless of whether sells succeed.  
   - **Wrong behavior:** positions after execution can be 3+ even though `max_positions=2`.

3) **Claim (MED): `max_positions` check ignores “buy” orders that reduce but keep a position (`to_notional` could be >0 on a sell-to-reduce edge cases are okay; the real issue is it doesn’t compute final unique symbols).**  
   **Failure scenario:**  
   - You can have a buy order whose `to_notional` is 0 (shouldn’t happen via `diff_orders`, but could via other strategy modules). It would be excluded from `buys` and not counted.  
   - More importantly, if multiple buy orders are for the same symbol (possible if upstream duplicates), they’re counted multiple times, causing incorrect rejection/approval patterns.  
   - **Wrong behavior:** `max_positions` gate is not tied to final set of symbols with nonzero target, so it can both under- and over-reject.

**src/tradebot/fastarm.py — `run_fast_once` / time handling**
4) **Claim (HIGH): market session times are hardcoded (9:30–16:00 ET) and ignore half-days; “flat before close” can fail, leaving positions open into/after early close.**  
   **Failure scenario:**  
   - On an early-close day (e.g., 13:00 ET close), broker stops trading at 13:00.  
   - Bot computes `close_dt = 16:00`, `flat_dt = 15:30`.  
   - At 12:30, `now < flat_dt`, so it does **not** execute EOD flatten. At/after 13:00, broker may reject closes or market is shut; bot will start returning `{"status":"market_closed"}` only when `now >= 16:00`, i.e., it will still think session is open for hours.  
   - **Wrong behavior:** intended invariant “everything flat before close” is violated; positions can persist overnight due to early close + wrong clock.

**src/tradebot/run.py — `run_once`**
7) **Claim (MED): idempotency can fail around UTC date vs market (ET) day; bot may run twice in one ET trading day or skip a day.**  
   **Failure scenario:**  
   - `today = datetime.now(timezone.utc).date().isoformat()` uses UTC date.  
   - `Ledger.last_run_date()` uses record `"ts"` which is UTC timestamp and slices `[:10]`.  
   - If you run near midnight UTC (e.g., 20:30 ET during DST is 00:30 UTC next day), the UTC date flips while still the same ET trading session.  
   - **Wrong behavior:** the “once per trading day” guard can allow an extra run in the same market day (or block the next morning) depending on when it ran relative to UTC midnight.
