### src/tradebot/risk.py — RiskManager.book_equity
1) **Claim (HIGH): book-cap baseline can “reset” after real trading losses, rebaselining away drawdown and preventing the kill switch.**  
**Failure scenario:**  
- Config: `risk.book_cap=50`, `risk.max_drawdown_pct=10`.  
- First capped run sets `book_baseline=100000` (slow arm on legacy $100k paper account as described in `config.yaml`).  
- A sequence of losses drops `raw` equity to `49,000` (a 51% loss; still a “real loss”, not a dashboard reset).  
- Condition triggers: `(raw < baseline*0.5)` is `49000 < 50000` **True** and `(raw <= cap*2)` is `49000 <= 100` **False** → so in this exact number it does *not* reset.  
  But if losses/drop plus some brokerage/account adjustment makes `raw` small enough to satisfy both, e.g. `raw=95` (possible after withdrawals, fees, account adjustments, or the account being switched/merged while code points at same state file), then:
  - `raw < 50000` **True** and `raw <= 100` **True** ⇒ baseline is re-anchored to 95.  
  - `book_equity` becomes `min(50 + (95-95), 95) = 50`, wiping out the historical loss in the capped equity path and therefore wiping out drawdown tracking in `check_drawdown()` (which reads equity passed in from `run_once`).  
**Why it’s concrete:** the code explicitly treats a collapse below `cap*2` as “reset” regardless of whether the equity drop came from trading or external account actions. With separate paper accounts now, an operator mistake (wrong credentials pointing to $50 account) plus old baseline in state, or any broker-side reset/adjustment, can satisfy the reset predicate and erase losses from the bot’s equity tracking.

### src/tradebot/risk.py — RiskManager.check_drawdown
2) **Claim (HIGH): high-water mark update is persisted *before* the drawdown check; any crash between `_save_state(state)` and `halt()` can permanently lose the halt even when drawdown was breached.**  
**Failure scenario:**  
- Equity falls from HWM 50 to 44.9 (10.2% DD).  
- `check_drawdown(44.9)` runs: it writes updated `high_water_mark` to disk, then computes `dd_pct` and calls `halt()`.  
- Process crashes after `_save_state` but before `halt()` writes `.halt`.  
- Next run: `.halt` is absent, so `run_once` proceeds to trade despite DD breach having occurred.  
**Why it’s concrete:** the halt state is not stored in the same atomic write as the HWM update; only `.halt` blocks trading in `run_once`.

### src/tradebot/risk.py — RiskManager.filter_orders
3) **Claim (HIGH): max_positions enforcement is incorrect; it limits *number of buy orders*, not resulting number of open positions.**  
**Failure scenario:**  
- Current positions already hold 2 symbols (at `max_positions=2`).  
- Rebalance generates one buy order to add a *third* symbol (e.g., rotate: sell 1, buy 2; or if dust sells get skipped under `min_order_notional`, you can end up not selling but still buying).  
- `buys` length is 1, so `len(buys) > max_positions` is False → buy is approved.  
- End state: 3 open positions, violating `risk.max_positions`.  
**Why it’s concrete:** the function never counts existing positions, and does not check `to_notional>0` uniqueness vs current holdings.

4) **Claim (MED): max_order_notional can be bypassed in drawdown flatten.**  
**Failure scenario:**  
- Large position market value `mv=200` exists (possible on the $100k slow arm if earlier logic ever allowed it, or manual intervention).  
- DD triggers; `flatten` creates an order with `notional=abs(mv)=200`.  
- These orders are submitted directly (`broker.submit`) without passing through `filter_orders`, so `max_order_notional=30` is ignored exactly when kill-switch fires.  
**Why it’s concrete:** flatten path in `run_once` bypasses `filter_orders`.

### src/tradebot/run.py — run_once
5) **Claim (HIGH): kill switch can place the *wrong side* order when broker positions are short and reported as negative market value.**  
**Failure scenario:**  
- Broker reports `positions()` as market value; for a short, Alpaca can return negative `market_value`. Suppose `mv=-20` for a short.  
- Flatten constructs: `side = "sell" if mv > 0 else "buy"` → selects `"buy"` (correct), `notional=abs(mv)=20`.  
- But `broker.submit` uses market order notional; depending on broker semantics, submitting a **buy notional** may *reduce* the short but can also **flip long** if the short quantity is smaller than implied by $20 notional at execution time (notional order sizing is not quantity-precise).  
- End state: can end up long after “flatten”.  
**Why it’s concrete:** flatten uses notional-based market orders derived from market value, not qty; `broker.close()` exists (qty-precise), but is not used here.

6) **Claim (MED): idempotency claim (“safe to re-run (idempotent per day)”) is false under `force=True`; can re-trade same day and bypass the daily-only invariant.**  
**Failure scenario:** operator runs `run_once(..., force=True)` twice on the same trading day. Second run is not blocked by `last_run_date()` check, so it can generate and submit a second full rebalance set (potentially oscillating positions and increasing costs / risk).  
**Why it’s concrete:** `force` bypasses the “already ran today” gate.

### src/tradebot/fastarm.py — run_fast_once (broker mode)
7) **Claim (HIGH): end-of-day flatten ignores early close days; uses hardcoded 16:00 ET. Positions can remain open into the close or be flattened too late.**  
**Failure scenario:**  
- Day after Thanksgiving: market closes 13:00 ET.  
- Code sets `close_dt` to 16:00 ET, `flat_dt` to 15:30 ET.  
- At 12:45 ET, `now >= flat_dt` is False, so it continues trading and does not force-flat before the real close.  
- At 13:05 ET, broker market is closed; `intraday_5min` may stop updating; positions remain open overnight (violates invariant) until next day’s `new_day` cleanup (which may be impossible if the market gaps and you can’t sell at intended time).  
**Why it’s concrete:** slow arm has `session_today()` logic in broker but fastarm never uses it.

8) **Claim (HIGH): kill-switch halt file is ignored by fast/movers arms; only `st["halted"]` is checked.**  
**Failure scenario:**  
- Global `.halt` is created (e.g., slow arm drawdown).  
- `run_fast_once` continues trading because it never checks `cfg.halt_path.exists()`.  
**Why it’s concrete:** `run_fast_once` checks only `st.get("halted")`.

9) **Claim (HIGH): risk caps from config (`risk.max_order_notional`, `risk.max_positions`) are not enforced at all in fast/movers broker mode.**  
**Failure scenario:**  
- `budget_per_slot = equity / top_k`; with equity ~50 and `top_k=2`, notional=25 is fine—but if equity grows (or if broker reports equity gross without subtracting accrued costs, or deposits happen), notional can exceed the global `risk.max_order_notional=30` and still be submitted.  
- Also can exceed `risk.max_positions=2` if `top_k` differs from risk, or if stale held count mismatch.  
**Why it’s concrete:** fastarm uses `f.top_k` and never calls `RiskManager.filter_orders`.

10) **Claim (HIGH): “broker mode” exit uses `broker.close(sym)` but still passes/assumes `pos["qty"]` from `positions_detail`; for short positions or partial fills, state/ledger qty can be wrong and stops can fail.**  
**Failure scenario:**  
- Broker has partial fills or corporate action changes qty; `_positions` returns broker qty, but `_fill(..., "sell", ..., qty=pos["qty"])` logs and computes modeled cost based on that qty/px even though the actual close uses `broker.close(sym)` (ignoring qty).  
- Modeled cost and P&L attribution become inconsistent with actual liquidation size.  
**Why it’s concrete:** sell path in live mode does not submit qty/notional; it closes full position but cost is computed from the passed `qty`.

11) **Claim (MED): opening-range calculation can include bars after the OR window due to timezone mismatch between `bars["t"]` and `or_end`.**  
**Failure scenario:**  
- `intraday_5min` returns timestamps tz-aware ET (`tz_convert(et)`), but if broker implementation (or a fake broker) returns naive timestamps or UTC timestamps, comparison `bars["t"] < or_end` can either error or silently mis-compare, including/excluding wrong bars.  
- Result: OR high/low computed with post-window bars (look-ahead) or empty OR causing no trades.  
**Why it’s concrete:** `opening_range` assumes consistent tz-aware datetimes; no normalization/validation exists.

### src/tradebot/signals.py — momentum_12_1
12) **Claim (LOW): insufficient-history check ignores `skip`; can compute momentum even when `skip` pushes the end index before available data.**  
**Failure scenario:**  
- `len(closes)=253`, `lookback=252`, `skip=21`.  
- Condition `len(closes) < lookback + 1` is `253 < 253` False, so it proceeds.  
- `end = closes.iloc[-(skip+1)]` is valid, `start = closes.iloc[-(lookback+1)]` is valid, but the effective lookback is not “252 excluding last 21” if series length barely meets 253; it uses a start that is too recent relative to intended window.  
**Why it’s concrete:** the minimum length for 12-1 with skip should be `lookback + skip + 1`, not `lookback + 1`.
