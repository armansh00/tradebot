### Findings

**src/tradebot/risk.py — `RiskManager.check_drawdown`**
1) **Claim (HIGH): high-water mark is updated and persisted *before* drawdown is evaluated, allowing a transient equity spike to permanently raise the HWM and trigger a false kill later.**  
   **Failure scenario:**  
   - Inputs: equity sampling uses `broker.equity()` at runtime (may include unsettled marks / intraday noise). Suppose day N morning equity reads **$55** (temporary), state saves `high_water_mark=55`. Later same day or next day equity normalizes to **$50** with no real loss.  
   - Wrong behavior: `dd_pct=(55-50)/55=9.09%` (near limit). Another small move to **$49.40** triggers `dd_pct=10.18%` → bot halts + flattens even though true peak equity may never have been $55.  
   - Concrete defect: you persist the HWM unconditionally before validating the equity sample quality; no smoothing/“close-only” rule; no rollback if equity sample is later deemed bad.

**src/tradebot/risk.py — `RiskManager.filter_orders`**
2) **Claim (HIGH): `max_positions` enforcement is logically wrong; it limits the *count of buy orders* rather than resulting open positions.**  
   **Failure scenario:**  
   - Config: `risk.max_positions=2`.  
   - Inputs: already holding 2 positions (e.g., positions = `{SPY: 25, QQQ: 25}`), strategy wants to rotate: sell QQQ, buy IWM, buy EFA (two buys) while SPY remains. `diff_orders` yields: `sell QQQ`, `buy IWM`, `buy EFA`.  
   - Wrong behavior: `filter_orders` sees `len(buys)=2` so both buys approved, even though after sells/buys you could end with **3 positions** (SPY + IWM + EFA) depending on whether QQQ sell fills/executes before buys or if sell is rejected/partial.  
   - The check ignores current holdings and sell fill uncertainty; a cash account can easily reject the sell/close? (or sell might be delayed), leaving you with >2 concurrent positions.

3) **Claim (MED): `max_positions` enforcement can reject valid rebalances and still allow excess positions due to ordering + mutation of `approved`.**  
   **Failure scenario:**  
   - Inputs: `approved` contains sells and buys; you compute `buys = [o for o in approved if ...]` and then remove from `approved` while iterating over `buys[self.cfg.risk.max_positions:]`. This removal is by object identity and depends on list contents not changing unexpectedly.  
   - Wrong behavior: if `approved` contains duplicate dict objects or reused dict references (possible if upstream mistakenly reuses), `approved.remove(o)` can remove the wrong element or raise `ValueError`, potentially skipping risk rejection and letting an over-positioning set through (or crashing open-loop).
   - This is concretely a mutation-while-filtering hazard without defensive copying.

**src/tradebot/run.py — `run_once`**
4) **Claim (HIGH): kill-switch flatten uses `positions = broker.positions()` market_value and submits that as `notional`, which can exceed `risk.max_order_notional` and bypass order-level caps entirely.**  
   **Failure scenario:**  
   - Config: `risk.max_order_notional=30`.  
   - Inputs: you are long SPY with market_value **$50** and drawdown triggers. Flatten order built as `{side:"sell", notional:50}`.  
   - Wrong behavior: flatten order notional **$50 > $30 cap**. It is submitted directly via `broker.submit(o)` without passing through `risk.filter_orders`, violating the documented invariant “no single order above $30”.  
   - If broker enforces its own limits (or buying power/available qty issues), flatten might partially fail, leaving exposure after “killed”.

**src/tradebot/fastarm.py — `run_fast_once` / `_fill`**
5) **Claim (HIGH): in broker mode, exits use `broker.close(sym)` but you still record modeled cost based on `qty*px` where `px` may be stale/0 and `qty` comes from `positions_detail`; this can make net equity math wrong and suppress the drawdown kill / daily loss stop.**  
   **Failure scenario:**  
   - Inputs: held symbol has no current bar and quote snapshot fails; `book_px` falls back to `entry_px` or even returns `(0.0, "none")`. `_fill(... side="sell" ...)` calls `broker.close(sym)` (doesn’t need px), but then accrues cost = `abs(qty * px * bps)`. If px fell back to **0.0**, accrued cost is **$0**.  
   - Wrong behavior: net equity `_mark_equity = broker.equity() - cost_accrued` is overstated; drawdown `dd` and `day_pnl_pct` are understated; kill-switch/daily loss stop may never fire when they should.

6) **Claim (MED): in broker mode, `st["or_low"]` maintenance is inconsistent and can disable stops after restarts.**  
   **Failure scenario:**  
   - Inputs: buy succeeds; you set `st["or_low"][sym]=lo` in the entry loop *after* `_fill` returns True. But in `_fill` buy path you also do `st["or_low"][sym] = st["or_low"].get(sym)` (no-op).  
   - If process crashes between `_fill` success and the later `st["or_low"][sym]=lo` assignment + `_save_state`, you can end up with a live broker position but **no `or_low` recorded** in state.  
   - Wrong behavior: stop logic uses `floor = st["or_low"].get(sym, ors.get(sym,(0,0))[1])`; if `ors` missing (data gap) and `or_low` missing, stop becomes unevaluable/never triggers.

**src/tradebot/broker.py — `intraday_5min`**
7) **Claim (MED): early-close protection in `fastarm.session_bounds()` is undermined because `intraday_5min()` hardcodes 16:00 ET end time, so on half-days you still request bars through 16:00 and may treat post-close emptiness/staleness as “no bar yet”, affecting OR/stop decisions.**

Depending on data API behavior, you may get last bar at 13:00 but still compute `lasts` from `df["c"].iloc[-1]` and proceed; any missing bars later are irrelevant, but your “market_closed” gating uses `now >= close_dt` (good) while data fetch is inconsistent and can return unexpected gaps/partials that make `opening_range()` or `live_px()` behave inconsistently around the boundary.
