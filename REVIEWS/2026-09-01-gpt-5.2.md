## Findings

### src/tradebot/risk.py — `RiskManager.filter_orders`
1) **Max-positions cap can be bypassed via sell+buy in same rebalance**  
**Severity: HIGH**  
**Claim:** `max_positions` is enforced only by counting buy orders (`buys = [...] if side=="buy" and to_notional>0`) and then limiting the *number of buy orders*, not the resulting number of nonzero target positions. A rebalance that *sells one symbol but buys two new ones* passes the check yet ends with 3 positions.  
**Failure scenario:**  
- Config: `risk.max_positions=2`  
- Current positions: `{"SPY": 25, "QQQ": 25}`  
- Targets: `{"TLT": 25, "GLD": 25}` (drop both SPY, QQQ; add TLT, GLD) would generate: sell SPY, sell QQQ, buy TLT, buy GLD → 2 buys OK.  
- Now a different rebalance: current positions `{"SPY": 25, "QQQ": 25}`; targets `{"QQQ": 25, "TLT": 25, "GLD": 25}` generates: sell SPY, buy TLT, buy GLD → `len(buys)=2` OK, but after execution positions are QQQ+TLT+GLD = **3 positions**, violating `max_positions`.

### src/tradebot/risk.py — `RiskManager.filter_orders`
2) **Order-notional cap ignores negative / NaN notionals**  
**Severity: MED**  
**Claim:** The check is `if o["notional"] > max_order_notional`. If an upstream bug (or broker adapter) produces `notional = float("nan")` or a negative notional, Python comparisons yield `False` (NaN) or fail to cap (negative), and the order will be “approved”.  
**Failure scenario:**  
- `orders=[{"symbol":"SPY","side":"buy","notional": float("nan"), ...}]`  
- `nan > 30.0` is False, order is approved and sent to broker with a NaN notional (behavior undefined; could be rejected, or could coerce to 0, or could throw and skip later risk logic). This is a concrete fail-open path in the risk gate.

### src/tradebot/run.py — `run_once`
4) **Kill-switch “flatten shorts included” logic is wrong: may buy *more* to cover shorts**  
**Severity: HIGH**  
**Claim:** `broker.positions()` returns `{symbol: float(p.market_value)}`. For shorts, Alpaca `market_value` is typically **negative** and its magnitude depends on price. Your flatten logic uses `notional=abs(mv)` and `side="buy" if mv < 0 else "sell"`. For a short, buying `abs(market_value)` notional is **not guaranteed** to close the position (and can overshoot/undershoot depending on current price and how Alpaca interprets notional buys for closing shorts).  
**Failure scenario:**  
- Short 1 share at $100, price moves to $50 → `market_value = -50`.  
- Kill triggers; code submits a **buy notional $50**. If broker interprets notional buy as “buy $50 worth” it buys 1 share (maybe closes) *only if fractional shares allowed for that asset/account*; if not, it may buy 0 shares or reject, leaving short open—contradicting the comment “Close EVERYTHING, shorts included”.  
- Worse: if price moved up to $200 → `market_value=-200`; buy notional $200 could buy 1 share and close, but the sizing is still incidental and not a robust “close position” action. Correct close should be via `close_position`/qty, not `market_value` notional.

### src/tradebot/fastarm.py — `run_fast_once` (broker/live mode)
5) **Positions are never updated after fills; `top_k` and stop logic can be violated intraday**  
**Severity: HIGH**  
**Claim:** In live mode `_positions()` returns `broker.positions_detail()`, but `run_fast_once` never refreshes `held` after submitting a buy within the same tick loop. Alpaca market orders can remain `new/accepted` briefly; `get_all_positions()` may not show the new position yet. The loop then still believes `len(held)` is unchanged and can submit additional buys, exceeding `top_k`. Similarly, stop/exit decisions within the same run can use stale holdings.  
**Failure scenario:**  
- `top_k=2`, `slots = 2 - len(held)=2` at tick start.  
- Two candidates, submits first buy; broker accepts but position doesn’t appear immediately.  
- Loop proceeds, submits second buy (fine), but if there are 3+ candidates and a transient delay, the loop can submit a third buy before `held` reflects any new positions because `slots` is decremented locally but `held` is never re-queried; more importantly, if a buy is rejected (insufficient buying power) `_fill` returns False, but `slots` is not decremented—then next candidate attempts again, potentially hammering submits up to `max_trades_per_day` without a consistent view of exposure. The risk cap for positions is not enforced at broker-submit boundary.

### src/tradebot/fastarm.py — `run_fast_once` / `_fill` (broker/live mode)
6) **Kill-switch + daily loss stop can submit invalid `sell` quantity in live mode**  
**Severity: HIGH**  
**Claim:** In live mode, exits use `_fill(... "sell", sym, px, pos["qty"], ...)`, but `_fill` ignores `qty` for sells and calls `broker.close(sym)` (good). However, the caller iterates `_positions(f, broker, st).items()`; in live mode those dicts have keys `qty/entry_px/market_value` and **no `last_px`**, and you often compute `px = lasts.get(sym, pos.get("last_px", pos["entry_px"]))`. If `entry_px` missing or non-float parse issues, px can throw. More importantly: you call `lasts[sym]` directly in some paths (`daily_loss_stop`, `eod_flat`) without guarding membership, which can crash mid-kill/flatten and leave positions open.  
**Failure scenario:**  
- Broker returns bars missing for a held symbol (halted name, data hiccup): `sym in held` but `sym not in lasts`.  
- At `daily_loss_stop`: `_fill(... lasts[sym] ...)` raises `KeyError`, the function aborts **before closing positions**, and `stopped_today` isn’t set. Trading can continue next tick; the daily loss stop is bypassed due to data gap exactly when it should flatten.

### src/tradebot/fastarm.py — `run_fast_once`
7) **Halt file is ignored by intraday arms (kill-switch bypass across processes)**  
**Severity: HIGH**  
**Claim:** Slow arm uses `RiskManager.halted()` which checks `cfg.halt_path` (the `.halt` file). Fast/movers arms never check `cfg.halt_path` at all; they only use `st["halted"]` in their own state file. So a global halt (manual or slow-arm-triggered) does **not** stop intraday trading.  
**Failure scenario:**  
- Slow arm hits drawdown; `RiskManager.halt()` writes `.halt`.  
- Scheduler continues calling `run_fast_once` every 30 minutes; it will keep trading because `.halt` is never consulted. This violates the explicit config rule: “presence of this file stops all trading”.

### src/tradebot/run.py — `run_once`
8) **Look-ahead / stale-data: daily closes may include current incomplete day**  
**Severity: MED**  
**Claim:** `broker.daily_closes(... TimeFrame.Day, start=...)` does not set an `end` and does not filter out “today”. Depending on Alpaca’s semantics, the returned daily bar set can include today’s in-progress daily bar during market hours. `signals.snapshot` uses `closes.iloc[-1]` as “price” and uses it for SMA filter; that can become a look-ahead-ish intraday value not available at the strategy’s intended “once per day” decision time (especially if run midday due to scheduler).  
**Failure scenario:**  
- `run_once` executes at 14:00 ET (market open).  
- Alpaca includes today’s partial day bar close so far. Strategy uses it as the latest close and could flip `above_sma` / momentum ranking based on intraday move, producing trades that would not exist using only completed daily bars.
