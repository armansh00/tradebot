### Findings

**File:** `src/tradebot/risk.py`  
**Function:** `RiskManager.filter_orders`  
**1) Claim (HIGH): max_positions cap can be bypassed via sell+buy rebalance in the same run.**  
- **Why:** It limits the *count of buy orders* (`buys = [...]`) rather than the *resulting number of non-zero target positions* after applying sells and buys together. If you already hold positions that are *not being fully sold to zero*, you can end up with more than `max_positions` total positions even when `len(buys) <= max_positions`.  
- **Failure scenario:**  
  - Config: `risk.max_positions = 2`  
  - Current positions (market value): `{"SPY": 10, "QQQ": 10}` (2 positions)  
  - Targets: keep `SPY` at 5 (partial sell), keep `QQQ` at 10, add `IWM` at 10 (one buy)  
  - `diff_orders` emits: sell SPY 5 (to_notional=5), buy IWM 10 (to_notional=10)  
  - `filter_orders` sees only **one** buy -> passes.  
  - **Result:** after execution you hold `SPY`, `QQQ`, `IWM` = **3 positions**, violating `max_positions`.

**File:** `src/tradebot/risk.py`  
**Function:** `RiskManager.filter_orders`  
**2) Claim (MED): order-notional cap can be bypassed if broker.submit accepts qty orders (cap only checks `o["notional"]`).**  
- **Why:** The risk check only enforces `o["notional"] > max_order_notional`. If any caller submits an order dict with `qty` (and an absent/0/understated `notional`), the cap is not enforced. `AlpacaBroker.submit` will prefer `qty` if present (`kw = {"qty": order["qty"]} if order.get("qty") else ...`).  
- **Failure scenario:**  
  - Config: `risk.max_order_notional = 30`  
  - A future strategy/arm bug or manual override produces `{"symbol":"SPY","side":"buy","qty": 1, "notional": 0.01, "to_notional": 999}` while SPY trades at $500  
  - `filter_orders` passes because `notional` is 0.01  
  - `broker.submit` sends `qty=1` -> ~$500 notional order, violating cap.

**File:** `src/tradebot/run.py`  
**Function:** `run_once`  
**3) Claim (HIGH): `force=True` bypasses both “market closed” and “already ran today” guards, enabling trades after the bot’s scheduling invariants.**  
- **Why:** With `force=True`, the code skips:
  - idempotency guard (`ledger.last_run_date() == today`)
  - `broker.market_open()` guard  
  It will still proceed to compute targets and submit orders.  
- **Failure scenario:**  
  - Operator runs `run_once(..., force=True)` on a Saturday or after market close when `broker.market_open()` would be false.  
  - Strategy emits orders; `broker.submit` places market orders (Alpaca may accept and queue/route depending on venue rules; at minimum you’ve violated “no trading when market closed” invariant).  
  - Even worse: repeated forced runs in one day can spam orders and thrash positions, potentially exceeding intended trade frequency/risk assumptions.

**File:** `src/tradebot/fastarm.py`  
**Function:** `run_fast_once`  
**4) Claim (HIGH): broker-mode exit paths can crash due to missing `qty` in `positions_detail()` records, preventing kill-switch flattening and leaving positions open.**  
- **Why:** In broker mode, `_positions()` returns `broker.positions_detail()` records shaped as `{"qty": ..., "entry_px": ..., "market_value": ...}`. That’s fine. But if the broker implementation ever returns a different schema (or a symbol record missing `"qty"` due to API change / partial data), multiple critical paths do `pos["qty"]` without guarding:
  - drawdown kill: `_fill(..., pos["qty"], "drawdown_kill", ...)`
  - daily loss stop: `... lasts[sym], pos["qty"] ...`
  - eod flat: `... lasts[sym], pos["qty"] ...`
  - overnight flatten: `... pos["qty"] ...`
- **Failure scenario:**  
  - `broker.positions_detail()` returns `{"SPY":{"market_value":25.0,"qty":None,...}}` or omits `qty` for one symbol (API hiccup or serialization bug).  
  - A drawdown breach occurs; loop hits that position; `pos["qty"]` KeyError/TypeError; function aborts before flattening others.  
  - **Result:** kill-switch intended flatten does not complete; positions remain open while `st["halted"]=True` might or might not be written depending where the exception hits.

**File:** `src/tradebot/fastarm.py`  
**Function:** `run_fast_once`  
**5) Claim (MED): opening-range logic can use future/unavailable bars if `broker.intraday_5min()` returns bars through session end regardless of `now`.**  
- **Why:** `bars = broker.intraday_5min(universe)` has no `end=now` parameter. If the data provider returns the full day’s bars (common in replay/backfill modes or if `intraday_5min` is called with a historical `day`), then:
  - `lasts = df["c"].iloc[-1]` becomes the *day’s close*, not the last price as of `now`.
  - `opening_range(df, or_end)` uses bars `< or_end`, which is fine, but entry/exit decisions compare `lasts[sym]` (potentially future close) to OR levels, causing look-ahead trading.
- **Failure scenario:**  
  - At 10:05 ET, `intraday_5min` mistakenly returns all bars up to 16:00 for today (or you run a replay where the full-day dataframe is handed in).  
  - `lasts[sym]` equals 15:55/16:00 close, potentially well above OR high.  
  - Bot “breaks out” immediately and enters based on information from the future.

**File:** `src/tradebot/compare.py`  
**Function:** `_daily_equity`  
**6) Claim (LOW): daily equity bucketing for `fast_run` can misattribute days, corrupting drawdown/evaluation windows.**  
- **Why:** For `run_type != "run"`, it uses `r.get("day", r["ts"][:10])`. In `fastarm`, `day=today` is based on `now_et().date()`, while `ts` is UTC. Around midnight UTC (evening ET), `ts[:10]` will be “tomorrow” while `day` is “today”. If any `fast_run` record is missing `day` (bug/partial write), it will bucket into the wrong date and distort overlap windows and stats.  
- **Failure scenario:**  
  - A `fast_run` record is written without `"day"` (future refactor/bug).  
  - It runs at 23:30 ET (03:30 UTC next day).  
  - `_daily_equity` buckets it as the UTC date (next day), shifting series forward one day, distorting max_dd and “overlap weeks” checks.
