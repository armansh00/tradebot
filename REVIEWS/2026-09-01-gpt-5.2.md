### Findings

**src/tradebot/run.py → `run_once`**
1) **Claim:** `force=True` bypasses the halt file completely (kill-switch bypass).  
**Severity:** HIGH  
**Scenario:** `.halt` exists because `RiskManager.halt()` fired yesterday (e.g., equity drawdown breach). Operator calls `run_once(cfg, broker, force=True)` to “just rerun logging”. Code path: `if risk.halted(): ... return` executes **before** the `force` check, so this looks safe—but only if `.halt` exists. If the state file is truncated/empty but `.halt` got deleted or never created (see risk.py state issues below), `force=True` will still allow trading even though a drawdown breach condition may still exist. Concretely: if `check_drawdown()` would have halted but state got reset/lost, `force=True` allows an extra trading run that should have been prevented by persisted HWM/halt.

**src/tradebot/risk.py → `filter_orders`**
2) **Claim:** max_positions enforcement is wrong; it counts buy *orders* not resulting *positions*, so you can exceed `max_positions`.  
**Severity:** HIGH  
**Scenario:** `max_positions=2`, current positions already include 2 symbols (e.g., `positions={"SPY":15,"QQQ":15}`), and targets rotate to two *different* symbols (e.g., sell SPY/QQQ, buy IWM/EFA). `diff_orders` creates 4 orders: 2 sells + 2 buys. `filter_orders` sees `buys` length == 2 and approves both, even though sells may fail/reject (or execute after buys), leading to 4 concurrent positions temporarily or permanently (if sell rejects). Inputs: broker rejects sells due to short-sale constraints/position mismatch or partial fills; output: bot holds >2 symbols despite cap.

3) **Claim:** `filter_orders` can violate `max_positions` due to mutation while iterating (`approved.remove(o)` on items derived from `buys[...]` which was built from `approved`).  
**Severity:** MED  
**Scenario:** If there are duplicate dict objects in `approved` (possible if upstream accidentally reuses dict references or broker layer returns same object), `remove` removes the first matching object, potentially not the one being iterated, leaving an excess buy in `approved`. Result: more buy orders survive than allowed.

**src/tradebot/risk.py → `book_equity`**
4) **Claim:** baseline “reset” condition can re-anchor after a real loss, effectively erasing drawdown and preventing the kill switch.  
**Severity:** HIGH  
**Scenario:** cap=50. baseline=100k-era baseline or prior baseline (say 100.00 if previously uncapped logic changed), raw equity falls due to trading losses to 49.90. Condition `(raw < baseline*0.5 and raw <= cap*2)` becomes true (49.90 < 50 and <=100), so baseline resets to 49.90. Then `book_equity` returns `min(cap+(raw-baseline), raw)=min(50+(0),49.9)=49.9`. High-water mark logic uses this equity; but resetting baseline can cause future `book_equity` to track near-raw and avoid reflecting losses relative to the originally intended anchored book. Path: large loss that brings raw under half baseline (which can happen if baseline was incorrectly set high, e.g., from prior $100k account state leak) triggers rebase and can suppress drawdown detection that should have fired earlier.

**src/tradebot/fastarm.py → `run_fast_once`**
5) **Claim:** In broker mode, `_positions()` returns dicts with keys `qty/entry_px/market_value`, but code assumes `pos["qty"]` exists everywhere; overnight flatten and kill switch will crash or misbehave if Alpaca returns positions with non-float qty formats or missing fields.  
**Severity:** MED  
**Scenario:** Alpaca returns `qty` as a string or a Decimal-like; `positions_detail()` casts to float, but if broker implementation differs (FakeBroker/tests), `pos["qty"]` may be absent (only `market_value`). Then flatten loops (`_fill(... pos["qty"] ...)`) raise KeyError, preventing flatten on daily loss stop / drawdown kill / EOD flat. Result: trades continue after kill condition because the flatten attempt aborts before setting `st["halted"]=True` (in drawdown path it is set after flatten loop).

6) **Claim:** Drawdown kill switch can be bypassed via division-by-zero/negative HWM behavior if equity becomes negative (possible with broker mode margin/shorts or bad cost accrual).  
**Severity:** HIGH  
**Scenario:** In broker mode `_mark_equity = broker.equity() - cost_accrued`. If cost_accrued exceeds broker.equity (e.g., repeated trading, cost accrues, equity ~50, cost_accrued ~60), equity becomes negative. Then `st["high_water_mark"] = max(st.get("high_water_mark", equity), equity)` keeps prior positive HWM, but kill computation `dd = (hwm - equity)/hwm*100` yields >100% and triggers—however, if `hwm` ever becomes 0 or negative due to corrupted state load (`high_water_mark` missing/0) and equity negative, the code sets `dd` to 0.0 (`if st["high_water_mark"] > 0 else 0.0`) and **never halts** while equity is negative. Inputs: state file missing `high_water_mark` (e.g., manual edit or truncated JSON replaced with `{}`) and equity negative → wrong behavior: no kill.

7) **Claim:** `now` timezone consistency is assumed; if broker.now_et() returns naive datetime, comparisons against `open_dt/close_dt` are wrong and day roll can corrupt “new_day” logic (DST/naive bug).  
**Severity:** MED  
**Scenario:** FakeBroker returns `datetime.utcnow()` (naive). `open_dt = now.replace(hour=9,30,...)` also naive but interpreted as UTC-like time; the arm will treat premarket or after-hours as regular session, producing trades outside intended window; also `today = now.date()` uses UTC date, so around midnight UTC (8pm ET) it flips “day”, triggers overnight flatten at the wrong time.

**src/tradebot/broker.py → `intraday_5min`**
8) **Claim:** Opening-range window in `fastarm.opening_range` is vulnerable to look-ahead depending on bar timestamp semantics (bar end vs bar start).  
**Severity:** HIGH  
**Scenario:** Alpaca bar timestamps are typically bar start time; some feeds use bar end. `opening_range` includes `bars["t"] < or_end`. If `t` is bar *end* time, the 10:00 bar representing 9:55–10:00 has `t==10:00` and is excluded correctly; but if `t` is bar *start* time, the 9:55 bar has `t==9:55` and is included (fine). The bug is if Alpaca’s `timestamp` is bar *end* and you later change provider or your FakeBroker uses bar-start—this function has no invariant check, and can accidentally include the 10:00–10:05 bar when `t==10:00` but represents period starting 10:00 (i.e., **post-window data** inside opening range), causing look-ahead: breakout levels incorporate bars after or_end.

**src/tradebot/ledger.py → `write`**
9) **Claim:** Ledger writes are not atomic; concurrent runs can interleave JSON lines and corrupt the ledger, breaking idempotency and potentially bypassing “already ran today”.  
**Severity:** MED  
**Scenario:** Two schedulers trigger `run_once` simultaneously. Both read `last_run_date()` before either writes “run”. Both proceed to trade. Their `ledger.write()` calls append concurrently; JSON lines can interleave on some filesystems, causing unreadable JSON, so future `last_run_date()` may return None, enabling repeated runs/trades in the same day.

**src/tradebot/compare.py → `_daily_equity`**
10) **Claim:** Fast/movers daily equity selection can silently pick an intraday snapshot (not end-of-day) because it takes the last record per calendar day, not the record at/after flatten. This can mask drawdowns and misstate results.  
**Severity:** LOW  
**Scenario:** fast arm writes multiple `fast_run` records per day. If the last tick is missed (scheduler outage), the last record could be midday while still holding positions; compare report treats that as the day’s equity, overstating performance and understating DD.

Overall risk assessment: **HIGH — multiple concrete paths can exceed position caps and/or fail to halt when drawdown/stop conditions should stop trading.**
