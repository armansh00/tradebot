### Findings

**src/tradebot/risk.py — `RiskManager.filter_orders`**  
1) **Claim:** `max_positions` cap is applied to the *count of buy orders*, not to resulting open positions; it can be bypassed with existing holdings or with “no-buy” rebalances.  
**Severity:** HIGH  
**Scenario:** `max_positions=2`. Current positions already hold 2 symbols (A and B). Strategy decides to rotate into C by selling A and buying C (still 2 target positions). `diff_orders` yields one sell (A) and one buy (C). `filter_orders` sees `len(buys)=1` so it approves the buy, even though during execution ordering/cash/partial-fill effects can temporarily produce 3 concurrent positions (A not fully liquidated yet, B held, C bought). With real broker fills, you can end up >2 positions intraday, violating the cap.

**src/tradebot/risk.py — `RiskManager.filter_orders`**  
2) **Claim:** Order notional cap checks `o["notional"]` only; flattening/close paths can generate orders that exceed cap and still get submitted (because they bypass `filter_orders`).  
**Severity:** HIGH  
**Scenario:** In `run.py`, drawdown flatten constructs `flatten` orders with `"notional": abs(mv)` where `mv` is market value of a position. If a position market value is $80 (possible if price moves up after purchase, or if earlier logic ever allowed larger notionals), the flatten order notional is $80, exceeding `max_order_notional=30`. Those orders are submitted directly via `broker.submit(o)` without going through `risk.filter_orders`, violating the “no single order above $30” rule exactly when the kill switch triggers.

**src/tradebot/run.py — `run_once`**  
3) **Claim:** Global halt file is checked only at start; trading can proceed even if `.halt` is created after the initial check (no re-check before submitting orders).  
**Severity:** MED  
**Scenario:** Process starts, `risk.halted()` is false. After decision is logged but before `broker.submit` loop, an operator (or another arm) writes `.halt`. `run_once` still submits approved orders because it never re-checks `risk.halted()` prior to execution.

**src/tradebot/fastarm.py — `run_fast_once` / `_fill` (broker mode)**  
4) **Claim:** Intraday arms ignore `risk.halt_file` entirely; `.halt` will not stop them.  
**Severity:** HIGH  
**Scenario:** Config sets `risk.halt_file: .halt` as the hard brake. If `.halt` exists, `run_once` stops, but `run_fast_once` only checks `st.get("halted")` (arm-local flag). So after a slow-arm drawdown halt writes `.halt`, the fast/movers arms will keep trading normally unless their own drawdown logic sets `st["halted"]=True`.

**src/tradebot/fastarm.py — `run_fast_once` (new day handling, broker mode)**  
5) **Claim:** Overnight-flatten in broker mode can crash due to missing `qty` in `positions_detail`, leaving positions unflattened and the state partially advanced to the new day.  
**Severity:** HIGH  
**Scenario:** `_positions(... broker ...)` returns `{"qty": float(p.qty), "entry_px": ..., "market_value": ...}` (no `last_px`). In `new_day` block:  
`px = lasts.get(sym, pos.get("last_px", pos["entry_px"]))` works, but then `_fill(..., "sell", ..., qty=pos["qty"], ...)` calls broker mode sell path which uses `broker.close(sym)` and **ignores qty**; that part is fine. The crash is earlier/later: other sell paths (eod_flat, daily_loss_stop, or_low_stop, drawdown_kill) use `lasts[sym]` directly; if `sym` missing from `lasts` (no bars yet / data hiccup), you get `KeyError` and the function exits before flattening. Because `_save_state` happens only at end (except on kill), the bot may repeatedly attempt and fail, carrying overnight positions indefinitely.

**src/tradebot/fastarm.py — `run_fast_once` (cost model / equity math)**  
6) **Claim:** In broker mode, modeled costs reduce “equity” used for risk decisions, but **do not reduce broker cash**, so sizing can exceed intended net-risk budget and violate practical cash constraints unpredictably.  
**Severity:** MED  
**Scenario:** Broker account equity/cash remain gross. `_mark_equity` returns `broker.equity() - cost_accrued`. Budget per slot uses this net equity, but order sizing uses `cash = broker.cash()` (gross) then `notional = min(budget_per_slot, cash)`. If costs accrue, net equity drops while cash may remain high (especially if positions unrealized up). This creates inconsistent state: decisions/risk stops based on net, execution based on gross, which can lead to larger exposure than implied by the “net equity” kill-switch logic (e.g., continue entering because cash is available even though net drawdown would have halted earlier/later).

**src/tradebot/signals.py — `momentum_12_1`**  
7) **Claim:** Look-ahead bug: `skip` is not enforced in the data sufficiency check; function can compute momentum using data that includes skipped period when `len(closes)` is between `lookback+1` and `lookback+skip+1`.  
**Severity:** MED  
**Scenario:** `lookback=252`, `skip=21`. If `len(closes)=253` (just enough for `lookback+1`), the function passes the check, but then `end = closes.iloc[-(skip+1)]` indexes beyond available history (negative index too large), raising `IndexError` or pulling wrong data depending on pandas behavior. If it doesn’t crash (e.g., caught upstream), it’s either stale/incorrect momentum or missing, but the bug is concrete: the guard should be `len(closes) < lookback + skip + 1`.

**src/tradebot/run.py — `run_once` / src/tradebot/ledger.py — `last_run_date`**  
8) **Claim:** “Idempotent per day” is based on UTC calendar day, not exchange day; can double-run or skip runs around midnight UTC.  
**Severity:** MED  
**Scenario:** Bot intended “once per trading day” (US equities). At ~20:30 ET it’s already next day in UTC during DST/standard shifts (e.g., 00:30 UTC). `today = datetime.now(timezone.utc).date().isoformat()` flips while the market session is still the same ET trading day, so a second invocation later in the same ET session will not match `ledger.last_run_date()` and will run again, potentially placing duplicate orders.

**src/tradebot/fastarm.py — `run_fast_once`**  
9) **Claim:** Opening-range and session boundaries are hardcoded 9:30–16:00 ET; half-days are not handled, so “flatten before close” can place trades after the actual close or fail to flatten by the real close.  
**Severity:** MED  
**Scenario:** Day after Thanksgiving closes 13:00 ET. Code still treats close as 16:00 and will continue trading between 13:00–16:00 with stale/empty bars (leading to KeyErrors on `lasts[sym]`, or simply not flattening when required). Positions may remain open overnight, violating the arm invariant.

**Overall risk assessment:** HIGH — multiple concrete paths allow trading to continue after a global halt, exceed position/order caps during kill behavior, and double-run on the same trading session due to UTC day logic.
