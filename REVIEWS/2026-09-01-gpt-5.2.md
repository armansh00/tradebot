### Findings

**src/tradebot/risk.py — `RiskManager.filter_orders`**
1) **Claim (HIGH): max_positions can be bypassed by “buy” orders that reduce an existing position, and by net-new “buy” orders with `to_notional == 0`.**  
   **Why:** max_positions enforcement counts only `approved` orders where `side=="buy"` and `to_notional > 0`. That is not equivalent to “orders that result in holding more than `max_positions` symbols”.  
   **Failure scenario:**  
   - Inputs: `max_positions=2`, current positions `{SPY: 15, QQQ: 15}`. Strategy produces orders:  
     - `{"symbol":"SPY","side":"sell","from_notional":15,"to_notional":0,"notional":15}`  
     - `{"symbol":"AAPL","side":"buy","from_notional":10,"to_notional":0,"notional":5}`  (a buggy strategy/order builder could do this; risk layer should fail closed)  
     - `{"symbol":"MSFT","side":"buy","from_notional":0,"to_notional":15,"notional":15}`  
   - Wrong behavior: The AAPL order is a “buy” but has `to_notional==0`, so it is *not counted* toward the buys list, and can slip through alongside the MSFT buy. Net effect can create >2 concurrent positions depending on broker fill behavior / existing holdings, while risk thinks it enforced the cap.

**src/tradebot/run.py — `run_once`**
2) **Claim (HIGH): kill-switch flatten can submit orders above `max_order_notional` (risk caps not applied during flatten).**  
   **Why:** On drawdown breach, it constructs `flatten` orders with `notional = abs(mv)` for each position and submits them directly, bypassing `RiskManager.filter_orders`. If a position market value exceeds `$30`, the bot will place an order > `$30` even though `risk.max_order_notional=30`.  
   **Failure scenario:**  
   - Inputs: `max_order_notional=30`, positions `{"SPY": 100.00}` (possible on the slow arm because `accounts.slow` uses a $100k paper account and `book_cap` is synthetic; also possible if drift or partial fills accumulate). `risk.check_drawdown(equity)` returns `True`.  
   - Wrong behavior: bot submits a sell notional $100 order during flatten. Risk cap is violated exactly when “hard brakes” are most needed.

3) **Claim (MED): halt-file can be ignored if created after the initial `risk.halted()` check (TOCTOU), allowing trades “after the kill switch should have fired.”**  
   **Why:** `run_once` checks `risk.halted()` only once at the start. If an external supervisor writes `.halt` after that point but before order submission, the run still proceeds to submit orders.  
   **Failure scenario:**  
   - Inputs: process starts at 09:31, passes `halted()` check. At 09:32 an operator drops `.halt`. At 09:33 the bot computes targets and submits orders.  
   - Wrong behavior: orders are placed even though halt condition is active. (Risk spec says “presence of this file stops all trading”.)

**src/tradebot/risk.py — `RiskManager.book_equity`**
4) **Claim (HIGH): book-cap “account reset” detection can erase real losses on the slow arm, preventing drawdown halt.**  
   **Why:** Re-anchoring condition is `raw < baseline*0.5 and raw <= cap*2`. On the slow arm, `cap=50` but the backing paper account is ~$100k. If the account equity ever drops (for *any* reason) below `cap*2 = $100`, the code reanchors baseline to that low value. That makes `book_equity = min(cap + (raw - baseline), raw)` jump back up to ~cap and can avoid triggering the drawdown kill switch that is based on book equity. This is exactly a “rebaseline logic that erases real losses” path, and the trigger is not restricted to “dashboard reset” vs “real loss”—it only inspects `raw`, not provenance.  
   **Failure scenario:**  
   - Setup: slow arm on $100k paper account. Initial baseline recorded at `raw=100000`.  
   - Event: broker API glitch/misread returns `raw=80` for one run (or account is actually reset by operator mistake, which is still a real loss relative to the bot’s prior high-water for evaluation purposes).  
   - Wrong behavior: condition true (`80 < 50000` and `80 <= 100`), baseline is re-anchored to 80, `book_equity` becomes `min(50 + (80-80), 80) = 50`. Drawdown check now sees equity ~50 vs prior HWM maybe ~50 as well, so no kill. The bot continues trading as if nothing catastrophic happened.

**src/tradebot/fastarm.py — `run_fast_once` / `_fill` (live mode)**
5) **Claim (HIGH): daily-loss stop and drawdown kill can fail to flatten shorts; code always sells to exit.**  
   **Why:** In fast arm kill paths, it calls `_fill(..., "sell", sym, ..., pos["qty"], ...)` regardless of whether the position is long or short. In live mode, `_fill` with side `"sell"` calls `broker.close(sym)` (which correctly liquidates either direction *if* the broker API does), but in simulated mode it assumes a long: it `pop`s the position and adds `qty * fill_px` to cash as if selling long. Also, `_positions_detail()` returns `qty` which will be negative for shorts on Alpaca; passing negative `qty` into simulated logic breaks cash/P&L math, and the stop logic is not side-aware.  
   **Failure scenario:**  
   - Inputs: a short exists (possible if broker mode allows shorting in paper, or if positions_detail reports negative qty due to some corporate action / borrow). `pos["qty"] = -1`. Drawdown kill triggers.  
   - Wrong behavior (simulated): `_fill` called with `side="sell", qty=-1` leads to `gross = qty*px` negative, cash update `st["cash"] += qty*fill_px` reduces cash (wrong direction), and position is popped without actually accounting for buy-to-cover economics. Kill switch can *worsen* equity math and leave state inconsistent.  
   - Wrong behavior (live): if Alpaca `close_position` handles shorts, you’re OK on execution, but your modeled costs and ledger quantities (`qty=round(qty,6)` negative) and stop-floor logic are inconsistent; in particular, OR-low stop compares `lasts[sym] < floor` even for shorts (should be reversed).

**src/tradebot/fastarm.py — `run_fast_once` (time/session handling)**
6) **Claim (MED): early-close days (13:00 ET) are not respected; “flat before close” can happen after the market is shut.**  
   **Why:** fast arm hardcodes `CLOSE_T = 16:00` and uses `now >= close_dt` to mark market closed. Broker has `session_today()` that explicitly handles half days, but fast arm doesn’t use it.  
   **Failure scenario:**  
   - Inputs: day after Thanksgiving, market closes 13:00. At 13:05 ET, `now < close_dt(16:00)` so arm believes market is open, continues evaluating, possibly submits orders (which get rejected) and—more importantly—misses the intended invariant “flat by 30 minutes before the bell” because `flat_dt` is computed off 16:00, not 13:00.

**src/tradebot/signals.py — `momentum_12_1`**
7) **Claim (LOW): look-ahead/stale-data mismatch with “skip” window definition; skip is not validated against series length and can silently use the wrong end index.**  
   **Why:** function checks only `len(closes) < lookback + 1`, but uses `end = closes.iloc[-(skip + 1)]`. If `skip` is large relative to `len(closes)`, pandas negative indexing can raise or select unintended data depending on exact length; there is no explicit guard `len(closes) >= lookback + skip + 1`.  
   **Failure scenario:**  
   - Inputs: `lookback=252`, `skip=21`, but broker returns only 253 closes (enough for lookback+1 but not for skip).  
   - Wrong behavior: `end = closes.iloc[-22]` is valid only if length ≥ 22; it is, but the skip window is not what you think; you’re effectively computing a shorter skip than configured, contaminating “12-1” with recent data.

**src/tradebot/run.py — `run_once` (idempotency/day rollover)**
8) **Claim (MED): idempotency is keyed to UTC date, not exchange session date; can double-run or skip a session around UTC midnight.**  
   **Why:** `today = datetime.now(timezone.utc).date().isoformat()` and `ledger.last_run_date()` compares `rec["ts"][:10]` (UTC timestamp string) to that. For US markets, the trading session is ET; UTC date flips at 20:00/21:00 ET depending on DST.  
   **Failure scenario:**  
   - Inputs: bot runs at 19:55 ET (23:55 UTC) and again at 20:05 ET (00:05 UTC next day) on the same trading session.  
   - Wrong behavior: second run sees a different `today` in UTC and will run again (placing duplicate orders), violating “idempotent per day” for the exchange day.

Overall risk assessment: **HIGH—multiple concrete paths allow risk caps and halts to be bypassed, and session/idempotency handling can trigger duplicate or late trades.**
