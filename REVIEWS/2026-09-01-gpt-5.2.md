### 1) Kill switch bypassed on “force” reruns
- **File/Function:** `src/tradebot/run.py::run_once`
- **Claim 1 (HIGH):** Setting `force=True` bypasses both idempotency and the `broker.market_open()` gate, allowing trades after the bot should be inert for the day or during closed market conditions.
- **Failure scenario:**  
  **Inputs:** operator/scheduler calls `run_once(cfg, broker, force=True)` at 22:00 ET (market closed) with no `.halt` file; strategy produces buy targets.  
  **Wrong behavior:** code skips the `market_open()` check and proceeds to compute signals and submit orders (`broker.submit`) anyway. If the broker accepts queued DAY orders (or your FakeBroker does), you have “trades” placed outside allowed session control, and potentially multiple runs per day (because `last_run_date()` check is also bypassed).

### 2) Max-positions cap can be violated via sells counted as “approved buys”
- **File/Function:** `src/tradebot/risk.py::RiskManager.filter_orders`
- **Claim 2 (HIGH):** `max_positions` is enforced by counting *buy orders* (`side=="buy" and to_notional>0`) rather than enforcing the *resulting portfolio position count*. This allows ending the cycle with more than `max_positions` holdings if the rebalance includes “buys” that are actually reductions but still have `to_notional > 0`.
- **Failure scenario:**  
  **Inputs:** `max_positions=2`. Current positions: `{"SPY": 10, "QQQ": 10, "IWM": 10}` (already 3 due to prior drift/manual action). Targets: keep all three but reduce each to 5 (so all deltas are negative? actually deltas are -5 so sells; not triggering). More direct: current `{"SPY": 0, "QQQ": 20, "IWM": 20}` targets `{"SPY": 5, "QQQ": 15, "IWM": 15}`. This creates **three** buy-side deltas? No, two sells and one buy; positions end at 3 (SPY added) while still holding QQQ and IWM.  
  **Wrong behavior:** `filter_orders` only limits count of buy orders, not final number of nonzero targets. It will approve the SPY buy because there is only one buy, even though resulting holdings become 3, exceeding `max_positions=2`. (Nothing elsewhere prevents targets from containing >2 symbols if strategy changes or if targets are injected; risk layer should still cap final portfolio.)

### 3) Order-notional cap can be bypassed in drawdown flatten
- **File/Function:** `src/tradebot/run.py::run_once` (drawdown branch)
- **Claim 3 (MED):** When drawdown triggers, flatten orders are submitted **without passing through** `RiskManager.filter_orders`, so `risk.max_order_notional` is ignored exactly when risk controls matter most.
- **Failure scenario:**  
  **Inputs:** `max_order_notional=30`. Positions contain one symbol with market value `$45` (possible if price moved after earlier compliant orders). Drawdown triggers.  
  **Wrong behavior:** flatten generates `{"notional": 45}` and submits it directly, violating the per-order notional cap.

### 4) Fast/movers arms: drawdown & daily-stop exits can fail (broker-mode) because you size sells using a qty field that doesn’t exist
- **File/Function:** `src/tradebot/fastarm.py::run_fast_once` (multiple exit paths)
- **Claim 4 (HIGH):** In broker mode, `_positions()` returns `broker.positions_detail()` records with keys `{"qty","entry_px","market_value"}`. But the code later computes `positions={... p["qty"] * lasts ...}` safely, **and also calls** `_fill(..., qty=pos["qty"], ...)` on sells. In broker mode `_fill` ignores `qty` for sells and uses `broker.close(sym)`, so that’s fine. The real bug is earlier: `for sym, pos in list(_positions(...).items()): px = lasts.get(sym, pos.get("last_px", pos["entry_px"]))` — in broker mode there is no `last_px`, fine; it falls back to `entry_px`. However, for **symbols missing from `lasts`**, you price exits at **entry price**, not current price, and then you compute equity/drawdown using `broker.equity()` (current), but log/order decisions (and modeled costs) using stale/incorrect px.
- **Failure scenario:**  
  **Inputs:** a held symbol has no intraday bars returned (API hiccup) so it’s absent from `lasts`, but broker equity reflects a large unrealized loss. Drawdown triggers; you call `_fill` with `px=entry_px` and accrue modeled cost based on `entry_px` instead of real liquidation notional.  
  **Wrong behavior:** modeled costs and ledger records materially wrong; also your stop logic `lasts[sym] < floor` can KeyError elsewhere (see next finding) so you may not exit when you should.

### 5) Fast/movers arms: KeyError can prevent exits and bypass daily-loss/eod-flat logic for missing bars
- **File/Function:** `src/tradebot/fastarm.py::run_fast_once`
- **Claim 5 (HIGH):** Several exit paths index `lasts[sym]` without checking `sym in lasts`, which can throw and abort the run, leaving positions open (including past intended flat time) and preventing kill-switch actions from executing.
- **Failure scenario:**  
  **Inputs:** you hold `AAPL`, but `broker.intraday_5min([...])` returns empty df for AAPL (rate-limit/partial outage). Then `lasts` has no `AAPL`. At/after `flat_dt`, code does `_fill(..., lasts[sym], ...)` for EOD flat.  
  **Wrong behavior:** raises `KeyError: 'AAPL'` before submitting close. Positions remain open, violating “flat by 15:30” and can continue trading next ticks if scheduler retries inconsistently.

### 6) Opening range window can include post-window bars depending on bar timestamp convention
- **File/Function:** `src/tradebot/fastarm.py::opening_range`
- **Claim 6 (MED):** `window = bars[bars["t"] < or_end]` assumes `t` is the bar *start* time. If Alpaca’s `timestamp` is bar *end* time (common for aggregated bars), then the bar covering 10:00–10:05 would have `t=10:05`, and your `< or_end` would **exclude** the last OR bar (or conversely include an extra bar, depending on convention). This is a concrete look-ahead/stale-window risk because the OR high/low is foundational to entries/exits.
- **Failure scenario:**  
  **Inputs:** OR ends 10:00. Data provider stamps the 9:55–10:00 bar as `10:00`.  
  **Wrong behavior:** `< 10:00` drops that bar, computing OR levels on only 25 minutes, changing triggers and potentially allowing entries that shouldn’t happen or missing ones that should.

### 7) Fast/movers arms ignore global halt file; slow arm honors it
- **File/Function:** `src/tradebot/fastarm.py::run_fast_once`
- **Claim 7 (HIGH):** The intraday arms do not check `cfg.risk.halt_file` / `cfg.halt_path` at all. They only look at `st.get("halted")`, which is arm-local. A global halt (e.g., slow arm drawdown triggers `.halt`) will not stop fast/movers from trading.
- **Failure scenario:**  
  **Inputs:** slow arm hits drawdown and writes `.halt`. Immediately afterward, scheduler runs `run_fast_once` for the fast arm.  
  **Wrong behavior:** fast arm continues placing orders because it never checks `.halt`, violating “presence of this file stops all trading”.

### Overall risk assessment: **HIGH — multiple concrete paths allow trading past halts/market-close and can leave positions open due to runtime exceptions, with inconsistent risk enforcement across arms.**
