## Findings

### 1) `src/tradebot/risk.py` — `RiskManager.book_equity`
**Claim 1 (HIGH): drawdown kill-switch can be bypassed by “account reset” re-anchoring that erases real losses.**  
**Scenario:**  
- Config: `risk.book_cap=50`, `risk.max_drawdown_pct=10`.  
- State: `book_baseline=100000` (slow arm’s legacy $100k paper baseline). `high_water_mark` already established near 50 (because `book_equity` previously returned ~50).  
- Broker equity (`raw`) falls due to actual trading loss to `raw=90` (still a real loss, just huge relative to the capped book concept).  
- Condition triggers: `raw < baseline*0.5` (90 < 50000) and `raw <= cap*2` (90 <= 100) ⇒ baseline is reset to 90.  
- `book_equity` returns `min(50 + (90-90), 90)=50`.  
**Wrong behavior:** the bot’s capped equity snaps back to $50 even though the account suffered an enormous loss relative to the prior baseline; drawdown computed off `book_equity` will *not* reflect the loss, so the halt may never trigger.

### 3) `src/tradebot/run.py` — `run_once` (halt path)
**Claim 3 (HIGH): kill-switch flatten orders can violate `max_order_notional` by submitting full position market values with no order-level risk filter.**  
**Scenario:**  
- Config: `risk.max_order_notional=30`.  
- Positions: `{"SPY": 45.00}` market value long.  
- Drawdown triggers (`check_drawdown` returns True).  
- Flatten list creates order `{side:"sell", notional:45}` and submits directly via `broker.submit(o)` without passing through `risk.filter_orders`.  
**Wrong behavior:** a liquidation order exceeds the configured per-order notional cap. If the cap is meant to be hard (as config suggests), this violates it; if Alpaca rejects big orders, bot may fail to flatten and still logs “killed”.

### 4) `src/tradebot/risk.py` — `RiskManager.filter_orders`
**Claim 4 (MED): `max_positions` enforcement is wrong; it counts buy *orders* not resulting positions, so it can allow exceeding `max_positions`.**  
**Scenario:**  
- `max_positions=2`. Current holdings already 2 symbols (e.g., SPY, QQQ).  
- Rebalance intends to rotate: sell SPY, buy IWM, buy TLT (temporarily needs 3 positions intraday or if sells fail).  
- `strategy.diff_orders` produces sells first then two buys. `filter_orders` sees `len(buys)=2` (≤2) and approves both buys even though after partial fills / rejected sell, you can end up with 3 held symbols.  
**Wrong behavior:** more concurrent positions than allowed can occur because the check ignores existing holdings and execution uncertainty.

### 5) `src/tradebot/fastarm.py` — `run_fast_once` (broker mode positions & flattening)
**Claim 5 (HIGH): live-mode flatten/exit paths can crash due to missing `qty` in broker positions detail, preventing stops/kill-switch/eod flatten from working.**  
**Scenario:**  
- `_positions(f, broker, st)` in live mode returns `broker.positions_detail()` dict like `{"AAPL":{"qty":1.0,"entry_px":...,"market_value":...}}`.  
- On any exit path (overnight flatten / drawdown_kill / daily_loss_stop / eod_flat / or_low_stop), code does `pos["qty"]`. OK.  
- But on price selection it does `pos.get("last_px", pos["entry_px"])`. In live mode, `pos` has no `"last_px"` key, so it falls back to `"entry_px"` (exists). OK.  
- The real crash is earlier: `lasts.get(sym, pos.get("last_px", pos["entry_px"]))` assumes `pos["entry_px"]` exists; Alpaca can return avg_entry_price as `"0"` for some states (or missing if API changes), and your own `positions_detail()` hard-casts `float(p.avg_entry_price)`—if Alpaca returns `None`/"" it throws before risk logic executes.  
**Wrong behavior:** a data edge (missing avg_entry_price) can crash the arm before flattening on kill switch / end-of-day. This is a concrete unhandled exception path in the critical exit logic chain (no try/except around `positions_detail` casting).

### 6) `src/tradebot/fastarm.py` — `run_fast_once` (live broker mode) + `src/tradebot/broker.py` — `AlpacaBroker.close`
**Claim 6 (HIGH): sell/flatten in broker mode always uses `broker.close(sym)` which always returns `side:"sell"`; shorts would be handled incorrectly.**  
**Scenario:**  
- Account is short (possible if broker enables shorting or via corporate actions/borrow quirks): `qty=-1`.  
- `run_fast_once` tries to flatten with `_fill(..., side="sell", ...)` regardless; `_fill` broker-mode ignores `px/qty` and calls `broker.close(sym)`.  
- `AlpacaBroker.close` returns `{"side":"sell" ...}` even though closing a short is effectively a buy-to-cover.  
**Wrong behavior:** ledger and any downstream logic treating `"side"` as economic direction will be wrong; more importantly, upstream logic in `run.py` explicitly mentions “shorts included” but fastarm has no such handling—if `close_position` fails for shorts in some regimes, the bot has no alternate path.

### 7) `src/tradebot/signals.py` — `momentum_12_1`
**Claim 7 (MED): lookback sufficiency check ignores `skip`, can index past the available history and crash or compute wrong momentum.**  
**Scenario:**  
- `lookback=252`, `skip=21`.  
- `len(closes)=253` passes `if len(closes) < lookback+1` (253 < 253 is False).  
- Then `end = closes.iloc[-(skip+1)]` requires at least 22 elements (ok), but `start = closes.iloc[-(lookback+1)]` uses `-253` which is valid for length 253 (ok).  
- Now reduce to `len(closes)=252` (common if data API returns exactly lookback): fails check and returns None (fine).  
- The actual bug: requirement should be `len(closes) >= lookback + skip + 1` if you intend “exclude the most recent skip days *within the same lookback window*”. Current math uses `start` at `-(lookback+1)` and `end` at `-(skip+1)` which makes the effective holding period shorter than declared when history is limited, and the sufficiency flag (`enough_data`) can be True when the skip window effectively cannibalizes the lookback window.  
**Wrong behavior:** momentum is not the pre-registered 12-1 definition unless you have substantially more than `lookback+1` points; strategy may trade on a different signal than specified.
