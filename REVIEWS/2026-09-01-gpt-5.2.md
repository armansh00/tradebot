### Findings

**src/tradebot/risk.py — RiskManager.filter_orders**
1) **Claim (HIGH): `max_positions` can be bypassed by splitting buys into multiple orders for the same symbol.**  
   **Why:** It enforces `max_positions` by counting buy *orders* (`len(buys)`), not resulting distinct positions/symbols. It also keys off `side=="buy" and to_notional>0`, which can still be true for multiple incremental buys of the same symbol.  
   **Failure scenario:**  
   - Config: `risk.max_positions=2`  
   - Existing positions: `{}`  
   - Incoming orders from some strategy/bug:  
     ```
     [{"symbol":"SPY","side":"buy","notional":10,"from_notional":0,"to_notional":10},
      {"symbol":"SPY","side":"buy","notional":10,"from_notional":10,"to_notional":20},
      {"symbol":"QQQ","side":"buy","notional":10,"from_notional":0,"to_notional":10}]
     ```  
   - `len(buys)=3` so one gets rejected, but **you can craft the list so that the rejected one is QQQ**, leaving **two SPY buys approved**. Net result: you end up with **1 position**, but the intent of the cap (limit concurrent exposures) is not the real issue—more importantly, if you instead split across **3 symbols with only 2 buy orders passing due to ordering effects**, you can get **>2 positions over multiple cycles** because this function does not consider *current holdings* + *approved new symbols*, only the count of buy orders in this batch.

2) **Claim (MED): `max_positions` ignores current positions; can approve buys that take you above the cap.**  
   **Why:** It counts only buy orders in the approved batch and compares to `cfg.risk.max_positions`. If you already hold 2 symbols and get 1 additional buy (e.g., due to stale positions input, or another module), it will approve it because `len(buys)=1` (≤2).  
   **Failure scenario:**  
   - Config: `max_positions=2`  
   - Actual broker positions already include 2 symbols (e.g., SPY and QQQ), but the strategy generates an extra buy for IWM due to mismatched position snapshot.  
   - Orders: `[{"symbol":"IWM","side":"buy","notional":10,"from_notional":0,"to_notional":10}]`  
   - `filter_orders` approves it → **3 positions** possible.

**src/tradebot/risk.py — RiskManager.book_equity**
3) **Claim (HIGH): baseline “reset” condition can erase real losses and prevent drawdown halt (book-cap rebaseline bypass).**  
   **Why:** Re-anchors baseline when `(raw < baseline*0.5 and raw <= cap*2)`. That can occur from real trading losses if the underlying account equity falls hard (especially if the account is small or multiple losses compound). Re-anchoring raises the computed `book_equity` by redefining the baseline lower, muting drawdown and potentially avoiding the kill switch.  
   **Failure scenario:**  
   - `cap=50`, prior `book_baseline=100000` (slow arm on the old $100k paper, per config comment).  
   - A genuine large loss drops `raw` to `90` (still possible if the “slow” arm mistakenly traded larger before cap enforcement elsewhere, or if external/manual activity hit the account).  
   - Condition: `raw=90 < 50000` and `raw=90 <= 100` → true → baseline resets to 90.  
   - Now `book_equity = min(50 + (90-90)=50, raw=90)=50`, **masking the fact that the account lost ~99.91%** and making drawdown logic operate on the artificial capped book, not the true equity path.

**src/tradebot/run.py — run_once**
4) **Claim (HIGH): drawdown “flatten” orders can exceed `max_order_notional` and bypass order-level caps.**  
   **Why:** On drawdown breach, it builds `flatten` orders with `notional=abs(mv)` for each position and submits them directly—no `risk.filter_orders`, no per-order cap enforcement.  
   **Failure scenario:**  
   - `max_order_notional=30`  
   - Positions include `SPY: 45` market_value (or any >30).  
   - Drawdown triggers; flatten creates order `{notional:45}` and submits it anyway → violates cap.

5) **Claim (MED): kill-switch flatten can fail to close positions due to notional-vs-qty mismatch.**  
   **Why:** Flatten uses `broker.submit()` with `notional=abs(mv)` for both selling longs and buying to cover shorts. For shorts, buying by notional may not fully cover if price moved between `positions()` snapshot and execution; also Alpaca market orders by notional may be unsupported/behave differently on buy-to-cover (implementation-dependent). There’s no post-check that positions are actually flat before returning `killed`.  
   **Failure scenario:**  
   - Short position exists: `positions()` reports `mv=-31.00`.  
   - Flatten sends `{"side":"buy","notional":31.00}`; if price spikes up immediately, $31 notional buys fewer shares than needed → **short remains**, but function logs `halted=True` and returns `"killed"`.

**src/tradebot/fastarm.py — run_fast_once**
6) **Claim (HIGH): broker-mode exits can crash on missing `qty` field, leaving positions unflattened despite kill/stop logic.**  
   **Why:** `_positions()` in live mode returns `broker.positions_detail()` which provides `qty`, `entry_px`, `market_value` but **not `last_px`**. The code often falls back to `pos.get("last_px", pos["entry_px"])` (fine) but the real issue is elsewhere: `_fill()` in live mode ignores `qty` for sells (uses `broker.close(sym)`), but callers still pass `pos["qty"]`. If Alpaca returns positions with `qty` as a string or missing during race conditions (position just closed), `pos["qty"]` access can KeyError or type issues elsewhere (e.g., ledger rounding). There’s no try/except around these flatten loops.  
   **Failure scenario:**  
   - During `daily_loss_stop` loop, `_positions()` returns a dict missing `qty` for one symbol due to an API hiccup/partial response.  
   - Access `pos["qty"]` raises KeyError → function aborts mid-loop → some positions remain open; kill/stop not enforced.

7) **Claim (HIGH): intraday arms ignore the global halt file; trading can continue after the main kill switch should have stopped everything.**  
   **Why:** Slow arm respects `risk.halt_file` via `RiskManager.halted()`. Fast arm uses only `st.get("halted")` and never checks `cfg.risk.halt_file`/`.halt` presence.  
   **Failure scenario:**  
   - `.halt` file exists (e.g., slow arm hit drawdown and wrote it).  
   - Scheduler continues calling `run_fast_once` every 30 minutes.  
   - Fast arm sees `st["halted"]` is False and proceeds to trade → **kill-switch bypass across arms**.

8) **Claim (MED): OR window can include future bars if the data feed returns bars beyond “now” (look-ahead).**  
   **Why:** `bars = broker.intraday_5min(universe)` fetches bars for the entire session window (09:30–16:00) in `AlpacaBroker.intraday_5min` (end fixed at 16:00). If Alpaca’s API returns completed bars later in the day, that’s fine; but if the call is made at (say) 10:05, the returned dataset *should* only include bars up to ~10:00. If the provider occasionally includes a bar timestamped slightly in the future (clock skew, delayed/aggregated updates), `lasts` uses `df["c"].iloc[-1]` (latest bar in response), and entry/exit comparisons use that—can become look-ahead.  
   **Failure scenario:**  
   - At 10:01 ET, API response mistakenly includes a 10:05 bar with close=510.  
   - `lasts[sym]=510` used for breakout check (`lasts > hi`) before that price was actually observable → enters early using future info.

**src/tradebot/compare.py — _daily_equity**
9) **Claim (LOW): daily equity alignment can silently mix days due to inconsistent day keys between arms.**  
   **Why:** For `fast_run`, it uses `r.get("day", r["ts"][:10])`. For `run` it always uses `ts[:10]` (UTC date). Fastarm’s `day` is derived from broker ET date; slow arm’s ledger timestamp is UTC. Around midnight UTC (evening ET), these can differ, causing the “same trading day” to be treated as different days, impacting overlap windows, drawdown stats, and evaluation week counts.  
   **Failure scenario:**  
   - A slow-arm `run` at 23:30 ET logs `ts` as next-day UTC date.  
   - Fast arm logs `day` as ET date (previous).  
   - Comparison misaligns series → overlap window and stats computed on mismatched days.
