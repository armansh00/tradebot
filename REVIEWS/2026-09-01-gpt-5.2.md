### src/tradebot/risk.py — `RiskManager.book_equity`
1) **Claim:** Book-cap rebaseline can erase real losses and bypass the drawdown kill switch.  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `risk.book_cap=50`, `max_drawdown_pct=10`. Baseline previously set at `baseline=100000` (slow arm sits on legacy $100k paper account as described).  
- Then a real trading loss occurs inside that account and `broker.equity()` drops to `raw=90,000` (a 10% loss that should halt).  
- Code path: `raw < baseline*0.5` is `90000 < 50000` False → no rebaseline; OK in this example. But if the account suffers a larger (still-real) loss to `raw=40,000`:  
  - `raw < baseline*0.5` is `40000 < 50000` True **and** `raw <= cap*2` is `40000 <= 100` False → no rebaseline; still OK.  
  - The dangerous case is when baseline is small due to an earlier rebaseline/reset heuristic: if baseline ever gets anchored near the cap (e.g., after a genuine reset or mis-detected reset), then subsequent real losses can be “absorbed” by `cap + (raw-baseline)` and you are effectively trading on a re-anchored book.  
- Concretely: baseline anchored at `raw=80` due to the heuristic on some prior run (see below). Later equity falls from `80` to `72` (a **10% drawdown**) but `book_equity()` returns `min(cap+(72-80), 72)=min(42,72)=42`. That’s a **47.5%** apparent drawdown from the capped book high-water if high-water was 50, but the *slow-arm* HWM is kept in the shared `state_path` (see next finding) and can be rewritten; this interaction can prevent consistent halting behavior.  
**Why this is a defect you can hit:** the “reset detection” condition `raw < baseline*0.5 and raw <= cap*2` is extremely specific and depends on prior baseline values; if baseline is ever wrong (including via state corruption or cross-arm sharing), the cap math can meaningfully change equity used by `check_drawdown()` and can allow trading on a “fresh” baseline rather than honoring cumulative loss.

### src/tradebot/risk.py — `_state()` / `_save_state()` / `check_drawdown()`
2) **Claim:** Single shared `state_path` high-water mark makes kill switch non-isolated across accounts/arms; one arm can raise another arm’s HWM and delay/avoid a halt.  
**Severity:** HIGH  
**Failure scenario:**  
- You run slow arm (legacy $100k) and it writes `high_water_mark=100000` to the shared `cfg.state_path`.  
- Then you run an intraday arm or another account that uses the same `RiskManager`/same `cfg.state_path` (or a future refactor mistakenly reuses it). Its `equity` is ~$50.  
- `check_drawdown(equity=50)` sets `hwm=max(100000,50)=100000`, `dd_pct≈99.95%` ⇒ immediate halt and forced flattening on an account that didn’t draw down. Or the reverse: a $50 arm runs first and sets HWM=50, then the slow arm’s drawdown is computed off 50 until it updates, producing inconsistent halt timing depending on run order.  
- Net: kill-switch becomes order-dependent and can either trigger falsely or fail to trigger when expected (if HWM is overwritten downward by another run—possible if `equity` is NaN or negative? you guard only `hwm <= 0`, not NaN).  
This is a concrete cross-book state bleed: the state file isn’t namespaced per account/arm anywhere in `RiskManager`.

### src/tradebot/risk.py — `filter_orders`
3) **Claim:** `max_positions` enforcement is wrong: it counts buy orders, not resulting positions, so it can exceed the position cap.  
**Severity:** HIGH  
**Failure scenario:**  
- Current positions: `{"SPY": 25, "QQQ": 25}` (already 2 positions, at cap).  
- Targets include adding a new symbol `IWM` by selling SPY down and buying IWM: orders become `sell SPY`, `buy IWM` (possibly also `buy QQQ` depending).  
- `buys = [o for o in approved if side=="buy" and to_notional>0]` includes the IWM buy. `len(buys)=1` so it passes, **even though after execution you may hold 3 symbols** (if SPY sell is partial and doesn’t go to 0, or if sell fails/rejects).  
- Even more direct: if you currently hold 0 positions and you generate 2 buy orders to 2 symbols (allowed), but the broker rejects one sell that was supposed to free cash in a rebalance day, buys still go through—position count can exceed cap because you never check *current holdings + new nonzero targets* nor execution contingencies.  
This violates your risk requirement “more positions than allowed”.

### src/tradebot/fastarm.py — `_fill` in live mode (broker)
6) **Claim:** Live-mode sells can bypass intent-id idempotency and can submit repeated closes on retries.  
**Severity:** MED  
**Failure scenario:**  
- For buys, you use `client_order_id=intent_id(...)` and broker suppresses duplicates.  
- For sells, you call `broker.close(sym)` with **no client_order_id**. If a retry occurs after a network drop (the exact scenario you defend against in `intent_id` docstring), the second invocation is a new request; Alpaca may accept/queue it or return an error depending on timing, but you do not have broker-enforced idempotency.  
- Concrete outcome: duplicated close attempts can lead to “position not found” errors or unexpected order churn; more importantly for risk: your “flatten” path (drawdown/eod) can fail idempotency and produce inconsistent state/ledger vs actual broker actions.

### src/tradebot/fastarm.py — position cap and order notional caps missing
7) **Claim:** Intraday arms ignore global risk caps entirely (`max_order_notional`, `max_positions`), so caps can fail.  
**Severity:** HIGH  
**Failure scenario:**  
- Config global `risk.max_order_notional=30`, `risk.max_positions=2`.  
- Fast arm uses its own `top_k` and `budget_per_slot=equity/top_k`; if equity grows (or if you later change start_cash), it can submit buys larger than $30 because there is no check against `cfg.risk.max_order_notional`.  
- Similarly, if broker returns additional positions (e.g., dust or partially closed positions), `len(held)` can be > `top_k` but code still computes `slots = top_k - len(held)` negative and doesn’t force-liquidate extras unless stop conditions happen; there’s no hard enforcement equivalent to `risk.filter_orders`.  
This is an explicit risk-cap failure state for the intraday arms.

### src/tradebot/fastarm.py — daily loss stop and drawdown equity math in live mode
8) **Claim:** Equity used for stops can be stale/inconsistent because `_mark_equity` in live mode uses `broker.equity()` (account equity) while positions/lasts are from `intraday_5min` bars, and costs accrue separately; drawdown can be missed or falsely triggered depending on timing.  
**Severity:** MED  
**Failure scenario:**  
- At tick, bars’ last close lags the live quote, but `_mark_equity` ignores `lasts` in live mode entirely and relies on broker equity snapshot.  
- You then execute orders and immediately re-check (later in function) equity again, but broker equity may not reflect fills yet (paper API latency), while `cost_accrued` is applied immediately.  
- Outcome: daily loss stop (`day_pnl_pct`) and drawdown (`dd`) can fail to trigger when they should (fills happened but equity not updated), allowing additional trades after a loss stop boundary.

### src/tradebot/fastarm.py — opening range data look-ahead
9) **Claim:** `opening_range()` uses all bars with timestamp `< or_end`, but you fetch the entire day’s bars (`intraday_5min(universe)` from 9:30 to 16:00) each tick. If the data API returns future bars early (common in some backfill/replay or caching paths), you get look-ahead.  
**Severity:** MED  
**Failure scenario:**  
- At 10:05 ET, broker data endpoint mistakenly includes bars through 16:00 (or through 10:30) due to caching / requesting full-day range with end=16:00.  
- `lasts` becomes the final close (`df["c"].iloc[-1]`) i.e., end-of-day close, and candidate selection uses that “last” to compare to OR high—full look-ahead.  
This is concrete because `intraday_5min` explicitly requests `end=16:00` regardless of `now`, and `run_fast_once` assumes the returned df is only up to “now” but never enforces it.

### src/tradebot/broker.py — `intraday_5min`
10) **Claim:** Hardcoded `end = 16:00` enables stale/future data ingestion (feeds look-ahead into fastarm).  
**Severity:** MED

No filtering by `now` exists in `run_fast_once` except for opening-range high/low; `lasts` always uses the last bar in the returned data, which can be post-decision.
