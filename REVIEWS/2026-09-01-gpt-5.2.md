### Findings

**src/tradebot/risk.py — `RiskManager.filter_orders`**  
1) **Claim (HIGH): max_positions is enforced on “buy orders count”, not on resulting open positions; you can exceed `risk.max_positions` without any rejected order.**  
**Failure scenario:**  
- Config: `max_positions=2`.  
- Current positions: `{"SPY": 25.0}` (1 open position).  
- Targets want 2 *additional* positions and keep SPY: targets `{"SPY": 25.0, "QQQ": 12.5, "IWM": 12.5}`.  
- `strategy.diff_orders` generates only two buys (`QQQ`, `IWM`) because SPY delta is 0 → no order.  
- `filter_orders` sees `len(buys)=2` which is `<= max_positions`, so both buys pass.  
- After execution you hold **3 positions** (SPY, QQQ, IWM), violating `max_positions=2`.

**src/tradebot/risk.py — `RiskManager.filter_orders`**  
2) **Claim (MED): order notional cap checks `o["notional"]` only, but flatten/close logic elsewhere can create orders whose executed notional differs materially (market order, broker close), so risk cap can be bypassed in practice.**  
**Failure scenario:**  
- A position has market_value estimate `mv=29.90` at snapshot time; flatten order uses `notional=29.90` and passes cap `30`.  
- Price gaps up before execution; broker executes a market sell closer to `35` notional equivalent (shares * price).  
- Bot intended “no single order above $30”, but actual execution breaches the cap. (This is structural: notional-at-submit != notional-at-fill; and `broker.close()` in fastarm bypasses notional entirely.)

**src/tradebot/run.py — `run_once`**  
3) **Claim (HIGH): kill switch flatten orders are not risk-checked, so the bot can submit flatten orders larger than `max_order_notional`, contradicting “Checked before every order”.**  
**Failure scenario:**  
- `risk.max_order_notional=30`.  
- Positions: `{"SPY": 50.00, "QQQ": 50.00}` (possible if risk rules were different earlier, manual intervention, broker drift, or stale position sizing).  
- Drawdown triggers; `flatten` creates orders with `notional=50` each.  
- Code submits both directly (`broker.submit(o)`), never calling `risk.filter_orders`.  
- If you truly require “no order above $30”, this violates it exactly when the system is under stress.

**src/tradebot/run.py — `run_once`**  
4) **Claim (MED): drawdown check uses *pre-trade* equity only; losses incurred by orders placed in this same run can exceed drawdown limit without triggering halt until the next scheduled run (which might be next day).**  
**Failure scenario:**  
- HWM = 50.00, current equity at start of run = 46.00 (8% DD, below 10% limit) → no halt.  
- Bot submits buys; intraday crash drops equity to 44.00 (12% DD) shortly after.  
- No further checks happen this day (designed “once per trading day”), so bot continues holding and does not flatten/halt at the moment it should have per stated rule.

**src/tradebot/fastarm.py — `run_fast_once` (new day handling)**  
5) **Claim (HIGH): “overnight flatten” can fail silently in broker mode and the arm proceeds as if flat; `_fill` returns False on rejection but caller ignores it, so positions can remain overnight and also corrupt subsequent risk logic (slots, stops, trade caps).**  
**Failure scenario:**  
- `new_day` true and account still holds `AAPL` (scheduler missed yesterday’s eod flatten).  
- Broker rejects `close_position` (e.g., trading halt, short locate issue, API transient) so `_fill(..., "sell", ...)` returns False.  
- Caller does not check return value; it still resets `trades_today`/`stopped_today` and continues.  
- Result: you carry an overnight position despite the invariant “flat overnight”; also `slots = top_k - len(held)` later still sees it (from broker), potentially preventing intended entries, while stop metadata (`or_low`) may be missing/incorrect.

**src/tradebot/fastarm.py — `run_fast_once` (kill switch + order sizing)**  
6) **Claim (MED): intraday arms have no `max_order_notional` / book-cap style enforcement at all; they can submit a single order near full equity (e.g., ~$25 per slot) regardless of global `risk.max_order_notional=30`, and if configs diverge (larger start_cash later) this becomes an uncapped notional path.**  
**Failure scenario:**  
- Later you change only `fast.start_cash` to 500 (or account grows) but forget to add/order-cap logic here.  
- `budget_per_slot = equity/top_k` could be $250, and `_fill` submits a $250 notional buy.  
- Nothing in `fastarm.py` consults `cfg.risk.max_order_notional` or any per-arm max notional, so the global cap is trivially bypassed for these arms.

**src/tradebot/fastarm.py — `run_fast_once` (opening range / stale data)**  
7) **Claim (MED): opening range computation can include post-OR bars depending on how Alpaca timestamps 5-min bars (bar “timestamp” often denotes bar start); using `bars["t"] < or_end` with `or_end=10:00` will include the 9:55 bar (covers 9:55–10:00) and exclude the 10:00 bar (10:00–10:05). If timestamps are bar *end* instead, it flips. This ambiguity can create look-ahead or truncation.**  
**Failure scenario:**  
- If Alpaca timestamps bars at bar *end* (common in some feeds): the bar labeled `10:00` represents trades from 9:55–10:00. Your filter `t < 10:00` **excludes** that bar, shrinking the OR window to 9:30–9:55 (25 minutes), changing hi/lo and triggering different entries.  
- If timestamps are bar *start*: bar labeled `9:55` covers 9:55–10:00 and is included, which is correct; but you are relying on a convention not asserted anywhere.

**src/tradebot/compare.py — `compare_report` / `_arm_row`**  
8) **Claim (LOW): cost accounting double-counts in broker mode for fast/movers. You accrue `st["cost_accrued"]` (used in equity), and `_arm_row` also sums `modeled_cost` from `fast_order` records; report “Costs paid” may not match the net equity series depending on how ledger equity is computed/recorded.**  
**Failure scenario:**  
- Broker mode: equity written in `fast_run` is already `broker.equity() - cost_accrued`.  
- Report: “Costs paid” separately sums `modeled_cost` from orders; if a reader subtracts costs again mentally (or another script uses both), performance is understated. Not a trading defect, but a concrete money-math/reporting inconsistency risk.

**src/tradebot/ledger.py — `Ledger.write`**  
9) **Claim (MED): ledger writes are not atomic; a crash mid-write can leave a truncated JSON line that makes `Ledger.read()` throw and potentially break idempotency/halts/reports.**  
**Failure scenario:**  
- Process dies while writing a line (power loss).  
- Next run: `read()` hits a truncated line; `json.loads` raises, causing the whole run to error.  
- Consequence: bot may stop running without writing a halt, and `last_run_date()` idempotency check cannot function (because reading fails).

Overall risk assessment: **HIGH — multiple concrete paths allow exceeding position/risk caps or failing to flatten/halt reliably under stress.**
