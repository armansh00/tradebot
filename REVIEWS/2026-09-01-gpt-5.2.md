### src/tradebot/risk.py — `RiskManager.filter_orders`
1) **Claim (HIGH): max_positions cap can be bypassed by target-delta buys that “top up” existing positions.**  
   **Why:** It counts `buys = [o for o in approved if o["side"] == "buy" and o["to_notional"] > 0]` and rejects if `len(buys) > max_positions`. That’s not the same as “resulting number of non-zero positions after all orders.” It’s “number of buy orders that end positive,” which can be smaller.  
   **Failure scenario:**  
   - Config: `max_positions=2`.  
   - Current positions: `{"SPY": 10, "QQQ": 10}` (2 positions already).  
   - Strategy targets: `{"SPY": 15, "QQQ": 15, "IWM": 5}`.  
   - `diff_orders` produces 3 buy orders (SPY+5, QQQ+5, IWM+5). `len(buys)=3`, so it rejects the 3rd buy (good).  
   But reverse the deltas:  
   - Current positions: `{"SPY": 15, "QQQ": 0, "IWM": 15}` (2 positions held: SPY & IWM).  
   - Targets: `{"SPY": 15, "QQQ": 15, "IWM": 0}`.  
   - Orders: sell IWM (to 0), buy QQQ (to 15). `len(buys)=1` so it approves buy QQQ. If sell fails/rejects at broker (or is blocked by short-sale/close failure), the buy still goes through, leaving **3 positions** (SPY, IWM, QQQ) and violating `max_positions`. There is no post-trade enforcement.

2) **Claim (MED): order notional cap can be exceeded via broker “close” path (flattening) because `filter_orders` is never applied there.**  
   **Why:** In `run.py`, on drawdown kill it constructs `flatten` orders and submits directly (`broker.submit(o)`), skipping `filter_orders`. Those orders use `notional = abs(mv)` where `mv` is market_value. That can exceed `max_order_notional`.  
   **Failure scenario:**  
   - `max_order_notional=30`.  
   - Position: SPY market_value = $45.  
   - Drawdown triggers. Bot submits sell notional 45 anyway. Risk cap is not enforced in the only moment it matters (forced flatten).

### src/tradebot/run.py — `run_once`
3) **Claim (HIGH): kill-switch can place trades after it should have fired due to equity/book_equity mismatch vs actual account equity.**  
   **Why:** Drawdown check is run on `equity = risk.book_equity(broker.equity())`. With `book_cap=50` on a large account, drawdown is computed on the **capped synthetic equity**, not the real account equity. If real equity collapses but still doesn’t force `book_equity` low enough (because of baseline logic), drawdown may not trigger though the real account is in distress; conversely it can trigger late/early vs actual.  
   **Failure scenario:**  
   - Baseline anchored at raw=100000. cap=50.  
   - Real equity drops to 90000 (a 10% drawdown). `book_equity = min(50+(90000-100000), 90000)=min(-9950,90000)=-9950` rounded → negative equity.  
   - `check_drawdown` computes hwm vs negative number; dd becomes >100% and triggers halt/flatten with nonsensical equity, **but** the flatten notional is based on positions from the broker (real), and can be huge, bypassing caps (ties into finding #2). This is an unstable kill path driven by synthetic equity math, not real equity.

4) **Claim (MED): idempotency “once per day” uses UTC date; trading day is ET—can double-run or skip on ET day boundaries.**  
   **Why:** `today = datetime.now(timezone.utc).date().isoformat()`, and `ledger.last_run_date()` also slices UTC timestamps. If the job runs late evening ET (after 20:00 ET = next day UTC), it will consider it a new “day” and run again within the same ET trading day (or vice versa around midnight UTC).  
   **Failure scenario:**  
   - Run at 19:30 ET on a trading day (23:30 UTC) → `today=YYYY-MM-DD`.  
   - Run again at 21:00 ET (01:00 UTC next day) while market still open (depending on broker clock / extended hours config) or due to a misreported `market_open()` → bot treats as a new day and rebalances twice.

### src/tradebot/fastarm.py — `run_fast_once`
5) **Claim (HIGH): in broker mode, `_positions()` returns a dict without `last_px`, but multiple paths assume it exists → crash or wrong pricing on forced sells; can bypass kill/flat rules by exception.**  
   **Why:** `broker.positions_detail()` returns `{"qty","entry_px","market_value"}` only. Code repeatedly does `pos.get("last_px", pos["entry_px"])` (fine) but also uses `lasts.get(sym, pos.get("last_px", pos["entry_px"]))` in new_day flatten; and later, in fast_run ledger positions: `p["qty"] * lasts.get(s, p.get("last_px", 0))` which becomes `qty*0` if lasts missing, understating exposure.  
   **Failure scenario:**  
   - Broker data hiccup: `bars` missing for a held symbol ⇒ `lasts` lacks that symbol.  
   - End-of-day flatten loop uses `lasts[sym]` (not `.get`) in several places (daily_loss_stop, eod_flat) → `KeyError` aborts function before `_save_state`, leaving `stopped_today`/`halted` not persisted. Next tick continues trading despite having hit stop/flat conditions.

6) **Claim (HIGH): opening range uses all bars returned, with no guard against including future bars relative to `now`; look-ahead if broker returns the full-day bar set.**  
   **Why:** `bars = broker.intraday_5min(universe)` is called with no `end=now` constraint; `opening_range` filters by `t < or_end` only, not `t <= now`. If the data source returns bars beyond current time (common in replay/backfill modes or if the API call returns “latest completed bars up to end-of-session”), the OR high/low includes information not known at decision time.  
   **Failure scenario:**  
   - At 10:05 ET, API returns 5-min bars through 16:00 (or through 10:30+ due to caching).  
   - OR window ends 10:00 for `or_minutes=30`. If bars include 9:30–10:00 plus later corrections/backfilled bars, `opening_range` may incorporate revised highs/lows that were not available at 10:00, changing breakout eligibility and stop levels.

7) **Claim (MED): daily-loss-stop can be bypassed in broker mode because “equity” is netted by `cost_accrued`, but `day_start_equity` is set from `_mark_equity` that can be computed before `cost_accrued` updates for fills in the same tick.**  
   **Why:** Within one invocation, the sequence can be: set `day_start_equity`, then trade, then accrue costs, then re-mark. But the daily stop check happens **before** entries/exits in the ORB block, using equity computed before any new fills in this tick. A large loss realized by fills in this tick won’t trigger the daily stop until the next tick.  
   **Failure scenario:**  
   - At 10:00, enters positions; immediate adverse move and stop should fire; but daily stop check already passed and is not re-evaluated after trades. Bot continues to hold until next tick, exceeding intended intraday loss discipline.

8) **Claim (MED): halted state is arm-local only; ignores global `.halt` file risk halt.**  
   **Why:** `run_fast_once` checks only `st.get("halted")` and never checks `cfg.risk.halt_file`/`RiskManager.halted()`.  
   **Failure scenario:**  
   - Slow arm triggers drawdown and writes `.halt`.  
   - Fast arm continues trading because its own state `halted` is False and it doesn’t consult the global halt file.

### src/tradebot/broker.py — `AlpacaBroker.intraday_5min`
9) **Claim (LOW): half-days not handled; hardcoded 16:00 end can request bars beyond session and enable the look-ahead issue in #6.**  
   **Why:** Session times are hardcoded 9:30–16:00 regardless of calendar; `session_today()` exists but is not used here.  
   **Failure scenario:**  
   - Half-day close 13:00 ET. Requesting until 16:00 can return empty/odd data; OR logic and flat timing may misbehave, potentially leaving positions open because bars/lasts are inconsistent.
