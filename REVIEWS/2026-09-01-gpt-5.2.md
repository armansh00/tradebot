### src/tradebot/risk.py — `RiskManager.book_equity`
1) **Claim:** Book-cap “reset” condition can erase real losses and bypass drawdown halt (re-anchors baseline after a loss).  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `risk.book_cap=50`, `max_drawdown_pct=10`.  
- State: `book_baseline=100000` (slow arm on the legacy $100k paper account, as described in config). `high_water_mark` previously updated near the capped equity (~$50).  
- Market loss / manual intervention / API glitch drops `broker.equity()` (`raw`) to `90` (a real loss vs baseline, but still `<= cap*2` is false; so no re-anchor) — ok.  
- But if `raw` drops to `95`? still no. Now assume the account is actually reset by Alpaca to **$80** (or a withdrawal / correction / fee), i.e. `raw=80`. Condition: `raw < baseline*0.5` (80 < 50k) **and** `raw <= cap*2` (80 <= 100) => **True**, so baseline is reset to 80.  
- Immediately after reset, `book_equity = min(cap + (raw-baseline), raw) = min(50 + 0, 80) = 50`.  
**Wrong behavior:** A large equity collapse that is not a “dashboard reset to ~$50” but still happens to land under `cap*2` causes baseline to re-anchor, preventing the drawdown logic from ever “seeing” the full loss path vs the prior baseline regime. This is a kill-switch bypass if raw equity can fall into that range for reasons other than a true reset (withdrawals/fees/corrections/manual liquidation/misreporting), because the cap-book equity is instantly restored to 50 and the slow-arm drawdown trigger becomes relative to the new baseline, not the old high-water mark regime.

This is exactly a “halt/high-water mark silently forgotten” failure mode.

### src/tradebot/risk.py — `RiskManager.filter_orders`
3) **Claim:** `max_positions` enforcement is wrong: it counts only **buy orders in this batch**, not resulting total positions, so you can exceed `risk.max_positions`.  
**Severity:** HIGH  
**Failure scenario:**  
- `risk.max_positions=2`.  
- Existing positions already hold 2 symbols at nonzero market value: `positions={"SPY": 25, "QQQ": 25}`.  
- Strategy rotates and emits targets that keep both but also adds a third (or bugs elsewhere generate it): diff produces **one buy** order for `"IWM"` (e.g., due to stale/missing position reporting; or because broker positions didn’t include a small existing holding and it thinks there’s room).  
- `filter_orders()` sees `buys` length = 1, so it approves it.  
**Wrong behavior:** After execution you can end with 3 positions, violating the hard cap. The check must consider current holdings + buys that create new symbols (or net-to-positive `to_notional`), not just the count of buy orders.

4) **Claim:** Per-order notional cap can be bypassed via broker-side rounding/minimums because the check is on `o["notional"]` but submit path may use `qty` elsewhere or rounding changes notional.  
**Severity:** MED  
**Failure scenario:**  
- Order dict contains `qty` (not in this slow-arm path today, but broker.submit supports it). If an upstream change starts sending `qty`, `filter_orders` still checks `o["notional"]`, which may be missing or stale (KeyError or incorrect).  
- Or notional is `30.004` and rounded by broker.submit to `30.00` (ok) vs `29.996` rounds to `30.00` (now exceeds cap post-rounding).  
**Wrong behavior:** Either a crash (KeyError) or sending an order whose actual submitted notional exceeds the intended cap due to rounding rules applied after risk-check.

### src/tradebot/run.py — `run_once`
5) **Claim:** Kill switch can place flatten orders **above `max_order_notional`** (risk caps fail during liquidation).  
**Severity:** HIGH  
**Failure scenario:**  
- `risk.max_order_notional=30`.  
- Existing position market value is `SPY: 45` (possible if price moved after entry; or multiple fills; or legacy holdings).  
- Drawdown triggers; code constructs flatten orders with `"notional": abs(mv)` => 45.  
- It submits directly: `broker.submit(o)` without passing through `risk.filter_orders`.  
**Wrong behavior:** A “hard brake” path violates the pre-registered max order notional. You can easily submit a liquidation order > $30, contradicting risk spec (and if the broker rejects oversized orders, flattening fails and the kill switch leaves exposure on).

6) **Claim:** Halt-file is not honored by the fast/movers arms, enabling trading after the global kill switch.  
**Severity:** HIGH  
**Failure scenario:**

- `run_fast_once` checks only `st.get("halted")` (arm-local) and ignores `cfg.risk.halt_file` / `cfg.halt_path`.  
**Wrong behavior:** Fast/movers keep trading even though the system-wide kill switch has fired. This is a direct kill-switch bypass.

### src/tradebot/fastarm.py — `run_fast_once`

**Wrong behavior:** `cost_accrued` diverges from intended modeled costs; `_mark_equity` subtracts it, potentially triggering (or failing to trigger) `daily_loss_stop_pct` / `max_drawdown_pct` incorrectly.

8) **Claim:** Daily loss stop can continue entering trades after it triggers (same tick) because `stopped_today` is set after flatten, but entry logic is guarded by `elif not st["stopped_today"] and now >= or_end:`; however if the daily stop triggers *inside* that block later in the session, the code continues within the same call before reaching that `elif` (it’s earlier, so ok). The real defect is different: daily stop does not persist across process restarts unless state is saved immediately.  
**Severity:** MED  
**Failure scenario:**  
- `day_pnl_pct` breaches stop; it flattens and sets `st["stopped_today"]=True` but does **not** `_save_state` until end of function.  
- Process crashes after flattening but before `_save_state`.  
- Next invocation reloads state with `stopped_today=False`, and resumes trading the same day.  
**Wrong behavior:** Daily kill switch can be bypassed by a crash/restart window.

9) **Claim:** New-day overnight-flatten can place orders even when the venue is closed (or before open), because `new_day` logic runs after a market-hours gate that uses fixed 9:30-16:00 ET, not the actual exchange calendar/half-days.  
**Severity:** MED  
**Failure scenario:**

- Overnight-flatten logic: if scheduler misses close and runs next day premarket but after 9:30? (or broker.now_et is wrong) it can attempt flattening based on stale `lasts`.  
**Wrong behavior:** Trading/closing logic violates “flat before close” invariant on half-days; can carry positions overnight and also attempt to act in sessions that don’t exist per calendar.
