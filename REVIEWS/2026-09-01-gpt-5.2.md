### src/tradebot/risk.py — `RiskManager.filter_orders`
1) **Claim:** `max_positions` can be bypassed by “rebalance buys” into existing holdings.  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `risk.max_positions = 2`.  
- Current positions already at the cap, e.g. `positions = {"SPY": 25, "QQQ": 25}` (2 symbols held).  
- Strategy emits orders that *buy more* SPY and QQQ (still 2 symbols, no new symbols), plus also buys a 3rd symbol due to a bug/mismatch upstream, e.g. approved orders contain:  
  - buy SPY `to_notional: 30`  
  - buy QQQ `to_notional: 30`  
  - buy IWM `to_notional: 20`  
- `filter_orders` computes `buys = [o for o in approved if o["side"]=="buy" and o["to_notional"]>0]` which counts **all buys**, including SPY/QQQ rebuys. `len(buys)=3` so it rejects buys after the first 2 *in list order*, which is arbitrary and can reject the wrong leg.  
- Worse: if there are **only** 2 buy orders (SPY, QQQ) but the account already holds 2 other symbols (e.g., due to stale `positions`), `filter_orders` does **not** check the existing position count at all—only the number of buy orders. Net result: you can end up with **> max_positions** after execution.

Concrete bypass: `positions` already has 2 names; `orders` contains 1 buy for a *new* name and only sells that execute later (or fail). `filter_orders` sees `len(buys)=1` and approves it, creating a 3rd concurrent position.

### src/tradebot/run.py — `run_once`
2) **Claim:** Kill-switch flatten can place orders above `max_order_notional`, violating the hard cap exactly when risk control is most needed.  
**Severity:** HIGH  
**Failure scenario:**  
- `risk.max_order_notional = 30`.  
- Drawdown breached, `positions = {"SPY": 200.0}` market value (or any value > 30).  
- Code builds `flatten` orders with `notional = abs(mv)` (here 200) and immediately submits them: `results = [broker.submit(o) for o in flatten]`.  
- These orders are **not passed through** `risk.filter_orders`, so the notional cap is bypassed.  
- If the broker enforces notional limits or buying power, the flatten may be **rejected**, leaving exposure **open after the kill switch fired**.

### src/tradebot/run.py — `run_once`
3) **Claim:** Kill switch can “fire” but fail to actually flatten shorts (or any position) due to using `broker.submit()` with a notional derived from `market_value` instead of quantity, and without using `close_position`.  
**Severity:** HIGH  
**Failure scenario:**  
- Suppose a short exists: broker reports positions as market value: `positions = {"SPY": -25.00}` (negative market value for a short).  
- Flatten order becomes: side `"buy"`, notional `abs(mv)=25`. That’s a *notional market order*, not a “close this position” order.  
- If the actual short quantity doesn’t correspond cleanly to $25 notional at current price (price moved, fractional share constraints, rounding, etc.), the buy notional can **under-cover**, leaving a residual short.  
- This is especially likely if the broker rounds notional to cents and converts to qty internally. The fast arm correctly uses `broker.close(sym)` to avoid this dust; the slow-arm kill path does not.

### src/tradebot/signals.py — `momentum_12_1`
6) **Claim:** Look-ahead / stale-data ambiguity: momentum uses `closes.iloc[-(skip+1)]` and `closes.iloc[-1]` for `price` in `snapshot()`, but `broker.daily_closes()` pulls bars up to “now” without ensuring the most recent bar is a *completed* day. This can incorporate partial current-day data in a “daily close” series depending on data vendor behavior.  
**Severity:** MED  
**Failure scenario:**  
- Bot runs intraday (or broker data includes an in-progress daily bar for today).  
- `snapshot()` sets `price = closes.iloc[-1]` (today’s partial), but momentum’s `end` uses `-(skip+1)` which now may refer to a different calendar alignment than intended, effectively shifting the 12-1 window.  
- Strategy decisions then use data not available at prior close (classic look-ahead relative to an intended end-of-day strategy).

This is concrete because `daily_closes()` request has only a `start` and no `end`, and no filtering of “today” vs “completed”.
