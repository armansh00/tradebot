### src/tradebot/risk.py — `RiskManager.filter_orders`
1) **Claim:** `max_positions` can be bypassed via small “top-up” buys (`to_notional` ≤ 0 filter bug).  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `max_positions=2`  
- Current positions: `{"SPY": 10, "QQQ": 10}` (already at cap)  
- Strategy produces orders including a *new* third symbol but with a small target due to rounding/partial fill state, e.g. `buy IWM` with `to_notional=0.01`, `notional=5.00` (delta buy), plus other approved orders.  
- Because buys are counted only when `o["side"]=="buy" and o["to_notional"]>0`, this buy is **not counted toward positions**, so it won’t be rejected by the `len(buys) > max_positions` logic, and the bot can place an order that opens an additional position beyond the cap.

2) **Claim:** `max_positions` enforcement is not based on *post-trade* holdings; it only truncates the list of buy orders, and can still exceed cap when combined with existing holdings.  
**Severity:** HIGH  
**Failure scenario:**  
- `max_positions=2`  
- Existing positions already: `{"SPY": 10}` (1 position)  
- Approved orders include buys for two *new* symbols (e.g., `buy QQQ`, `buy IWM`) and no sell closing SPY (or sell is rejected for notional reasons elsewhere).  
- `len(buys)=2` is not `> max_positions`, so both buys remain approved, resulting in **3 concurrent positions** after execution.

### src/tradebot/risk.py — `RiskManager.book_equity`
4) **Claim:** Book-cap “reset” logic can erase real losses (rebaselining after loss) and prevent drawdown halt.  
**Severity:** HIGH  
**Failure scenario:**  
- `book_cap=50`, baseline initially `100000` (slow arm on legacy $100k paper).  
- A real trading loss drops raw equity from 100000 → 40000 (still “far above the cap” in the comment sense, but **below** `baseline*0.5`).  
- Condition `(raw < baseline*0.5 and raw <= cap*2)` becomes `(40000 < 50000 and 40000 <= 100)` = **False**, so *no reset yet*.  
- Later, due to broker-side event, partial withdrawal, or any equity discontinuity (paper resets, corporate action effects, or API glitch) raw equity is reported as `95` for a moment (or even `100`). Now condition becomes `(95 < 50000 and 95 <= 100)` = **True**, so baseline is reset to 95.  
- From then on `book_equity = min(50 + (raw-baseline), raw)` ≈ `min(50+(raw-95), raw)`. When raw recovers back to something like `100000` (paper systems can “snap back” after glitch/reset), book_equity becomes `min(50+(100000-95), 100000)=99955` (rounded) — **exploding the tradable book** and also **eliminating the drawdown history**, because `check_drawdown` uses this book equity series, not raw.  
- Net: a transient raw equity collapse near `$cap*2` causes a re-anchor that can both (a) erase real loss path relative to the original baseline and (b) scale the “book” far beyond intended $50.

*(This is concretely triggered by any momentary low raw equity observation; the code has no provenance check that the drop is a true “dashboard reset” rather than a reporting glitch.)*

### src/tradebot/fastarm.py — `run_fast_once` / `_fill` (broker mode)
5) **Claim:** Intraday arm ignores global `.halt` kill switch; trades continue even if risk halt file is present.  
**Severity:** HIGH  
**Failure scenario:**  
- Slow arm triggers `RiskManager.halt()` writing `.halt`.  
- Scheduler continues running `run_fast_once` every 30 minutes.  
- `run_fast_once` checks only `st.get("halted")` (arm-local state), never `cfg.halt_path.exists()`.  
- Result: fast/movers arms **continue submitting broker orders** after the system-wide kill switch should have stopped all trading.

6) **Claim:** Flattening can submit the wrong side for shorts in broker mode; `_fill` always calls `broker.close(sym)` for sells, and `broker.close` always returns side `"sell"` even when closing a short requires a buy.  
**Severity:** HIGH  
**Failure scenario:**  
- Account is short `AAPL` (qty = -1) in broker positions_detail.  
- Drawdown kill triggers; loop calls `_fill(..., "sell", sym, ..., qty=pos["qty"], ...)` unconditionally.  
- In `_fill` broker mode, side != "buy" routes to `broker.close(sym)` (good), but the record and intent id are built with `side="sell"` and ledger writes a `"sell"` event. More importantly, earlier in run.py slow-arm flatten uses side based on `mv > 0` and submits a **buy** to cover; fastarm does not.  
- If broker’s `close_position` fails or is rate-limited and you retry, deterministic `intent_id` is not used for close, and side mismatch makes reconciliation/error handling brittle; you can repeatedly attempt “sell” semantics while needing a buy-to-cover. Concrete wrong behavior: **arm can fail to flatten shorts on kill conditions** because it doesn’t compute correct close intent per position sign and doesn’t use idempotent ids for closes.

7) **Claim:** Risk caps on order notional / max positions / trade count are not enforced against broker fills; partial fills and re-runs can exceed intended exposure.  
**Severity:** MED  
**Failure scenario:**  
- `top_k=2`, equity near 50; `budget_per_slot = equity/top_k = 25`.  
- First buy submits `notional=25` but broker partially fills only $10 due to liquidity/odd lot constraints; positions_detail shows smaller market_value but still counts as a position.  
- Next tick, strategy still sees `slots = 2 - len(held)`; held length is 1 so it buys another symbol with `notional=min(25,cash)`; repeated partial fill behavior can lead to many small positions over time because there is no `max_positions` enforcement beyond `top_k` and `held` is derived from broker positions, which can include dust positions; combined with no dust-close logic, **position count can drift above 2** (e.g., leftover dust positions remain after close failures).

### src/tradebot/fastarm.py — `opening_range`
8) **Claim:** Opening-range window can include bars not actually complete by decision time (stale/forward bar inclusion) due to using `bars["t"] < or_end` but `bars["t"]` is bar timestamp (bar start) not bar end.  
**Severity:** MED  
**Failure scenario:**  
- OR ends 10:00. Bar labeled 9:55 represents interval 9:55–10:00 and may not be complete at 9:57 decision time.  
- If broker returns the in-progress 9:55 bar with timestamp 9:55, it satisfies `t < or_end` and is included in OR high/low, which uses data not fully known at decision time.  
- Result: signal uses future intra-bar extremes, overstating breakouts and biasing fills.

### src/tradebot/ledger.py — `Ledger.write`
9) **Claim:** Ledger writes are not atomic; a crash mid-write can corrupt the JSONL and break parsing, potentially losing last run marker and enabling duplicate same-day runs/orders.  
**Severity:** MED  
**Failure scenario:**  
- Process is killed while writing a line; file ends with truncated JSON.  
- Next `Ledger.read()` hits `json.loads(line)` and raises, crashing the bot, or if handled elsewhere, might skip records.  
- `last_run_date()` may return None/older date, so `run_once` may execute again and place orders twice in the same day (no broker-side idempotency in slow arm orders).

**Overall risk assessment:** HIGH — multiple concrete paths exist for trading after a halt, exceeding max positions, and using forward/stale intraday data.
