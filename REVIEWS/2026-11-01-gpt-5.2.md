### src/tradebot/risk.py — `RiskManager.book_equity`
1) **Claim (HIGH): book-cap “reset” logic can erase real losses and bypass the drawdown kill switch.**  
**Why:** baseline is re-anchored when `(raw < baseline * 0.5 and raw <= cap * 2)`. That condition can be satisfied by a genuine trading loss (not just a “dashboard reset”), and once baseline is reset downward, `cap + (raw - baseline)` jumps back up toward `cap`, hiding the loss from `check_drawdown()`.  
**Failure scenario:**  
- Config: `book_cap=50`, `max_drawdown_pct=10`.  
- State: `book_baseline=100000` (slow arm on old $100k paper account per config comment).  
- A real catastrophic trading loss happens inside the account: broker reports `raw=90` (still `<= cap*2 == 100` and also `< baseline*0.5`).  
- `book_equity()` resets baseline to 90 and returns `min(50+(90-90)=50, raw=90) => 50`.  
- `check_drawdown(equity=50)` sees no drawdown at all (HWM likely 50 after a reset) and **does not halt**, even though the true account is down ~99.9% from its prior baseline.

### src/tradebot/risk.py — `RiskManager.filter_orders`
2) **Claim (HIGH): max_positions enforcement is wrong; it counts buy *orders*, not resulting open positions, so it can exceed the cap.**  
**Why:** it computes `buys = [o for o in approved if o["side"]=="buy" and o["to_notional"]>0]` and limits the number of such buy orders. It does not account for existing positions that are *not* being sold to zero, nor for buys that increase positions already held.  
**Failure scenario:**  
- `max_positions=2`. Current positions: `{"SPY": 10, "QQQ": 10}` (already 2 positions).  
- Targets introduce a third symbol without closing one fully (e.g., partial sell in SPY but still nonzero), producing orders:  
  - `sell SPY` to_notional = 5 (still held)  
  - `buy IWM` to_notional = 10 (new position)  
- `buys` has length 1, so it passes. After execution you now hold **SPY, QQQ, IWM = 3 positions**, violating `max_positions`.

3) **Claim (MED): order-notional cap can be bypassed via rounding mismatch between risk check and broker submission.**  
**Why:** `filter_orders` checks `o["notional"] > max_order_notional` on the unrounded float. In `broker.submit()`, notional is rounded to 2 decimals: `round(order["notional"], 2)`. That can flip an order from “allowed” to “actually above cap” at submission time if the threshold is near a rounding boundary and you later change caps, or if broker enforces a stricter comparison on rounded notional.  
**Failure scenario:**  
- `max_order_notional=30.00`.  
- Strategy creates `notional=30.004` (passes if you later change comparison to `>=`, or broker treats 30.00 as strict). After rounding it becomes `30.00` (or vice versa with `29.996 -> 30.00`), creating inconsistent enforcement vs broker-side behavior and potentially sending an order that violates the intended strict cap semantics.

### src/tradebot/run.py — `run_once`
4) **Claim (HIGH): kill switch can fail to actually flatten because flatten orders are themselves subject to `max_order_notional` at the broker, but there is no chunking/looping.**  
**Why:** on drawdown breach, it builds `flatten` orders with `notional = abs(mv)` for each symbol and submits each once. If a position market value is > `$30` (your cap), the broker may reject (or partially fill) the close order. The code does not retry with smaller chunks nor verify positions are actually flat before returning `"killed"`.  
**Failure scenario:**  
- Config: `max_order_notional=30`.  
- You hold SPY with `market_value=45` (possible because target per pick can be ~`(equity*(1-cash_buffer))/2` and equity/book math can allow >30; also market movement can push it above 30).  
- Drawdown triggers. Flatten order is `{"side":"sell","notional":45}`.  
- Broker rejects due to notional constraints (or buying power / fractional constraints).  
- Bot logs `"killed"` and stops future trading due to `.halt`, **but the risky position remains open**, violating “flatten + halt”.

5) **Claim (MED): `force=True` bypasses both “already ran today” and “market_closed” safeguards, and can place trades even when market is closed.**  
**Why:** both checks are guarded by `if not force`. There is no secondary guard preventing order submission on closed markets when forced.  
**Failure scenario:**  
- Operator runs `run_once(..., force=True)` on a weekend or holiday.  
- `broker.market_open()` is False but bypassed; strategy generates orders from daily bars; broker accepts market orders queued for next session (or rejects inconsistently). This can create unintended exposure or inconsistent state relative to “Designed to run once per trading day”.

### src/tradebot/fastarm.py — `_fill` (live/broker mode)
6) **Claim (HIGH): sell-side logic uses `broker.close(sym)` for *all* sell actions, which will liquidate the entire position even if `qty` is meant to be partial; risk/position caps can be violated via unintended over-selling/flattening.**  
**Why:** `_fill(... side="sell", qty=pos["qty"] ...)` ignores `qty` and calls `broker.close(sym)`. If upstream ever calls `_fill` with a partial qty (or if positions_detail qty differs from expected), you can unintentionally close more than intended, breaking strategy accounting and any constraints based on incremental rebalancing.  
**Failure scenario:**  
- Held position is 0.8 shares, but logic intends to sell 0.4 (e.g., future change to scale out, or a bug passes wrong qty).  
- `_fill` calls `close(sym)` and fully liquidates 0.8. Ledger records qty=0.4 “intended”, but broker closes 0.8. State/cost accrual diverges from reality.

### src/tradebot/fastarm.py — `run_fast_once` (broker mode)
7) **Claim (HIGH): max_positions/top_k can be exceeded because `held = _positions(...)` may be stale immediately after submitting buys (async fill), so slots calculation can be wrong.**  
**Why:** In broker mode, `_positions` calls `broker.positions_detail()`. After submitting a market order, Alpaca may not reflect the new position immediately (especially if order is accepted but not filled yet). The loop continues, still sees fewer held positions, and submits additional buys, exceeding `top_k`.  
**Failure scenario:**  
- `top_k=2`. Start with no positions at 10:05.  
- Two breakouts appear; first buy submitted, broker accepts but position not yet in `get_all_positions()`.  
- `held` is not refreshed inside the entry loop after each fill; `slots` is decremented locally, but if earlier `held` count was undercounted and/or an existing position exists but is not yet reported, you can submit too many orders.  
- Result: 3+ concurrent positions in the real account.

8) **Claim (MED): daily loss stop can be bypassed on the first tick of the day due to `day_start_equity` reset conditions being inconsistent and duplicated.**  
**Why:** there are two separate blocks resetting `day_start_equity` using a mix of `st["day"]`, `st["day_equity_set"]`, and `today`, but `new_day` handling updates `st["day"]=today` before the first block, and the conditions include `st.get("day") != today` which is now false—so whether the baseline resets depends on presence/absence of `day_equity_set` key. This makes the baseline fragile across partial state files / older state schema.  
**Failure scenario:**  
- State file from an older version lacks `day_equity_set` but has `day` set to yesterday.  
- On new day, `st.update({"day": today,...})` runs, then the condition `'day_equity_set' not in st` triggers and sets baseline. If state was partially written and includes `day_equity_set` but mismatched value, the second block may reset it again mid-day. Daily P&L comparisons can be against the wrong baseline, delaying or preventing the daily stop.

### src/tradebot/signals.py — `momentum_12_1`
9) **Claim (MED): look-ahead via incorrect sufficiency check; ignores `skip` requirement.**  
**Why:** it checks `if len(closes) < lookback + 1` but uses `end = closes.iloc[-(skip+1)]`. If `skip` is large, you need at least `lookback + skip + 1` observations to ensure `end` exists and corresponds to the intended “skip recent month”. With shorter series, pandas negative indexing will still return something, but it’s the wrong date, effectively using more recent data than allowed.  
**Failure scenario:**  
- `lookback=252`, `skip=21`. Provide `len(closes)=253` (passes current check).  
- `end = closes.iloc[-22]` exists, but `start = closes.iloc[-253]` is the first element. This computes momentum over **231 trading days excluding 21**, not the intended 252 excluding 21, and can accidentally incorporate part of the “skip window” depending on series length and alignment, changing eligibility/selection.
