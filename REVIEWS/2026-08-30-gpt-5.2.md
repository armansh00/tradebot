### src/tradebot/risk.py — `RiskManager.book_equity`
1) **Claim:** Book-cap rebaseline can erase real losses and bypass drawdown/kill logic.  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `risk.book_cap=50`, `risk.max_drawdown_pct=10`.  
- Day 1 baseline set at `raw=1000` → `book_equity=min(50+(1000-1000)=50,1000)=50`.  
- Account loses 60% (real loss) to `raw=400`. Condition `raw < baseline*0.5` triggers “reset” → `baseline=400`.  
- Now `book_equity=min(50+(400-400)=50,400)=50` again. The bot’s tracked equity never reflects the huge loss; `check_drawdown()` sees stable equity and may never halt. This is a kill-switch bypass path for any drawdown that first manifests in `raw` crossing the 50% threshold.

### src/tradebot/run.py — `run_once`
2) **Claim:** Drawdown flattening ignores short positions; kill switch can “fire” but leave exposure on.  
**Severity:** HIGH  
**Failure scenario:**  
- Broker returns `positions={"SPY": -40.0}` (short market value).  
- `risk.check_drawdown(equity)` returns True → code builds `flatten` with `if mv > 0` only, so SPY short is excluded.  
- Bot writes `halted=True` and returns `"killed"` but the short remains open at broker. Risk cap (“flatten + halt”) fails.

3) **Claim:** Kill switch checks capped equity, not raw account equity; can fail to halt on true account drawdown.  
**Severity:** HIGH  
**Failure scenario:**  
- `risk.book_cap=50`, baseline logic keeps `equity` near 50 despite account falling.  
- `run_once` uses `equity = risk.book_equity(broker.equity())` then `risk.check_drawdown(equity)`.  
- Account can drop far more than 10% from its own HWM without triggering halt because the value fed into drawdown is the capped/book equity, not the real account equity. (Even without the 50% rebaseline bug above, this design makes drawdown enforcement inconsistent with the paper account’s true equity path.)

### src/tradebot/risk.py — `RiskManager.filter_orders`
4) **Claim:** `max_positions` enforcement is based on count of buy orders, not resulting portfolio positions; can exceed position cap.  
**Severity:** HIGH  
**Failure scenario:**  
- `max_positions=2`. Current broker positions already hold 2 symbols (e.g., `{"SPY": 25, "QQQ": 25}`).  
- Strategy targets rotate fully into 2 different symbols (`{"IWM": 25, "TLT": 25}`) producing 2 sells + 2 buys.  
- `filter_orders` counts only buy orders (2) → passes. If broker executes buys before sells (or partially fills sells), portfolio can temporarily hold 4 positions, violating `max_positions`. There is no check on *current holdings + pending buys* or on execution ordering guarantees.

### src/tradebot/fastarm.py — `run_fast_once`
5) **Claim:** Per-day reset comment says “carry nothing overnight” but code does not flatten; overnight positions persist.  
**Severity:** HIGH  
**Failure scenario:**  
- End of day: function not called at/after `flat_dt` due to outage/scheduler miss; positions remain in state.  
- Next calendar day: `if st.get("day") != today: st.update({...})` resets counters only; does not close positions.  
- Bot continues with prior day positions, violating stated invariant and potentially bypassing intraday risk controls (e.g., OR stops based on new day OR levels) because the position was never intended to exist.

6) **Claim:** Daily loss stop does not halt further trading that day; it flattens but then can re-enter on the same tick/run.  
**Severity:** HIGH  
**Failure scenario:**  
- At `now >= or_end` and `day_pnl_pct <= -daily_loss_stop_pct`, code flattens and sets `st["stopped_today"]=True`.  
- Immediately after, flow continues into the same `elif not st["stopped_today"] and now >= or_end:` block?  
  - Actually it’s `elif` chained to `if now >= flat_dt:`. The daily-loss-stop block is independent; after it executes, execution continues to the `if now >= flat_dt: ... elif not st["stopped_today"] and now >= or_end:`. Since `stopped_today` is now True, entries are blocked in this invocation.  
  - **But** there is no early return: later runs that day keep `stopped_today=True`, so entries remain blocked.  
This one is **not** a defect in isolation; however, it depends on state persistence. The actual concrete defect is below (state corruption) that can reset `stopped_today` unintentionally.

### src/tradebot/fastarm.py / src/tradebot/risk.py — `_save_state` and `RiskManager._save_state`
7) **Claim:** State files are written non-atomically; partial write/corruption can reset kill switches/counters and allow trading after halt/stop.  
**Severity:** HIGH  
**Failure scenario:**  
- Process crashes or is killed mid-`write_text(json.dumps(...))` for `fast_state_path` or `state_path`.  
- Next run: `_load_state` / `_state` attempts `json.loads` and throws, or (more dangerous) file truncation produces valid but incomplete JSON missing fields like `"halted": true` / `"high_water_mark"` / `"stopped_today"`.  
- Result: kill switch and daily stop can be silently cleared (or crash prevents halt enforcement, depending on exception handling not shown). No atomic temp-file + rename, no fsync, no schema validation.

### src/tradebot/fastarm.py — `run_fast_once` time handling
8) **Claim:** Market session boundaries computed by `now.replace(...)` can be wrong on DST transitions / ambiguous times, causing trading outside intended window.  
**Severity:** MED  
**Failure scenario:**  
- `now` is timezone-aware ET. On DST shift days, `replace(hour=..., minute=...)` does not re-localize; it keeps the same tzinfo but can create ambiguous/nonexistent local times semantics depending on Python’s zoneinfo behavior.  
- `open_dt`, `close_dt`, `or_end`, `flat_dt` can be miscomputed, leading to `now < open_dt` / `now >= close_dt` checks being wrong and allowing ticks during closed market or skipping trading during open market.

---

**Overall risk assessment:** HIGH — multiple concrete kill-switch bypass paths (book-cap rebaseline + capped-equity drawdown + incomplete flattening) and position-limit enforcement that can be violated under realistic execution/order scenarios.
