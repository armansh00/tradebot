### src/tradebot/risk.py — RiskManager.filter_orders
1) **Claim:** `max_positions` enforcement is wrong: it counts buy *orders*, not resulting non-zero positions, and ignores existing holdings.  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `risk.max_positions=2`  
- Current positions: `{"SPY": 25.0, "QQQ": 25.0}` (already 2 positions)  
- Targets shift to `{"IWM": 25.0, "EFA": 25.0}`  
- `strategy.diff_orders` produces 2 sells (SPY, QQQ) and 2 buys (IWM, EFA).  
- `filter_orders` builds `buys=[IWM, EFA]` (len=2) so it approves both buys even though, depending on execution ordering/fills, the account can temporarily hold **4** positions (SPY+QQQ not yet closed, plus IWM+EFA opened). There is no gate preventing exceeding `max_positions` intra-run.

2) **Claim:** `max_positions` logic can be bypassed with target reductions because it checks `o["to_notional"] > 0` rather than post-trade positions; it also ignores “buy to cover” on shorts as a position count risk.  
**Severity:** MED  
**Failure scenario:**  
- Current positions include a short: `{"SPY": -25.0, "QQQ": 25.0}`  
- Target wants to close short: SPY to 0 triggers `side="buy"` with `to_notional=0`.  
- This “buy” is excluded from `buys` list, so position-limit logic doesn’t consider that the bot is operating with shorts/cover actions at all; you can end up with `max_positions` new longs plus outstanding short exposure until cover executes.

### src/tradebot/run.py — run_once
3) **Claim:** Kill switch can be bypassed by `force=True`. `force` skips both “already ran today” and “market_closed” gates, allowing trading when market is closed (or multiple times per day) even though the docstring says “safe to re-run (idempotent per day)”.  
**Severity:** HIGH  
**Failure scenario:**  
- Operator runs `run_once(cfg, broker, force=True)` after the drawdown halt file is *not* present (or was cleared manually).  
- Even if `broker.market_open()` would be false (weekend/after hours), `force` bypasses the check and proceeds to compute signals and submit orders. Any broker that accepts queued DAY orders will place them, violating “run once per trading day” and can cause multiple rebalances per day.

4) **Claim:** Drawdown flatten orders are **not risk-filtered**, so the “hard brakes checked before every order” invariant is false; flatten can violate `max_order_notional` and be silently submitted.  
**Severity:** HIGH  
**Failure scenario:**  
- Config: `risk.max_order_notional=30`  
- Positions: `{"SPY": 200.0}` market value (e.g., account drifted or manual funding); equity drawdown triggers `check_drawdown=True`.  
- `flatten` builds an order with `notional=200.0` and submits it directly via `broker.submit(o)` without calling `risk.filter_orders`.  
- Result: an order 6.7x above the max-order cap is sent despite the risk config.

### src/tradebot/risk.py — RiskManager.book_equity
5) **Claim:** Book-cap “rebaseline” can erase real trading losses after a large loss if raw equity also falls under `cap*2`, preventing the drawdown kill switch from ever seeing the loss magnitude.  
**Severity:** HIGH  
**Failure scenario:**  
- `book_cap=50`, baseline initially `raw=1000` (so book equity ≈ 50 initially).  
- Trading causes real account to drop to `raw=90` (still far below baseline; catastrophic loss). Condition `(raw < baseline*0.5 and raw <= cap*2)` is true (`90 < 500` and `90 <= 100`).  
- Code resets `baseline = raw = 90`, causing `book_equity` to become `min(50 + (90-90)=50, raw 90) = 50`.  
- The slow arm now reports equity ~50 instead of reflecting that the account cratered from 1000 to 90; drawdown vs HWM on the *book* can be massively understated, allowing continued trading instead of halting.

### src/tradebot/fastarm.py — _fill / run_fast_once
6) **Claim:** P&L math is wrong on partial exits (or any mismatch between `qty` passed and stored position qty). `_fill` assumes `pnl=(exit-entry)*qty` and then `pop`s the whole position.  
**Severity:** MED  
**Failure scenario:**  
- State corruption or a future change calls `_fill(..., "sell", qty=0.5*pos_qty, ...)`.  
- `_fill` removes the entire position via `pop(sym)` but computes P&L on only the partial `qty`, leaving the remaining exposure untracked and understating realized P&L; equity/state diverge.

7) **Claim:** Stop logic uses freshly recomputed OR-low from `opening_range(df, or_end)` but **stores** `or_low` in the position and then never uses it; if `bars` source later backfills/revises early bars, the OR-low can move and retroactively change stops (stale/unstable signal boundary).  
**Severity:** LOW  
**Failure scenario:**  
- Broker data vendor revises the 9:35 bar low after initial publication (common with consolidated feeds corrections).  
- Later tick recomputes `ors[sym]` from revised history; stop triggers/not triggers based on data that was not available at decision time, changing trade outcomes ex post.

### src/tradebot/signals.py — momentum_12_1
8) **Claim:** Insufficient-history check ignores `skip`; it should require `len(closes) >= lookback + skip + 1`, but it only requires `lookback + 1`. This can compute momentum using indexes that unintentionally reference the wrong part of the series (negative indexing wraps).  
**Severity:** HIGH  
**Failure scenario:**  
- `lookback=252`, `skip=21`, but `len(closes)=253` (passes current check `>=253`).  
- `end = closes.iloc[-(skip+1)] = closes.iloc[-22]` is valid, but `start = closes.iloc[-(lookback+1)] = closes.iloc[-253]` is valid too; however the intended window is 252 trading days ending 21 days ago, which actually requires at least 274 points.  
- You get a “12-1 momentum” computed over a shorter-than-specified history (and different start date), contaminating eligibility/ranking with a lookback the config did not authorize.

**Failure scenario:**  
- Process crashes while writing a ledger line (partial JSON).  
- Next run: `Ledger.read()` hits truncated line, `json.loads` throws, and `run_once` never reaches `risk.halted()` logging or `last_run_date()` checks; behavior depends on uncaught exception handling (not shown), but it’s concretely a single-point-of-failure for idempotency and auditability.
