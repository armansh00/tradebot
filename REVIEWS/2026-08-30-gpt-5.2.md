### src/tradebot/risk.py — RiskManager.book_equity
1) **Claim (HIGH): book-cap “reset” logic can erase real losses and bypass drawdown kill switch.**  
**Failure scenario:**  
- Config: `risk.book_cap=50`, `risk.max_drawdown_pct=10`.  
- Initial baseline recorded at `raw=1000` (large paper account), so `book_equity = min(50 + (raw-baseline), raw) = 50`. HWM becomes ~50.  
- A genuine trading loss occurs in the real account: `raw` falls to `raw=400` (a real -60% account drawdown).  
- Condition `(raw < baseline*0.5 and raw <= cap*2)` is true (`400 < 500` and `400 <= 100`). Actually second clause is **false** here; but any path where equity collapses to near `cap*2` (e.g., broker reports equity temporarily as `90` due to margin/cash timing, or user withdraws) triggers baseline reset.  
- If broker/equity feed ever reports `raw=90` (<=100) during/after losses, code re-anchors `baseline=90`, making `book_equity ≈ min(50+(90-90)=50, raw=90)=50`, restoring the book to $50 and preventing the slow-arm drawdown halt from reflecting the actual loss path.  
**Wrong behavior:** high-water-mark/drawdown in the slow arm can be made to “forget” losses by baseline reset, keeping equity near cap and avoiding/maximizing delay of kill switch.

### src/tradebot/risk.py — RiskManager.check_drawdown / run.py interaction
2) **Claim (HIGH): halt is written but can still place orders in the same run if flatten orders exceed caps / are rejected elsewhere.**  
**Failure scenario:**  
- Drawdown breach occurs, `check_drawdown()` calls `self.halt(...)` and returns `True`.  
- `run_once()` builds `flatten` orders with `notional=abs(mv)` for each position. If any position market value is, say, `$500` and `broker.submit()` rejects/partially fills (or API error), there is no retry or verification that positions are actually flat.  
- Next scheduler tick: `risk.halted()` will stop *new* runs, but the account may still have open exposure because flatten failed.  
**Wrong behavior:** kill switch claims “flatten + halt” but may leave positions open; halt then prevents future corrective flatten attempts unless `force=True` is used manually.

### src/tradebot/risk.py — RiskManager.filter_orders
3) **Claim (HIGH): max_positions enforcement is logically wrong; can exceed position limit without being rejected.**  
**Failure scenario:**  
- `max_positions=2`. Current positions already hold 2 symbols.  
- Strategy outputs targets that rotate into 2 *different* symbols: you get 2 sells + 2 buys (still 2 final positions), but order list may include **more than 2 buys** if partial reductions create multiple buy legs? More concretely: if positions dict includes 0-valued symbols or broker returns tiny residuals, `diff_orders()` can generate buys for >2 symbols.  
- `filter_orders()` only counts `buys = [o for o in approved if side=='buy' and to_notional>0]` and rejects buys beyond max_positions based solely on the count of buy orders, **not** on the resulting number of distinct non-zero positions after sells+buys.  
- If you already have 2 positions and also generate 2 buys to increase both (rebalances), `len(buys)=2` passes even though you might also be initiating a *third* new position via a buy order whose `to_notional>0` but gets counted within the first 2 buys due to ordering, while an increase-buy on an existing holding gets rejected as “exceeds max_positions”.  
**Wrong behavior:** (a) may allow ending the day with >`max_positions` positions, or (b) reject the wrong buys (existing rebalances) while allowing new positions, depending on order ordering—no invariant on final distinct holdings.

4) **Claim (MED): max_order_notional check uses `o["notional"]` only; can exceed cap via multiple orders on same symbol in one run.**  
**Failure scenario:**  
- `max_order_notional=30`.  
- `diff_orders()` produces multiple orders for the same symbol across reruns (idempotency break, see below) or due to broker returning stale `positions()` during run. Each single order is <=30, but total traded notional for that symbol/day can exceed intended per-run cap.  
**Wrong behavior:** cap is per-order not per-run/per-symbol; risk cap can be bypassed by fragmentation.

### src/tradebot/run.py — idempotency / timezone
5) **Claim (HIGH): daily idempotency check is based on UTC date, not market/ET date; can run twice in one trading day.**  
**Failure scenario:**  
- Bot runs at 19:55 ET (23:55 UTC) and writes a `run` record with `ts` date = today UTC.  
- Bot runs again at 20:10 ET (00:10 UTC next day) while the market is still open/after-hours logic depends on broker; `today = datetime.now(timezone.utc).date()` has advanced, so `ledger.last_run_date() != today`.  
- If `broker.market_open()` returns True (or is buggy around close), it will trade again “same market day” from an ET perspective.  
**Wrong behavior:** duplicate daily rebalance/trades because “day” is tracked in UTC instead of the trading session calendar.

6) **Claim (MED): kill switch can be bypassed with `force=True`.**  
**Failure scenario:**  
- `.halt` file exists (or drawdown halt triggered).  
- Operator/scheduler calls `run_once(..., force=True)`; the halt check is unconditional (good), but force bypasses “already ran today” and “market_closed”. If the halt file is cleared manually (or absent but state high-water mark forgotten/corrupted), `force` enables trading in conditions normally blocked by schedule.  
**Wrong behavior:** operational path that increases chance of violating pre-registered evaluation discipline; not a code exploit, but a bypass path.

### src/tradebot/fastarm.py — _fill / P&L math
7) **Claim (HIGH): modeled cost is not actually removed from P&L as reported; `fast_close.pnl` ignores entry-side cost when position is overwritten.**  
**Failure scenario:**  
- Buy: `entry_px = px*(1+bps)` stored. Good.  
- But if you buy the same symbol again (no guard except `if sym in st["positions"]` in entry loop; however symbol can re-enter after being stopped out within same day), entry is overwritten and previous cost basis is lost, while ledger still counts modeled costs on all fills.  
- Close P&L is `(fill_px - pos["entry_px"]) * qty` for the **last** entry only, ignoring earlier realized P&L/cost if multiple round trips occur in same symbol/day and state was overwritten incorrectly.  
**Wrong behavior:** ledger P&L can be wrong/inconsistent with cash/equity for multi-trade-in-same-symbol paths.

### src/tradebot/fastarm.py — risk caps / kill switch bypass
8) **Claim (HIGH): fast/movers arms ignore `risk.halt_file`; their own `st["halted"]` is independent, so global halt does not stop simulated trading.**  
**Failure scenario:**  
- `.halt` is created by slow-arm drawdown or manual intervention.  
- `run_fast_once()` never checks `cfg.halt_path.exists()`. It only checks `st.get("halted")` (per-arm).  
**Wrong behavior:** kill switch is not global; simulated arms continue trading after the system-wide halt condition “should have fired.”

9) **Claim (MED): fast arm can exceed `top_k` exposure transiently due to stale `slots` and stops/entries ordering within one tick.**  
**Failure scenario:**  
- In the same run, you stop out 1 position (`or_low_stop`) and then enter new ones. `slots = top_k - len(st["positions"])` computed **after** exits (good), but if multiple positions are stopped and candidates loop buys multiple, cash may be insufficient and still buys proceed because `notional=min(budget_per_slot, st["cash"])` is computed each time yet `st["cash"]` can go negative if costs push fill over cash (since fill uses `fill_px` > `px` but `notional` computed off `px`).  
**Wrong behavior:** negative cash / leverage occurs, violating implicit book cap.

10) **Claim (HIGH): buy sizing uses `qty = notional / lasts[sym]` but debits cash at `fill_px` (> lasts), so it can overspend cash and go negative.**  
**Failure scenario:**  
- `st["cash"]=10.00`, `lasts[sym]=10.00`, `bps=0.0005` (5 bps).  
- `notional=min(budget_per_slot, cash)=10.00`, `qty=1.0`.  
- Cash debit = `qty*fill_px = 1*10.005 = 10.005` -> cash becomes `-0.005`.  
**Wrong behavior:** simulated account violates no-leverage constraint; risk cap fails (can accumulate negative cash across trades).

### src/tradebot/signals.py — momentum lookback
11) **Claim (MED): momentum_12_1 ignores `skip` in sufficiency check; can compute with insufficient history for skipped window and silently use wrong bar.**  
**Failure scenario:**  
- Need `lookback + skip + 1` closes to safely index `-(skip+1)` and `-(lookback+1)` without overlapping unintended periods.  
- Code checks only `len(closes) < lookback + 1`. With `lookback=252, skip=21`, series length 253 passes, but `end = closes.iloc[-22]` is valid while `start = closes.iloc[-253]` is valid; however the “skip” intent (exclude most recent month) is meaningless with minimal data and can overlap regime; more importantly, if `skip` is large and `len` barely passes, you may be using end/start that are too close or not representing intended calendar distance.  
**Wrong behavior:** stale/incorrect momentum window relative to configured skip; not look-ahead, but mis-specified data requirement.

### src/tradebot/ledger.py — state corruption
12) **Claim (LOW): ledger writes are not atomic; concurrent runs can interleave JSON lines and corrupt the JSONL.**  
**Failure scenario:**  
- Two scheduler instances run simultaneously, both open file append and write; OS-level append is not guaranteed to be line-atomic across processes.  
**Wrong behavior:** truncated/merged JSON lines break `Ledger.read()`, potentially causing idempotency failures and miscomputed equity series (risk controls relying on ledger history become unreliable).
