## Findings

### src/tradebot/risk.py — `RiskManager.filter_orders`
1) **Claim (HIGH): max_positions cap can be bypassed by “buy” orders with `to_notional <= 0`, allowing more than `max_positions` positions.**  
**Why:** the max-positions filter counts only `buys = [o for o in approved if o["side"] == "buy" and o["to_notional"] > 0]`. A buy order that opens/increases a position but has `to_notional` missing/zero/negative will not be counted toward the cap. `filter_orders` also doesn’t validate presence/types of `to_notional`.  
**Failure scenario:**  
- Inputs: `cfg.risk.max_positions = 2`; `orders` includes three opening buys, but two are malformed:
  ```python
  orders = [
    {"symbol":"SPY","side":"buy","notional":10,"to_notional":10},
    {"symbol":"QQQ","side":"buy","notional":10,"to_notional":0},     # malformed but would open
    {"symbol":"IWM","side":"buy","notional":10,"to_notional":0},     # malformed but would open
  ]
  ```
- Wrong behavior: only SPY counts toward `buys`, so none are rejected for `max_positions`; all three buys are approved -> **3 concurrent positions**.

### src/tradebot/run.py — `run_once`
2) **Claim (HIGH): drawdown kill-switch flatten orders can exceed `max_order_notional` and there is no risk check on them.**  
**Why:** on drawdown breach, `flatten` orders are submitted directly via `broker.submit(o)` without going through `risk.filter_orders`. Each flatten order uses `notional = abs(mv)` where `mv` is position market value. That can be far above the configured `risk.max_order_notional` ($30).  
**Failure scenario:**  
- Inputs: `cfg.risk.max_order_notional = 30`; positions: `{"SPY": 45.00}` (market value). Drawdown breach occurs.  
- Wrong behavior: flatten order generated with `notional=45.00` is submitted anyway, violating the per-order notional cap. If the venue accepts it, the bot breaks its hard risk rule; if the venue rejects large notionals, the bot may fail to flatten despite claiming kill behavior.

3) **Claim (MED): `force=True` allows trading while market is closed (bypasses `broker.market_open()` guard), potentially violating “once per trading day” assumptions and enabling stale-data decisions.**  
**Why:** `if not force and not broker.market_open(): ... return`. With `force=True`, it proceeds to fetch closes, decide, and submit orders regardless of market state.  
**Failure scenario:**  
- Inputs: run at Saturday 14:00 UTC with `force=True`; broker accepts paper orders queued for next session (or rejects inconsistently).  
- Wrong behavior: bot places orders based on stale `broker.daily_closes()`/positions snapshot at a time when it normally would not trade, undermining invariants and potentially bypassing operational kill expectations (e.g., human uses force for rerun but unintentionally trades).

### src/tradebot/fastarm.py — `_fill` (live/broker mode)
4) **Claim (HIGH): exit (“sell”) path ignores side and always calls `broker.close(sym)`; this cannot cover short positions and can increase exposure instead of flattening.**  
**Why:** In live mode:
```python
if side == "buy": broker.submit(...)
else: result = broker.close(sym)
```
`broker.close()` always returns `{"side": "sell" ...}` and calls Alpaca `close_position(symbol)` (which closes by submitting the appropriate opposite-side order). But your wrapper hardcodes `"side": "sell"`, and more importantly `_fill` only ever requests `close()` for any non-buy (including “buy to cover” to exit a short).  
**Failure scenario:**  
- Inputs: account holds a short position in `TSLA` with qty = -0.2 (possible if account is margin/short-enabled, or via manual intervention). Kill switch / EOD flatten triggers `_fill(..., side="sell", sym="TSLA", qty=0.2, ...)`.  
- Wrong behavior: `_fill` calls `broker.close("TSLA")` but records side as sell; depending on broker behavior/wrapper semantics, you can (a) fail to close the short, or (b) submit the wrong direction in logs/intent, making risk/audit wrong. In the worst case, logic that expects “sell reduces exposure” is false for shorts.

### src/tradebot/fastarm.py — `run_fast_once` (broker mode accounting)
5) **Claim (HIGH): simulated cost model is double-counted / mis-scaled when `broker.equity()` already includes realized losses, but `cost_accrued` is applied regardless of whether an order actually filled at the assumed price/size.**  
**Why (concrete):**
- In live mode, `_fill` accrues `cost = abs(qty * px * bps)` **after** checking only `status` strings; it does not verify `filled_qty`/`filled_avg_price` or partial fill status. Alpaca paper can return accepted/new without immediate fill; partials are possible. Yet cost is accrued as if full `qty` filled at `px`.  
- `_mark_equity` then subtracts `cost_accrued` from `broker.equity()`, producing a synthetic net equity that can diverge arbitrarily from actual executed exposure/costs.
**Failure scenario:**  
- Inputs: buy notional intended $25 at `px=250` => `qty=0.1`. Broker accepts order but it doesn’t fill (status `"new"` with `filled_qty=0`).  
- Wrong behavior: `cost_accrued` increases as if filled; `_mark_equity` decreases equity; daily loss stop / drawdown kill can trigger **without any real executed loss**, causing unnecessary liquidation/halts.

### src/tradebot/fastarm.py — `run_fast_once` risk caps
6) **Claim (HIGH): intraday arms do not enforce `risk.max_order_notional` or `risk.max_positions`; configured caps can be violated.**  
**Why:** `run_fast_once` computes `notional = min(budget_per_slot, cash)` with `budget_per_slot = equity / f.top_k`. There is no comparison to the global risk caps in `cfg.risk.*` and no per-order cap other than `if notional < 5: break`.  
**Failure scenario:**  
- Inputs: fast arm account grows to equity = $200 (or misreported due to cost accounting bug); `top_k=2` => `budget_per_slot=100`; cash available $100.  
- Wrong behavior: submits a $100 notional order even though `cfg.risk.max_order_notional=30` is supposed to be a hard brake.

### src/tradebot/signals.py — `momentum_12_1`
7) **Claim (MED): look-ahead / window-definition bug: momentum ignores `skip` when checking sufficiency; can use data more recent than allowed.**  
**Why:** It checks `if len(closes) < lookback + 1: return None` but later accesses `closes.iloc[-(skip + 1)]`. If `skip` is large and series length is only `lookback+1` but `< lookback+skip+1`, the code will still run and the “end” point will be far earlier than intended (or even index into the wrong region), violating the declared 12-1 definition.  
**Failure scenario:**  
- Inputs: `lookback=252`, `skip=21`, `len(closes)=253` (passes check), but `end = closes.iloc[-22]` is valid and corresponds to ~22 trading days ago, while `start = closes.iloc[-253]` is the first element. This computes something closer to **(t-22)/(t-252)** over ~230 days, not 252-day skip-21 momentum.  
- Wrong behavior: strategy ranks on a different horizon than preregistered; also across symbols with varying history length, this creates inconsistent signal definitions.
