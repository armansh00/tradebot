### Findings

**src/tradebot/run.py — `run_once`**  
1) **Claim:** Kill-switch flatten orders can exceed `risk.max_order_notional`, so the flatten can be blocked by the broker and leave risk on.  
**Severity:** HIGH  
**Failure scenario:**  
- Inputs/state: `cfg.risk.max_order_notional=30`. Existing position `positions={"SPY": +100.0}` (market value $100), equity drawdown breaches limit.  
- Code path: `risk.check_drawdown(equity)` returns True → builds `flatten` with `notional=abs(mv)=100`.  
- Wrong behavior: submits a $100 sell notional despite the $30 cap (no call to `risk.filter_orders` on these flatten orders). If broker enforces notional limits / buying-power constraints or rejects oversized orders, flatten fails and the bot returns `{"status":"killed"}` while still holding the position. Risk cap invariant “flatten on kill” fails.

**src/tradebot/risk.py — `filter_orders`**  
2) **Claim:** `max_positions` enforcement is based on number of *buy orders in the batch*, not resulting portfolio positions; it allows ending the run with more than `risk.max_positions`.  
**Severity:** HIGH  
**Failure scenario:**  
- Inputs/state: `cfg.risk.max_positions=2`. Current holdings already at limit, e.g. `positions={"SPY": 25.0, "QQQ": 25.0}`.  
- Strategy targets add a new symbol without selling first due to small deltas being filtered out, e.g. targets `{"SPY":25.0,"QQQ":25.0,"IWM":2.5}` and `min_order_notional` permits IWM buy but SPY/QQQ sells are below dust threshold and therefore omitted.  
- Orders passed to `filter_orders` include exactly one buy (IWM). `len(buys)=1` so it passes.  
- Wrong behavior: after execution, portfolio has 3 positions, violating `max_positions=2`. The check needs to consider existing positions with nonzero exposure plus buys that create new symbols, not just count buy orders.

**src/tradebot/fastarm.py — `_fill` (live/broker mode)**  
3) **Claim:** Sell/exit orders ignore side and quantity semantics; `_fill(..., "sell", ...)` always calls `broker.close(sym)` and assumes it succeeded, but failures can silently leave positions open while state/logic proceed as if exited.  
**Severity:** HIGH  
**Failure scenario:**  
- Inputs/state: live mode, broker rejects close (e.g. trading halted, order rejected, API error) and returns `{"status": "rejected_by_venue"}` or some non-filled status not containing “reject”/“cancel” (or close returns a status like `"accepted"` but never fills).  
- Code path: `_fill` for sells calls `broker.close(sym)`; it only treats as failure if `"reject"` in status or `"cancel"` in status. Many “not filled” states (accepted/new/partially_filled) are treated as success.  
- Wrong behavior: fast arm removes stop metadata (`st["or_low"].pop(sym, None)`) and records a “fast_order” as if the liquidation happened, but the account can still hold the position. Subsequent risk logic (daily stop, EOD flat, drawdown kill) may not retry correctly because the metadata implying a position/stop is gone, and the bot can carry overnight despite believing it flattened.

**src/tradebot/fastarm.py — run loop `run_fast_once` (drawdown kill branch + `_positions` in broker mode)**  
4) **Claim:** In broker mode, the drawdown-kill liquidation can throw or misbehave because position dicts from `broker.positions_detail()` don’t guarantee `last_px`, but downstream code (`book_px`) assumes it may exist; moreover `_fill` sell ignores the `qty` argument entirely in broker mode, so the recorded `qty` can be wrong.  
**Severity:** MED  
**Failure scenario:**  
- Inputs/state: broker mode, held positions returned as `{"SPY":{"qty":0.1,"entry_px":500.0,"market_value":50.0}}` (no `last_px`). `lasts` missing SPY (no bar returned).  
- Code path: drawdown kill iterates positions, calls `book_px(sym, pos, lasts, broker)`. `live_px` returns None, then `book_px` checks `pos.get("last_px")` (missing) then `entry_px` (works).  
- Wrong behavior: liquidation uses `entry_px` as “px” and logs it; in broker mode sell uses `broker.close(sym)` ignoring that px/qty. Ledger now contains materially wrong execution info (qty/px/notional), so equity vs cost attribution and audit trail are corrupted. This undermines drawdown / day P&L explanations and can mask real breaches.

**src/tradebot/fastarm.py — `opening_range` + entry logic in `run_fast_once`**  
5) **Claim:** Look-ahead/stale-bar risk: `intraday_5min(universe)` as implemented always requests bars through 16:00 ET, and `lasts` is taken as the last bar in the returned dataframe. If the data API returns “future” bars within the same request (common for historical/replay or if `day` is passed), `lasts` can reflect information after `now`, contaminating decisions.  
**Severity:** HIGH (in replay / backfill / any mode where bars endpoint returns full-day bars)  
**Failure scenario:**  
- Inputs/state: `run_fast_once(..., now=10:05 ET)` in replay/sweep mode where broker returns the entire day’s bar series up to 16:00 because request end is fixed at 16:00.  
- Code path: `bars = broker.intraday_5min(universe)` and `lasts = df["c"].iloc[-1]` uses the day’s close or a later bar than `now`.  
- Wrong behavior: entries/exits compare `lasts[sym]` to OR high/low using prices not yet known at 10:05, producing systematic look-ahead bias (buys that “knew” the breakout would happen; stops that “knew” it would recover). This directly invalidates the pre-registered evaluation for fast/movers and can bypass loss stops (because a later recovery price suppresses an earlier stop trigger).

**src/tradebot/run.py — `run_once` idempotency guard**  
6) **Claim:** Day boundary/idempotency is based on UTC date (`datetime.now(timezone.utc).date()`), but trading logic is based on US market hours; this can cause double-runs or skipped runs around UTC midnight vs ET trading day.  
**Severity:** MED  
**Failure scenario:**  
- Inputs/state: A run executes at 20:30 ET (00:30 UTC next day) for the same market session/day. `today` becomes next-day ISO date in UTC.  
- Code path: `if ledger.last_run_date() == today` compares UTC dates in ledger timestamps.  
- Wrong behavior: bot may run twice for the same ET trading day (once before 00:00 UTC and once after), placing duplicate rebalances in the same session; or it may skip the real next ET day early morning because UTC date already advanced while ET still prior day. This can break risk caps (extra turnover) and violate “once per trading day” invariant.
